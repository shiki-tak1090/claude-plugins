# 設計書の変換スキル（Markdown → Word / Excel）

正本の Markdown を、納品用の Word や Excel に変換する。**このスキルは設計書の内容を一切変えない。** 内容の正しさは `basic-design` と `detailed-design` スキルのレビューで担保済みとし、ここでは「変換で何も失われていないこと」だけを保証する。

## 基本方針

- **変換は同梱のスクリプトだけで行う。** Claude が Markdown を読んで Word や Excel を手作業で組み立てることはしない。手作業の変換は毎回結果が変わり、要約や行の抜けが起きるため。
- **変換後のファイルを直接編集しない。** 照合で問題が見つかったら、原因を正本の Markdown かスクリプトの側で直し、変換からやり直す。
- **照合に通らないファイルは納品物として扱わない。**

## 0. 前提

`xxxxx_document` リポジトリの直下で実行する。

| パス | 内容 |
|---|---|
| `01_要件定義/` 〜 `05_DB設計/` など | 正本の Markdown（変換元） |
| `99_テンプレート/export/reference.docx` | Word の書式見本（フォント、見出し、表のスタイル）。任意 |
| `99_テンプレート/export/template.xlsx` | Excel の雛形（表紙シートなど）。任意。変換したシートはこの後ろに追加される |
| `exports/docx/`, `exports/xlsx/` | 変換結果。リポジトリ直下からの相対パスと同じフォルダ構成で出力する |

`exports/` は生成物なので `.gitignore` に入れる。納品時は、変換元の Markdown のコミットにタグ（例: `delivery-2026-11-30`）を付け、どの版から作ったかを追えるようにする。フォルダを指定した場合、`.obsidian/`、`.claude/`、`exports/`、`99_テンプレート/` の中は変換しない。

### Obsidian 記法の扱い

| 記法 | Word / Excel での表示 |
|---|---|
| `[[文書]]`、`[[パス/文書\|表示名]]` | 表示名（なければ文書名）の文字列。リンクにはしない |
| `![[パス/画像.png]]` | 画像。変換元と同じフォルダ → リポジトリ直下 → リポジトリ内のファイル名の順に探す |
| `- [ ] 条件` | ☐ 付きの行 |

### 必要なツール

- `uv`（スクリプト冒頭の依存関係の宣言から、python-docx、openpyxl、Pillow、pandoc を自動で用意する）
- Mermaid の図がある場合は `mmdc`（`npm install -g @mermaid-js/mermaid-cli`）。ない場合、docx の変換はエラーで止まる。xlsx は図の代わりに Mermaid のソースを書き出す（この場合、照合は図の数の不一致で NG になる）

pandoc を個別にインストールする必要はない。誰が変換しても同じ出力になるよう、スクリプトは依存パッケージの版を固定しており、pandoc も `pypandoc-binary` に同梱された版（pandoc 3.9）だけを使う。PATH に別の pandoc があっても使わない。版を上げるときは、3 つのスクリプト冒頭の `dependencies` と `exclude-newer` をまとめて変え、上げた後は見た目の確認（5 を参照）を行う。

Bash ツールから実行するときは、出力の文字化けを防ぐため `PYTHONIOENCODING=utf-8` を付ける。

## 1. 変換形式の決定

引数で形式が指定されていればそれに従う。指定がなければ、`CLAUDE.md` の「納品物の一覧」の「形式」の列に従う。どちらもなければ、次の目安で案を出し、ユーザーに確認してから進む。

| 設計書の性質 | 形式 |
|---|---|
| 文章が中心（方式設計、処理概要、業務フローなど） | docx |
| 表が中心で、列が 8 個を超える表がある（テーブル定義、項目定義、メッセージ一覧など） | xlsx |

## 2. 変換前の確認

変換元の Markdown について、次の点を確認する。

1. `【要確認】` や `【基本設計への差し戻し候補】` が残っていないか。残っていれば一覧にしてユーザーに見せ、そのまま納品用に変換してよいか確認する。
2. 変換元に、コミットされていない変更がないか（`git status`）。あれば、そのまま進めてよいかユーザーに確認する。どの版から作ったかを追えなくなるため。

## 3. 変換と照合

スクリプトは `${CLAUDE_SKILL_DIR}/scripts/` にある。変換と照合は必ずセットで実行する。

```bash
# Word
PYTHONIOENCODING=utf-8 uv run ${CLAUDE_SKILL_DIR}/scripts/md_to_docx.py 02_基本設計 03_詳細設計/ランク・ポイント設計.md
# Excel
PYTHONIOENCODING=utf-8 uv run ${CLAUDE_SKILL_DIR}/scripts/md_to_xlsx.py 05_DB設計/テーブル定義.md
# 照合（変換したファイルごとに実行する）
PYTHONIOENCODING=utf-8 uv run ${CLAUDE_SKILL_DIR}/scripts/verify_export.py <変換元.md> <変換後.docx|xlsx>
```

照合スクリプトが確認する内容は次のとおり。

- **本文の欠落と順序**: 見出し、段落、箇条書き、表のセル、コードの各行が、変換後に同じ順序で現れるか
- **ID の出現回数**: 要件 ID や画面 ID などが、Markdown と同じ回数だけ現れるか。既定では `FR-FAV-01`、`ADM-NEWS-01`、`U-1.1` のような形式を ID とみなす。プロジェクトの体系と合わない場合は `--id-pattern` で正規表現を渡す
- **構造**: 図の数。docx の場合は、見出しの並びと、表の数・各表の行数・列数も確認する
- **表示の崩れ（警告）**: 太字にならずに `**` がそのまま出力された箇所

## 4. 照合で NG になったとき

変換後のファイルは直さない。エラーの内容から原因を切り分ける。

| 原因 | 対応 |
|---|---|
| 変換元の Markdown が [記法ルール](${CLAUDE_SKILL_DIR}/references/markdown-rules.md) の範囲外の記法を使っている | 記法だけを直す修正案をユーザーに示し、了承を得てから Markdown を直す。文言や内容は変えない |
| スクリプトの不具合（記法ルールの範囲内なのに崩れる） | スクリプトを直し、**これまで変換したファイルもすべて変換と照合をやり直す** |
| 警告「ID の増加」 | テンプレートの表紙などに含まれる ID なら問題ない。そうでなければ重複出力を疑ってスクリプトを調べる |
| 警告「図にしか書かれていない ID」 | 変換の問題ではないが、記法ルール違反なので、本文か表への追記をユーザーに提案する |
| 警告「強調記号 ** がそのまま出力」 | 閉じの `**` の直前が括弧・句読点になっている。`**` の後ろに半角スペースを入れる修正案をユーザーに示す |
| エラー「図の数が不一致」 | `[画像が見つかりません: …]` が出ていれば画像のパスを確認する。mmdc がなく Mermaid が図にならなかった場合は、mmdc を入れて変換し直す |

## 5. 見た目の確認（人が行う）

照合スクリプトが保証するのは、文字が欠けていないことだけである。レイアウトや書式は確認できない。次のときだけ、ユーザーに変換結果を開いて見た目を確認してもらう。

- 初めて変換するとき
- `reference.docx` や `template.xlsx` を変えたとき
- スクリプトを直したとき、または依存パッケージ（pandoc を含む）の版を上げたとき

それ以外の変換では、見た目の確認は不要と伝えてよい。

### Word の書式見本を初めて用意するとき

`reference.docx` がなければ、pandoc の既定の見本を書き出し、ユーザーに Word でスタイル（見出し、本文、表）を整えてもらう。内容（本文）は消してよく、スタイルの定義だけが使われる。

```bash
uv run --with pypandoc-binary==1.17 python -c "import pypandoc, subprocess; subprocess.run([pypandoc.get_pandoc_path(), '-o', '99_テンプレート/export/reference.docx', '--print-default-data-file', 'reference.docx'], check=True)"
```

## 6. 報告

ユーザーには次の内容を報告する。

1. 変換したファイルの一覧（変換元 → 変換先）
2. 照合結果（すべて OK か。警告があればその内容）
3. 見た目の確認が必要かどうか（5 の条件に当たるか）
4. 変換元の Markdown のコミット（ハッシュかタグ）
