# 未決定事項を見つける観点

段階 3 の初稿を書くときに、この観点と立場で、要件定義書と設計情報から決まらないことを洗い出し、未決定事項一覧に入れる。ここにあるのは未決定事項を見つけるための観点であり、見つけたものを人に聞くためのものではない。人に聞くのは、SKILL.md の「4. 人に聞くこと」で、決める工程が基本設計で優先度が高いものだけである。

## 3 つの段階で探す

| 段階 | 探すこと | 例 |
|---|---|---|
| なぜ作るか | 目的、困っていること、失敗とみなす状態 | 期限切れの植物を見落とすことが、最も避けたい失敗か |
| 何が変わるか | 利用者と運用者の作業、守るべきデータ、止まってよい時間 | 止まっている間、利用者は何ができなくなるか |
| 何を作るか | 構成、稼働場所、データの持ち方、外部との連携、環境 | 本番のほかに、検証の環境が要るか |

## 立場ごとに探す

| 立場 | 探すこと |
|---|---|
| 発注者 | 費用の上限、期限、契約や法令の制約、受け入れられないリスク |
| 利用者 | 使う端末と時間帯、止まったときに困ること、データを失ったときに困ること |
| 運用（通知を受ける人、本番に入る人、復旧する人） | 誰が気づき、誰が直すか、どこまで手で戻せるか |
| セキュリティ | 誰に使わせないか、どの経路を防ぐか、どのデータを守るか、方式に由来する脅威（ほかのサイトからの要求、直接の経路での迂回、総当たりなど） |
| 開発チーム | リポジトリの構成、言語、主なライブラリ、テストの進め方 |

## 基本設計で決めないもの

次のことは、決める工程を基本設計にしない。未決定事項一覧に、決める工程を付けて入れる（[granularity.md](granularity.md)）。

- 画面の項目、文言、メッセージの対応表、一覧の並び順、メニューの置き方、操作の後の遷移先の細部、削除済みのデータを開いたときの応答、二重送信の防ぎ方（機能の詳細設計）
- エラーコードの体系、時間切れの秒数、要求と応答の項目（統合仕様）
- 監視の閾値、ログの保存の設定、マイグレーションを適用する場所と経路、E2E と組み合わせる版、パイプラインの作り（インフラ・運用、setup-architecture）
- 関数やクラスの名前、ライブラリの使い方（実装）
- 会社方針や、設計を進める人が制約として答えたことの理由の詳しさ（理由は答えのままでよい）
- PR や設計書の承認の体制（どの設計書でも決めないこと）
