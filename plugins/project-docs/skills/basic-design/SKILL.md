# 基本設計スキル

要件定義書を入力に、テンプレートに沿って基本設計の文書を Markdown で作る。目指す状態は、**根拠のある設計が書かれ、文書に残る欠陥は 0 件で、人が決める必要のある事項は未決定事項として管理されている** ことである。設計書の正本は Markdown とし、Word や Excel への変換は `design-export` スキルで行う。機能ごとの詳細設計は、このスキルの後に `/project-docs:detailed-design` で作る。

このスキルで AI がすることは、整理、執筆、レビューである。**前提、制約、方式の採用、リスクの受け入れは人が決める。AI は、人が明示した委任の範囲（「3-2. 委任」）を超えて決めない。** 委任のない選択を、設計書に決定事項として書かない。決められないことは、質問で作業を止めずに未決定事項として残し、書き進めるのに要るものだけを人に聞く。基本設計の承認や次の工程の着手に要る判断は、引数「判断 <関門>」のモードで、人が求めたときに決める。

## 0. 前提とディレクトリ構成

このスキルは、ドキュメントのリポジトリ `xxxxx_document` の直下で起動する前提で書いている。このリポジトリは Obsidian の保管庫として閲覧する。コードのリポジトリは兄弟ディレクトリにある。

```
xxxxx/                          # ただのフォルダ（Git 管理しない）
├─ xxxxx_document/              # ← このスキルを起動するリポジトリ
│  ├─ CLAUDE.md                 # ドキュメント作成ルールと納品物の一覧（このスキルより優先する）
│  ├─ 00_プロジェクト概要/        # 用語集.md（用語の統一に使う）
│  ├─ 01_要件定義/              # 要件定義書（入力）
│  ├─ 02_基本設計/              # システム概要、システム構成図、方式設計、非機能要件定義、インフラ方針設計、画面一覧、画面遷移、バッチ処理一覧、仕様確定
│  ├─ 04_API仕様/               # API一覧.md（このスキルで作る）
│  ├─ 05_DB設計/                # テーブル一覧.md と ER図.md（このスキルで作る）
│  ├─ 07_画面仕様書/            # 画面仕様書.md（このスキルで作る）と画面デザイン（.pen）
│  ├─ 09_開発標準/              # 開発標準.md（開発ガイドラインとして納品する。実装規約の正本）
│  ├─ 98_レビュー記録/           # 設計情報、設計判断ログ（社内向け）
│  │  └─ 基本設計/              # 未決定事項一覧、レビューの要旨（社内向け）。レビューの途中経過は作業中/に置き、完了時に消す
│  └─ 99_テンプレート/           # 各文書のテンプレート
├─ xxxxx_backend/
└─ xxxxx_frontend/
```

フォルダ名がこの構成と異なる場合は、`CLAUDE.md` に書かれた構成を優先する。どちらからも判断できないときは、推測で進めずにユーザーにパスを確認する。要件定義書が 1 つに決まらないとき（引数がなく、フォルダに複数あるときなど）も、どれを使うかをユーザーに確認する。

### 社内向けのファイル

| ファイル | 内容 | 完了した後 |
|---|---|---|
| `98_レビュー記録/設計情報.md` | 目的、設計を進める人の立場、委任、利用者と運用者、対象と対象外、制約と決定済みのこと、失敗したときの扱い、判断の優先順位 | 残す（詳細設計で書き足す） |
| `98_レビュー記録/設計判断ログ.md` | 人が決めた判断の結論、回答の原文、選択肢、理由、受け入れるリスク、前提、再検討の条件 | 残す（詳細設計で書き足す） |
| `98_レビュー記録/基本設計/未決定事項一覧.md` | 入力から決められず、人の判断や確認が要る事項。決める工程、必要な関門、進められる範囲、依存、候補案、状態 | 残す（後の工程が読み、決めたら状態を更新する） |
| `98_レビュー記録/基本設計/レビューの要旨.md` | レビューのラウンドごとの件数、欠陥の ID と対応の結果、再指摘の理由、反対役が見つけた欠陥 | 残す |
| `98_レビュー記録/基本設計/作業中/` | 欠陥の台帳、ラウンドごとのレビュー記録、修正の差分、トレーサビリティ、出典の照合、波及の点検、反対役の確認 | 完了したら消す（9-5） |

納品物（`01_`〜`09_`。`CLAUDE.md` の「納品物と社内向けの文書」を参照）から、これらの社内向けのファイルへリンクしない。社内向けのファイルの番号（設計判断ログの `DL-xx`、未決定事項の `U-xx`、欠陥の `F-xx`、設計情報の No）も書かない。顧客はこれらのファイルを読めないため、番号を見ても中身が分からない。納品物には、採用した設計、適用の条件、制約、確かめられる技術的な根拠、未決定事項だけを書く。設計作業で AI を使った経緯（AI の推奨、AI への委任、AI が選んだこと、おすすめ、選択肢の説明）は、設計情報と設計判断ログにだけ書き、納品物には書かない。委任を「発注者の承認」や「会社方針」に置き換えることもしない。製品の機能としての AI など、設計の対象として要る記述はこの限りでない。

残すファイルから `作業中/` のファイルへリンクしない。途中で止まったとき（段階 7 の中断）は `作業中/` を消さない。`作業中/` が残っていることが、レビューが終わっていない印になる。

### 未決定事項一覧

`98_レビュー記録/基本設計/未決定事項一覧.md` に、次の表で書く。基本設計で決めないことを後の工程へ引き継ぐ一覧も兼ねる（後の工程はこの一覧を読み、決めたら状態を更新する）。

```markdown
# 未決定事項一覧（基本設計）

入力から決められず、人の判断や確認が要る事項の一覧。決める工程で、すべてを決める。

作成日：2026-05-01
版：v0.1

---

| ID | 決めること | 決められない理由（足りない情報） | 影響する箇所 | 決める工程 | 対象の機能 | 決める人 | 必要な関門 | 未決定でも進められる範囲 | 依存 | 候補案 | 状態 | 決めた文書・判断 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| U-01 | （例: 計画停止をしてよい時間帯） | （例: 利用の多い時間帯が要件にない） | （例: 非機能要件定義「可用性」） | 基本設計 | — | 発注者 | 基本設計の承認 | （例: 構成と反映の方針は書ける） | — | （例: 平日の夜間） | 未決定 | |
| U-02 | （例: 削除した植物の水やり記録の扱い） | （例: 要件定義書 FR-PLT-02 が「詳細設計で定義」としている） | （例: 画面一覧「DLG-01」） | 機能の詳細設計 | （例: 植物管理） | 開発チーム | 詳細設計:植物管理 | （例: ほかの機能の詳細設計） | — | | 未決定 | |

---

## 変更履歴

| 日付 | 変更者 | 変更内容 |
|---|---|---|
| 2026-05-01 | — | 初版 |
```

- **決める工程**は、基本設計 / 機能の詳細設計 / 統合仕様 / インフラ・運用 / 開発標準・setup-architecture / テスト計画 / 実装 のどれかにする。[granularity.md](${CLAUDE_SKILL_DIR}/references/granularity.md) の文書ごとの範囲と送り先で決める。
- **対象の機能**は、決める工程が機能の詳細設計のときだけ書く。複数の機能に共通するものは「全機能」とし、最初に作る機能の詳細設計で決める。
- **決める人**は、発注者 / 開発チーム / 不明 のどれかにする。分からなければ「不明」と書き、担当者や日付を作らない。
- **必要な関門**には、その事項が決まるまで着手できない作業（関門）を、当てはまるものすべて書く。1 つの事項が複数の関門を止めてよい（同じ ID のまま管理し、関門ごとに別の行を作らない）。

  | 関門 | 当てはまる事項 |
  |---|---|
  | 書き進める | 答えがないと、基本設計の文書の多くの章が書けない（その章を `【未決定】` にするだけでは済まない） |
  | 基本設計の承認 | 顧客との約束（範囲、非機能の水準、費用、セキュリティ、データの扱い、運用）に影響する。どの文書に書かれるかではなく、何に影響するかで決める。迷ったら当てはめる |
  | setup-architecture | 開発標準の決まり（層、配置、主なライブラリ、テスト、横断的なルール、検査）に影響し、実装規約を作れない |
  | 詳細設計:<機能名> | その機能（または全機能）の詳細設計を書けない |
  | インフラ・運用 | インフラの構築や運用手順を書けない |

- **未決定でも進められる範囲**には、その関門の作業のうち、この事項が決まっていなくても進められる部分を書く（例: 「画面の項目は書ける。性能に依存する処理の方式は判断待ち」）。
- **依存**には、この事項を決める前に決まっている必要がある事項の ID を書く。
- **候補案**には、AI の案を書いてよい。候補案は決定ではないので、本文には書かない。
- **状態**は「未決定」か「決定済み」にする。決めたら「決めた文書・判断」に、決めた文書と節、または設計判断ログの番号を書く。
- **決める工程を後の工程に移しても、行を消さず、ID と「未決定」の状態を保つ。** 移した理由を変更履歴に書く。工程を付け直しただけでは、判断は済んでいない。
- 決める工程が基本設計の事項は、本文の影響する箇所に `【未決定】` と、何が決まっていないかを書く（例: 「計画停止の時間帯は【未決定】」）。社内の番号（`U-xx`）は本文に書かない。
- 決める工程が後の工程の事項は、その細部を本文に書かない。ただし、その未決定が基本設計の記述を制約するなら、制約されることを本文に書く（例: 「保存期間は未決定のため、容量の見積もりと削除の処理は未確定」）。本文が、決まっていない値を前提にして書かれていてはならない。
- **未決定事項として認める条件**：何が決まっていないか、何に影響するか、どの工程で決めるか、どの関門を止めるかが一覧で分かり、本文や関係する文書がそれを決定済みとして扱っていないこと。要件定義書や人の回答で決まっていることを、未決定事項に戻してはならない。

### 設計の決まり（CLAUDE.md）

案件の `CLAUDE.md` の「設計の決まり」の節に、いま有効な要件と規約、その適用範囲、変更を承認できる人、承認済みの変更が書かれていれば、それを読む。人の答えや設計の記述が決まりと食い違ったときに使う（「3. 人の答えの扱い」）。節がなければ、食い違いは人に確かめる。

### テンプレート

- テンプレートは `99_テンプレート/` から探す。
- 合うテンプレートがない場合は、次の順で決める。勝手に章立てを決めて書き始めない。
  1. 設計情報、設計判断ログなら、このスキルに同梱の `assets/` のテンプレート（[設計情報](${CLAUDE_SKILL_DIR}/assets/設計情報テンプレート.md)、[設計判断ログ](${CLAUDE_SKILL_DIR}/assets/設計判断ログテンプレート.md)）を使う。`99_テンプレート/` に追加してチームで共有してよいか、ユーザーに確認する。
  2. 納品物のテンプレートがなければ、ひな型（project-template）の最新の `99_テンプレート/` から取り込んでよいか、ユーザーに確認する。取り込めない場合は、同じフォルダにある既存の文書の構成を調べ、テンプレート案を作ってユーザーに確認する。
- テンプレートが Markdown 以外（Excel や Word）で渡された場合は、作業を始める前に、Markdown 版のテンプレートを作ってよいかユーザーに確認する。

### 出力形式

- 記法は [記法ルール](${CLAUDE_PLUGIN_ROOT}/skills/design-export/references/markdown-rules.md) の範囲に限る。このルールは `design-export` スキルでの変換と照合の前提になっているため、必ず守る。
- `CLAUDE.md` のドキュメント作成ルール（Mermaid の使用、`[[]]` リンクの活用など）にも従う。

## 1. 進め方

| 段階 | すること | 人がすること |
|---|---|---|
| 1. 前提の整理 | 入力を読み、書き始めるのに要る前提だけを聞き、設計情報に制約として書く | 答える |
| 2. 文書の地図 | 作る文書と、章ごとの「決めること」と「扱わないこと（送り先）」を表にする | 確認する |
| 3. 初稿 | 確定できることだけで書き、決められないことを未決定事項一覧に入れる | — |
| 4. 人に聞くこと | 必要な関門が「書き進める」の事項だけを聞く。一覧の要約を見せる | 答える。ほかに今決めたいものを選ぶ |
| 5. レビュー | 新しいレビュアーが全体を独立して見て、指摘を欠陥・未決定事項・改善の提案に分ける | — |
| 6. 指摘の仕分けと修正 | 欠陥を台帳に入れて直し、未決定事項を一覧に入れる。修正の後の点検をする | 必要な関門が「書き進める」の新しい事項に答える |
| 7. 修正の確認 | 新しいレビュアーが、台帳の欠陥が解消したかと、修正の影響を確かめる。欠陥が残り 0 件になるまで繰り返す | — |
| 8. 反対役の確認 | 今回新しく選んだ影響の大きい判断に、具体的なリスクがないかを確かめる | 必要な関門が「書き進める」のものに答える |
| 9. 仕上げ | 推敲、仕様確定、レビューの要旨、作業中フォルダの片付け、報告 | — |

人に聞くのは、段階 1、段階 2、段階 4、段階 6、段階 8 だけにし、それぞれ 1 回にまとめる。それ以外の場面で人の判断が要ることに気づいたら、未決定事項一覧に入れ、本文には決めた結果を書かない。基本設計の承認や、次の工程の着手に要る事項は、ここでは聞かず、「10. 関門の判断」のモードで決める。

## 2. 書くときの決まり

- **粒度を守る。** [references/granularity.md](${CLAUDE_SKILL_DIR}/references/granularity.md) の「決めること」だけを書く。範囲の外のことは本文に書かず、未決定事項一覧に、決める工程を付けて入れる。親切のつもりで細部や実装例を足さない。
- **確定できることだけを、決定として書く。** 決定として書けるのは、要件定義書に書かれたこと、`CLAUDE.md` の設計の決まり、会社方針や設計情報の制約、人の回答（設計情報、設計判断ログ）、有効な委任の範囲での選択（「3-2. 委任」）から導けることだけである。導くのに新しい前提や選択が要るなら、決定として書かずに未決定事項にする。一般的な慣習や推奨値も、人の決定の代わりにしない。
- **説明と、選んだ理由を分ける。** 決まった構成や方式から説明できる性質や効果（例: 「業務ルールを画面やデータベースから分けると、業務ルールだけを試験できる」）は、出典がなくても書いてよい。ただし、新しい選択、数値、この案件に固有の保証（例: 「この構成なら性能要件を満たす」）を足してはならない。効果が未決定の事項に左右されるなら、「〜が決まれば」と条件を付ける。一方、人が何のために、なぜ選んだか（選んだ目的や理由）は、人の回答や記録にない限り補わない。
- **すべての設計項目に根拠を付ける。** 要件 ID を書く（テンプレートにトレーサビリティ欄があればそこへ、なければ項目末尾に `[根拠: FR-FAV-01]` の形式で）。人が決めたことが根拠なら、`[根拠: 発注者の決定（2026-05-01）]` か `[根拠: 開発チームの決定（2026-05-01）]` と書く。「誰」は、その決定に責任を持つ組織（設計を進める人の立場、委任による選択なら委任した組織）で、発注者か開発チームのどちらかにする。社内向けのファイルの番号は書かない。
- **選んだ理由は、記録にあるものだけを書く。** 書けるのは、人が答えた理由（「会社方針」「社内標準」「チームの実績」などはそのまま十分な理由として扱い、意味を聞き直さない）と、採用した案の技術的な根拠（質問のときに選択肢の説明として示し、設計判断ログに残ったもの、または委任による選択で記録した根拠）である。技術的な根拠は「採用した案の根拠」として書き、「発注者や開発チームがこの理由で選んだ」とは書かない。どちらもなければ「—（未確認）」と書き、作成者が補わない。
- **人が答えた文言は、そのまま使う。** 水準や用語（「平日」など）を言い換えない。
- **納品物に、設計作業で AI を使った経緯を書かない。** 「AI の推奨」「委任」「おすすめ」「選んだ選択肢の説明」などは、設計情報と設計判断ログにだけ書く（「0. 社内向けのファイル」）。
- **テンプレートの構造を変えない。** 章立て・見出し・表の列は削除も並べ替えもしない。該当しない項目は削らずに「該当なし（理由: …）」と書く。
- **テンプレート内の記入指示や記入例（`{{…}}` や `（…を記述）`）は、本文で置き換える。** テンプレートの「**書き方のルール**」の箇条書きは作成者への指示なので、作った文書には残さない。
- **用語・ID・名称を統一する。** 用語集と既存の文書の表記に合わせる。新しい画面 ID や API ID を採番するときは、既存の体系に従う。
- **同じことを 2 か所に書かない。** 段階 2 の「正とする文書」の表で決めた文書にだけ書き、ほかの文書からはリンクで参照する。
- **版は実行中に上げない。** 新しく作った文書は v0.1 のまま、変更履歴は「初版」の 1 行だけにする。既存の文書を更新した場合は、9-1 の後に 1 回だけ版を上げる。納品物の変更履歴には、文書の内容がどう変わったかを書き、社内の作業の名前や番号は書かない。
- 新しく作った文書は、そのフォルダの `README.md` の「ドキュメント一覧」の表に 1 行追加する。

使うマーカーは次のとおり。

| マーカー | 意味 |
|---|---|
| `【未決定】` | 基本設計で決めることのうち、まだ決まっていないこと。未決定事項一覧に行がある |
| `【仮定】` | 作成者が仮に置いた前提。設計情報にだけ書き、設計書の本文には書かない |

人が決めた判断は、設計書の本文に決めた結果を書き、理由は設計判断ログに書く。AI が決めたことを示すマーカー（`【設計判断】` など）は使わない。

## 3. 人の答えの扱い

- **会社方針と、設計を進める人の答えは、制約として扱う。** 言語、フレームワーク、稼働場所、層の分け方などを「会社方針」「チームの方針」と答えられたら、それで確認を終える。理由を聞き直したり、ほかの案と比べ直したりしない。要件との具体的な矛盾や、実現できない問題が見つかったときだけ、その問題への対応を聞く。
- **答えが質問、異議、保留なら、決定として記録しない。** 「その他」の記入や返事が、問いへの質問（「なぜ今それを聞くのか」「違いは何か」など）、異議、保留だったら、まず答えるか説明し、必要なら同じ問いを聞き直す。保留なら、未決定事項のまま残す。
- **答えを受け取ることと、判断が確定することを分ける。** 答えが、要件定義書、`CLAUDE.md` の設計の決まり、テンプレート、ほかの答えと食い違ったら、確定として記録しない。次の順で扱う。
  1. `CLAUDE.md` の設計の決まり（有効な要件と規約、適用範囲、承認済みの変更）で解消できるかを確かめる。食い違う相手がテンプレートで、テンプレートが決まりに追従していないだけなら、答えを確定し、テンプレートの追従漏れとして報告する。
  2. 解消しなければ、食い違いを示し、「決まりや既存の文書に合わせる」か「決まりと関係する文書を変える」かを聞く。後者なら、変える決まりと文書の範囲と、その変更を承認できる人（設計の決まりにあれば、その人）を示す。どちらが優先するかを AI が決めない。
  3. 解決するまで、その事項は未決定事項として残す（理由に食い違いを書く）。
- **答えは、確定したらすぐに記録する。** 次の作業に進む前に、設計判断ログ（「回答の原文」を含む）か設計情報に書き、未決定事項一覧の状態を「決定済み」にする。
- 設計判断ログに残すのは、後から変えると影響が大きいもの、標準から外したもの、意見が割れたもの、制約で妥協したもの、暫定の対応、委任による選択である。それ以外の答えは設計情報に書く。判断した人が述べていない理由を、推測で書き足さない。

### 3-2. 委任

人は、範囲と守る条件を決めて、選択を AI に委任できる（例: 「画面のライブラリとテストの道具は、決まった構成と会社方針に合う範囲で任せる」）。

- 委任は、設計情報の「委任」に、委任した人（立場）、日付、範囲、守る条件、範囲外の扱いを記録したときにだけ有効になる。記録がなければ、AI は選ばずに未決定事項のまま残す。AI が委任を勝手に推定しない。
- 委任を求めるときは、範囲と守る条件の案を示し、人が承認したら記録する（「10. 関門の判断」）。委任してほしいと人に頼むのは、1 回の確認にまとめる。
- AI が委任の範囲で選ぶのは、範囲に入り、守る条件と依存する事項（一覧の「依存」）をすべて満たす選択だけである。依存する事項が未決定なら、選ばずに残す。範囲の外の選択や、既存の制約と食い違う選択は、人に聞く。
- 委任の範囲で選んだことは、設計判断ログに、委任の記録とは別に書く。「判断した人」は「委任による選択（設計情報の委任 No.n）」とし、選んだ案、比べた案、技術的な根拠を書く。委任した人の承認を個別に得たようには書かない。
- 委任の範囲で選んだことについて、同じ承認を人に繰り返し求めない。報告で、委任の範囲で選んだことの一覧を見せる。
- 納品物では、委任による選択の決定責任を、委任した組織（例: 開発チーム）として書く。AI や委任のことは書かない。

## 4. 人に聞くこと

スキルの初回の実行で人に聞くのは、**必要な関門に「書き進める」が入っていて、決める人が設計を進める人である未決定事項だけ** にする。それ以外は聞かずに未決定事項一覧に残し、「10. 関門の判断」のモードで、人が求めたときに決める。質問が多いと、人が本当に決めるべきことに集中できず、確認の手間も大きくなるため。

### 聞き方

- 1 つの事項を 1 つの質問にし、AskUserQuestion で聞く（1 回に 4 問まで。おすすめを先頭に置く）。選択肢ごとに、採ったときに何が変わるかを description に書く。質問文には、答えによって基本設計のどこが変わるかを 1 文で添える。
- 互いに依存する選択（例: 画面のライブラリとテストの道具）は、そろった 1 組の推奨案として 1 つの質問にしてよい。その場合も、組に含まれる選択とそれぞれの影響をチャットに表で見せ、「この組でよい」「一部を変える（番号と変更を書く）」を選べるようにする。複数の重要な判断を、組にして見えなくしない。
- 選択肢の中で使う用語（「平日」など）は、聞くときに意味を書いておく。
- 「今のまま」と「変える案」を並べて聞くときは、今のままだと何が起きるか（前提、起きる失敗、満たせなくなる要件）と、変えると何が良くなり何を失うかを書く。それが書けないなら、聞かずに「問題なし」として扱う。
- 段階 4 の質問の数の目安は 3〜5 問である。それを超えるときは、「書き進める」の当てはめが甘いか、粒度が細かすぎる可能性が高い。地図と関門を見直す。
- 聞いたあとに、未決定事項一覧の要約（関門ごとの件数と、決める人ごとの件数）を見せ、ほかに今決めたいものがあれば番号で選んでもらう。選ばれなければ、未決定のまま進める。
- その場にいない関係者（発注者など）の回答が要るものは、聞かずに「決める人: 発注者」として未決定事項一覧に残す。9-2 で仕様確定の「確認をお願いする事項」に載せる。

## 段階 1. 前提の整理

1. 要件定義書を読む。要件 ID の体系（例: `FR-FAV-01`, `NFR-FAV-01`, `UC-FAV-01`）と、画面 ID の体系を把握する。ID がない場合は、見出し番号を要件の参照キーとして使い、その旨を最終報告に書く。
2. `CLAUDE.md` の「納品物の一覧」、`00_プロジェクト概要/用語集.md`、`00_プロジェクト概要/リポジトリ一覧.md`、既存の基本設計書、`98_レビュー記録/設計情報.md` と `98_レビュー記録/設計判断ログ.md`（あれば）を読む。
3. 要件定義書の中で **「詳細設計で定義」「詳細設計で決める」「別途定義」** など、判断を設計に委ねている箇所と、`【要確認】` を grep で洗い出し、未決定事項一覧の最初の行にする。
4. 設計情報テンプレートに沿って、`98_レビュー記録/設計情報.md` を作る（あれば更新する）。要件定義書から書けることは要件 ID で参照する。
5. 書き始めるのに要る前提だけを、1 回にまとめて聞く。要件定義書や設計情報で決まっていれば聞かない。
   - 設計を進める人の立場（発注者 / 開発チーム / 発注者と開発チームを兼ねる）
   - コードリポジトリの構成（例: 画面とサーバーを分けるか、1 つにまとめるか）
   - 各リポジトリの言語・フレームワーク。**サーバー側の言語を選択肢で聞くときは、Rust を先頭に置く**
   - データベース
   - 稼働させる場所（クラウドの種類など）
   - 判断の優先順位（データの保全、運用の手間、費用、開発の速さ など）
   - 役割のうち、システムの作りが変わるもの：監視の通知を受ける人、本番の環境に入れる人、障害から復旧する人

   方式設計の「技術の選定」に載る選択（言語、フレームワーク、データベース、稼働場所）は、理由が設計情報などで分かっていなければ、選択を聞いた後に 1 回だけ、まとめて理由を選んでもらう（会社方針 / チームの実績 / 発注者の指定 / その他。技術ごとに違えば自由記入）。答えは、それで十分な理由として扱い、聞き直さない（「3. 人の答えの扱い」）。答えがなければ「—（未確認）」とする。開発の進め方の取り決め（PR や設計書の承認、公開の許可と担当など）は聞かない（[granularity.md](${CLAUDE_SKILL_DIR}/references/granularity.md) の「どの設計書でも決めないこと」）。
   答えは設計情報の「設計を進める人」と「制約と決定済みのこと」に書く。答えが「未定」なら、未決定事項にする。

## 段階 3. 初稿

テンプレートに沿って、段階 2 の書く順に、地図の範囲だけを書く。質問で作業を止めない。

- 確定できること（「2. 書くときの決まり」）だけを決定として書く。
- 書いている途中で、新しい前提や選択が要ったら、決定として書かない。決める工程が基本設計なら本文に `【未決定】` と何が決まっていないかを書き、未決定事項一覧に行を足す。決める工程が後の工程なら、本文には書かず、一覧にだけ足す。典型的なのは次の場面である。
  - 構成要素やサービスを足す（例: 振り分けの仕組み、証明書、通知のサービス）
  - 人が答えた用語や水準を、別の言葉にする
  - 環境ごとに扱いを変える
  - 要件や答えにない振る舞いや値を決める（例: 保存期間を 90 日にする）
- 未決定事項を見つける観点は、[references/question-checklist.md](${CLAUDE_SKILL_DIR}/references/question-checklist.md) を使う。

文書ごとの書き方は次のとおり。

- **システム概要**：要件定義書を書き写さず、要約と要件 ID とリンクにする。
- **非機能要件定義**：テンプレートの項目を削らない。水準は確かめられる形（数値、条件）で書き、決まっていない水準は `【未決定】` にする。約束しない項目は「目標を置かない」と理由を書く。
- **システム構成図**：利用者の通信の経路の図と、運用のための構成を分ける。
- **方式設計**：技術の選定、アプリケーションの構成、データの扱い、外部との連携、品質の確保の方針を、方式の名前ではなく顧客にとっての利点で書く。選んだ理由は、人が答えたものを書く（「会社方針のため」の 1 行でよい）。
- **インフラ方針設計**：方針までを書く。設定値や手順は未決定事項一覧（インフラ・運用）に回す。
- **画面一覧・画面遷移**：画面 ID を採番する。
- **テーブル一覧・ER図**：テーブル名は、要件の用語を英語の複数形の snake_case にする（既存の統合仕様があれば、その体系に従う）。ER図には、主キーと外部キーのほかのカラムを書かない。
- **画面仕様書**：画面一覧と同じ画面 ID で、同じ順に書く。「元のデータ」はテーブル一覧のテーブル名で書く。
- **API一覧**：API ID は `API-<機能の略号>-<2 桁の連番>` で採番する。画面仕様書の「できる操作」のうち、データを読み書きするものに、対応する API があること。
- **バッチ処理一覧**：バッチ処理 ID は `BAT-<2 桁の連番>` で採番する。
- **開発標準**（開発ガイドライン）：コードリポジトリごとに、層と責務・依存してよい向き・迷いやすい配置の決め方・横断的なルール・テストの方針・機械的な検査の方法を決める。ほかの文書の方針は書き写さず参照し、適用の細部と検査の道具の設定は書かない（粒度の決まり）。
- 開発手法やアーキテクチャの方式の名前（TDD、DDD など）と具体的な決まりは、開発標準にだけ書く。`01_`〜`08_` の文書には混ぜない。
- 図は、1 つの図で 1 つのことを伝える。図の前の文で、何を伝える図かを書く。
- 作った文書は、それぞれのフォルダの `README.md` の表に 1 行ずつ足す。

### 自己点検

書き終えたら、段階 4 に進む前に次を確かめる。

- 段階 2 の「作る文書」がすべてあり、`README.md` の表に載っていること。
- 要件 ID と、設計書の扱った箇所の対応表を `作業中/traceability.md` に出す。どこにも対応しない要件は、意図的な対象外か、未決定事項か、漏れかを判定し、漏れなら書き足す。
- **出典の照合**：納品物の「の決定（」「選んだ理由」「理由」と、根拠が要件 ID でない記述を集め、1 件ずつ出典（要件 ID、設計情報の行、設計判断ログの番号）と突き合わせて `作業中/出典の照合.md` に書く。出典のない決定は、`【未決定】` にして未決定事項一覧に入れる。
- 本文の `【未決定】` と、未決定事項一覧の「決める工程: 基本設計」で「未決定」の行が、1 対 1 で対応していること。一覧のすべての行に、必要な関門と、未決定でも進められる範囲が書かれていること。
- 本文が、決まっていない値（未決定事項）を前提にして書かれていないこと。後の工程で決める事項が基本設計の記述を制約するなら、そのことが本文に書かれていること。
- 非機能要件定義の「約束の対象外」が、設計判断ログの「受け入れるリスク」の文言どおりであること。
- 文書どうしで ID と名前がそろっていること（画面 ID、テーブル名、構成要素の名前）。
- 段階 2 の「正とする文書」の内容が、ほかの文書に書き写されていないこと。
- 納品物（`01_`〜`09_`）に、社内向けのファイルの番号（`DL-`、`U-`、`F-`）と「本人」がないこと（grep で確かめる）。
- 納品物に、設計作業で AI を使った経緯がないこと。「AI」「委任」「推奨」「おすすめ」「選択肢の説明」を grep で集め、1 件ずつ文脈で確かめる（製品の機能としての AI など、設計の対象の記述は残す。語を一律に消さない）。
- テンプレートの見出しがすべて残り、「書き方のルール」が残っていないこと。
- 記法ルールの範囲外の記法を使っていないこと。

## 段階 5. レビュー（独立コンテキスト）

### 5-1. レビュアーの起動方法

レビューは **作成者（このセッション）とは文脈を共有しないサブエージェント** に任せる。

| 役割 | エージェント | 起動する数 |

| 文書のレビュー | `project-docs:basic-design-reviewer` | 下の表のまとまりごとに 1 体 |
| 横断レビュー | `project-docs:basic-cross-reviewer` | 1 体 |
| 反対役 | `project-docs:basic-decision-challenger` | 段階 8 で 1 体 |

| レビュアー | レビュー対象 | 出力先の名前 |
|---|---|---|
| 文書のレビュー 1 体 | システム概要、システム構成図、方式設計 | 概要と構成 |
| 文書のレビュー 1 体 | 非機能要件定義、インフラ方針設計 | 非機能とインフラ |
| 文書のレビュー 1 体 | 画面一覧、画面遷移、画面仕様書 | 画面 |
| 文書のレビュー 1 体 | テーブル一覧、ER図、API一覧、バッチ処理一覧 | データとAPI |
| 文書のレビュー（コードリポジトリごとに 1 体） | 開発標準の、そのリポジトリの節。全リポジトリに共通の節は、最初のリポジトリのレビュアーだけが見る | 開発標準_<リポジトリ名> |

- 作成時の判断理由、作成者の見解、結論を誘導する言葉は渡さない。
- 全員の結果がそろってから仕分けに進む（読んでいる途中で文書を書き換えない）。

## 段階 6. 指摘の仕分けと修正

レビュアーは、指摘を **欠陥・未決定事項の候補・改善の提案** に分けて返す。作成者は、まず分け方を確かめ、次のように扱う。

| 種類 | 中身 | 扱い |
|---|---|---|
| 欠陥 | 要件との矛盾、根拠のない断定、記載漏れ、文書の中や文書どうしの矛盾、粒度を超えた記述、明文化された記入ルールの違反 | 重大度を付けて欠陥の台帳に入れ、直す。残り 0 件を目指す |
| 未決定事項の候補 | 入力から決められず、人の判断や確認が要ること | 未決定事項一覧に入れる。本文がそれを決定済みとして扱っていれば、それは「根拠のない断定」の欠陥として台帳にも入れる |
| 改善の提案 | 要件や記入ルールに違反せず、よりよくするための案 | 重大度を付けず、対応は任意。採るかどうかは作成者が決め、採らなくてもよい |

### 6-1. 欠陥の台帳

`作業中/欠陥の台帳.md` に、欠陥を固定の ID で書く。ID はラウンドをまたいで変えない。

| ID | 重大度 | 箇所 | 問題 | 違反する要件・基準 | 解消の条件 | 対応 | 状態 |
|---|---|---|---|---|---|---|---|
| F-01 | Major | 非機能要件定義「可用性」 | （問題） | （要件 ID、テンプレートの規定、粒度の決まり、ほかの文書の記述など） | （何がどうなっていれば解消か） | （直した箇所） | 未解消 / 解消 / 対象外 |

- 複数のレビュアーが同じ問題を指摘していたら、1 つの ID にまとめる。
- 作成者が誤検出と判断したものは、根拠（要件 ID、粒度の決まり、人の決定など）を「対応」に書き、状態を「対象外」にする。「問題ないと考える」だけの理由は認めない。Critical を対象外にするときは、人に確かめる。
- **実在する欠陥を、リスクとして受け入れたり、後の工程に送ったりして、解消済みにしない。** 欠陥を直す方法が人の判断を要するなら、その判断を未決定事項にし、本文を `【未決定】` にして断定を外すことで欠陥を解消する。要件定義書や人の回答で決まっていることを未決定に戻して、欠陥を消してはならない。

### 6-2. 直し方

- **直し方が新しい判断を要するなら、作成者が決めない。** 値、用語、対象の範囲、構成要素、環境ごとの扱いを変えたり足したりする直し方は、未決定事項にする。必要な関門に「書き進める」が入るものだけを、この段階でまとめて聞く（「4. 人に聞くこと」の聞き方）。それ以外は `【未決定】` のまま残し、関門を一覧に書く。
- **直すときに、文書の粒度を上げない。** 細部を書き足して欠陥を消さない。
- **レビュアーの指摘の文をそのまま採らない。** 正とする文書の書き方と、人が決めたことの文言に合わせて書く。
- **判断が置き換わったら、前提も直す。** 前の判断の区分を「置き換え済み」にし、設計情報と、非機能要件定義の「約束の対象外」も同時に直す。

### 6-3. 修正の後の点検

直したら、修正の確認に進む前に次を行う。

1. 直すのは、正とする文書だけにする。ほかの文書に書き写されていたら、参照に置き換える。
2. 変えた事実や判断ごとに、探す語の一覧（変える前の文言、言い換え、関係する値や用語）を作り、全文書と用語集で grep して、書いている箇所をすべて直すか参照に置き換える。
3. 修正の差分を `作業中/修正の差分_r{ラウンド番号}.md` に書く（`git diff` の出力か、変えた箇所の一覧）。差分に段階 3 の自己点検をもう一度かける。
4. 新しいサブエージェント（`general-purpose`）を 1 体起動し、波及の漏れを探させる。渡すのは、作業ディレクトリ、修正の差分、段階 2 の「正とする文書」の表、出力先（`作業中/波及の点検_r{ラウンド番号}.md`）だけにする。指示は「差分で変わった事実や判断が、ほかの文書・用語集・設計情報・設計判断ログ・未決定事項一覧に、古いまま残っていないか、食い違っていないかだけを探し、箇所と古い記述を表で返す。設計書は書き換えない」とする。見つかったものを直す。

## 段階 7. 修正の確認と終了条件

### 7-1. 修正の確認のプロンプト（雛形）

ラウンド 2 以降は、直したかどうかの確認を中心にする。レビュアーは、これまでどおり毎回新しく起動する。前のラウンドの欠陥と対応を渡すので、解消した論点の掘り返しを防げる。

```
あなたは設計レビュアーです。指示はエージェント定義に従ってください。

モード: 修正の確認
作業ディレクトリ: {xxxxx_document の絶対パス}
レビュー対象: {まとまりの全文書のパス。横断レビューでは対象の全文書のパス}
欠陥の台帳: 98_レビュー記録/基本設計/作業中/欠陥の台帳.md（このまとまりの欠陥）
修正の差分: 98_レビュー記録/基本設計/作業中/修正の差分_r{前のラウンド番号}.md
要件定義書: {要件定義書のパス}
設計情報: 98_レビュー記録/設計情報.md
設計判断ログ: 98_レビュー記録/設計判断ログ.md
未決定事項一覧: 98_レビュー記録/基本設計/未決定事項一覧.md
テンプレート: {まとまりの全文書のテンプレートのパス。横断レビューでは「なし」}
用語集: {00_プロジェクト概要/用語集.md。なければ「なし」}
粒度の決まり: ${CLAUDE_SKILL_DIR}/references/granularity.md
レビュー観点: ${CLAUDE_SKILL_DIR}/references/review-checklist.md
指摘の出力先: 98_レビュー記録/基本設計/作業中/{まとまりの名前 | 横断}_review_r{ラウンド番号}.md
```

- 修正の確認で起動するのは、未解消の欠陥があるまとまりと、修正の差分で変わった文書を含むまとまりと、横断である。どちらにも当たらないまとまりは起動しない。
- レビュアーの結果で、台帳の状態を更新する。新しく見つかった欠陥は、新しい ID で台帳に足す。

### 7-2. 終わる条件

- **完了：** 台帳のすべての欠陥（過去のラウンドと反対役のものを含む）が「解消」か「対象外（根拠付き）」になり、最新の修正の確認でそれが確かめられたこと。未決定事項は、未決定事項一覧で管理されていれば残ってよい。
- **進んでいないときは止めて相談する：** 次のどれかに当たったら、ラウンドを重ねずに止め、原因と残っている欠陥を見せてユーザーに判断を仰ぐ。
  - 解消したはずの欠陥が、同じ箇所で 2 回再発した
  - レビュアーの基準が揺れている（あるラウンドで求められたことを、次のラウンドで逆に指摘された）
  - 欠陥を直すには人の判断が要るが、それを未決定事項にできない（要件と矛盾するなど）
- **上限：** 修正の確認は最大 4 ラウンドとする。上限に達しても欠陥が残っていたら、「未収束で中断」として報告し、完了とは書かない。`作業中/` は消さない。

## 段階 8. 反対役の確認

欠陥が残り 0 件になったら、完了と判定する前に、`project-docs:basic-decision-challenger` を新しく 1 体起動する。渡すのは、作業ディレクトリ、設計判断ログ、設計情報、未決定事項一覧、対象の文書のパスと、出力先（`作業中/反対役の確認.md`）だけにする。

- 対象は、今回新しく選んだ影響の大きい判断（構成、方式、水準など）と、リスクの受け入れ、先送りに限る。会社方針や、設計を進める人が制約として答えたことは、具体的な矛盾がない限り対象にしない。
- 反対役は、見つけたものを欠陥・未決定事項・改善の提案に分けて返す。欠陥は台帳に入れて段階 6・7 の流れで直し、確かめる。未決定事項は一覧に入れる。改善の提案は報告に入れる。
- 人に聞くのは、反対役が具体的なリスク（前提、起きる失敗、満たせなくなる要件）を示し、必要な関門に「書き進める」が入るものだけにする。それ以外は未決定事項一覧に、関門を付けて入れる。「4. 人に聞くこと」の聞き方に従う。
- 反対役の確認は 1 回だけ行う。問題がなければ「問題なし」で終えてよい。

## 段階 9. 仕上げ

### 9-1. 日本語の推敲

レビューが終わった設計書を、Skill ツールで `natural-japanese` スキルを呼び出して推敲する。対象は段階 3 で作った文書だけとする。呼び出すときは、次の制約を必ず伝える。

- 見出し、章番号、表の構造（行・列）、テンプレートの項目名は変えない
- 要件 ID、画面 ID、API ID、テーブル名、カラム名、API パス、コード、数値、単位は一字も変えない
- `[[リンク]]` の中身は変えない
- `【未決定】` のマーカーは残す
- 推敲は文体と読みやすさに限る。設計内容の追加・削除・解釈の変更はしない
- 人が答えた水準や用語の文言（設計判断ログの「回答の原文」）は変えない
- 設計書の文体は「である調」で統一する（テンプレートや `CLAUDE.md` に指定があればそれに従う）
- Markdown の記法は記法ルールの範囲を守る

natural-japanese のスクリプトを Bash から実行するときは、`PYTHONIOENCODING=utf-8` を付ける。

推敲後、推敲前後で、各種 ID の出現回数、見出しと `[[リンク]]` の一覧、表の数と行数・列数が一致することを確かめる。一致しなければ元に戻す。納品物に社内向けのファイルの番号や名前が出てこないことも確かめる。

### 9-2. 仕様確定

`99_テンプレート/仕様確定テンプレート.md` に沿って、`02_基本設計/仕様確定.md` を作る。新しいことは決めず、すでに決まったことと未決定事項を、発注者が読める形に写す。

| 章 | 写す元 | 写し方 |
|---|---|---|
| 確定した仕様 | 設計判断ログのうち「反映した文書」が `01_`〜`08_` の判断と、設計情報の「制約と決定済みのこと」 | 事項、確定した内容、理由（人が答えた理由か、採用した案の技術的な根拠。なければ「—（未確認）」）、決定責任（その決定に責任を持つ組織。委任による選択なら委任した組織）、状態（「確定」。発注者の承認が要る事項で、まだ承認を得ていなければ「承認待ち」）、決めた日、反映した文書の章 |
| 確認をお願いする事項 | 未決定事項一覧のうち、決める工程が基本設計で、決める人が発注者の行 | 確認事項、決められない理由、設計書の該当箇所、根拠の要件 |

- 社内向けのファイルの番号は書かない。作ったら 9-1 と同じ制約で推敲する。

### 9-3. 改善を戻す

レビューで繰り返し出た種類の欠陥（ラウンドや文書をまたいで 2 回以上出たもの）があれば、`references/review-checklist.md` の「プロジェクト固有」に足す観点か、テンプレートの記入ルールに足す内容の案として、報告に書く。追加するかどうかはユーザーが決める。

### 9-4. レビューの要旨

`98_レビュー記録/基本設計/レビューの要旨.md` に、次を書く。`作業中/` のファイルへのリンクは書かない。

- ラウンドごとの件数（欠陥の重大度ごと、未決定事項の候補、改善の提案）と、起動したレビュアー
- 欠陥の台帳の要旨（ID、重大度、箇所、問題の要旨、対応の結果、対象外の根拠、再指摘があればその理由）
- 反対役が初めて見つけた欠陥と、その扱い
- 終わり方（完了 / 未収束で中断）

### 9-5. 作業中フォルダの片付け

完了したときだけ、`98_レビュー記録/基本設計/作業中/` をフォルダごと消す。消す前に、残すファイル（設計情報、設計判断ログ、未決定事項一覧、レビューの要旨）と納品物に、`作業中/` のファイルへの参照が残っていないことを grep で確かめる。未収束で中断したときは消さない。

### 9-6. コミット

コミットは `xxxxx_document` リポジトリで行い、コードのリポジトリの変更と混ぜない。コミットや PR の作成は、ユーザーに指示されたときだけ行う。指示されたら、`develop` から作業用のブランチ（例: `feature/<担当者>/basic-design`）を切って作業し、PR の向き先は `develop` にする。ブランチ運用が `CLAUDE.md` に書かれていれば、それに従う。

### 9-7. 報告

ユーザーには次の形で報告する。結論から書く。

```

基本設計の承認：承認を求められる（または「判断待ち n 件」と、その事項と決める人）
次の工程：
  setup-architecture：着手できる（または「判断待ち n 件」と事項）
  詳細設計：<機能名> は着手できる。<機能名> は <事項> が判断待ち（進められる範囲：…）
  インフラ・運用：…
未決定事項：n 件（決める工程ごと、決める人ごとの件数）
```

関門ごとの判断は、未決定事項一覧の「必要な関門」と「未決定でも進められる範囲」から作り、ひとまとめに「進められる」と書かない。

そのうえで、次を箇条書きで短く書く。

1. 作った文書と、`作業中/` を消したこと
2. 人に聞いた事項の数（段階ごと）
3. レビューのラウンド数と、ラウンドごとの欠陥の件数の推移
4. 人が決めた判断と、委任の範囲で選んだこと（設計判断ログの番号と結論）、反対役の確認の結果
5. 仕様確定、未決定事項一覧、レビューの要旨のパス
6. 改善を戻す案（9-3）

判断待ちの関門があれば、`/project-docs:basic-design 判断 <関門>` でその関門に要る判断を決められることを添える。次の工程として、機能ごとの詳細設計は `/project-docs:detailed-design <機能名>` で、開発標準のコードリポジトリへの落とし込みは各コードリポジトリで `/project-dev:setup-architecture` で行うことを添える。Word や Excel での納品が必要な場合は、`/project-docs:design-export` で変換できることを最後に 1 行で添える。

## 10. 関門の判断（引数: 判断 <関門>）

基本設計の初回の実行が完了した後に、人が「次の関門に進みたい」と求めたときに使う。未決定事項を消化すること自体が目的ではなく、指定された関門の作業を始められる状態にするために、要る判断だけを、少ない手間で決める。関門は、`基本設計の承認`、`setup-architecture`、`詳細設計:<機能名>`、`インフラ・運用` のどれかを指定する。

1. **対象を選ぶ。** 未決定事項一覧のうち、状態が「未決定」で、必要な関門に指定の関門が入っている行を集める。後の工程に移した行も含め、統合仕様など基本設計以外の工程の行も漏らさない。依存（一覧の「依存」）の順に並べる。
2. **事項ごとに、決め方を分ける。**

   | 決め方 | 当てはまる事項 | すること |
   |---|---|---|
   | 決まりの当てはめ | 要件定義書、`CLAUDE.md` の設計の決まり、会社方針、決定済みの判断から導ける | 導いて確定し、出典を記録する。人には聞かない |
   | 委任の範囲での選択 | 設計情報の「委任」に有効な記録があり、範囲と守る条件と依存をすべて満たす | 「3-2. 委任」に従って選び、記録する。人には聞かない |
   | 人の判断 | 上のどちらにも当たらない | 決める人が設計を進める人なら、「4. 人に聞くこと」の聞き方で聞く。決める人が発注者なら、ここでは決めず、仕様確定の「確認をお願いする事項」に載せる |

3. **委任を提案してよい。** 人の判断が要る事項のうち、技術的な選択で顧客との約束に影響しないもの（例: 開発標準のライブラリ、配置、テストの道具）がまとまってあれば、範囲と守る条件の案を示し、委任するかを 1 回だけ聞いてよい。委任されなければ、それぞれを人の判断として扱う。この案件で一度委任された範囲は、次の関門でも有効であり、同じ承認を求めない。
4. **反映する。** 決めたことを本文と未決定事項一覧に反映し、`【未決定】` を消し、設計判断ログか設計情報に記録する。決めた事項に依存していた事項があれば、手順 2 に戻って続ける。
5. **確かめる。** 変えた箇所に段階 3 の自己点検と 6-3 の修正の後の点検をかけ、変えた文書を含むまとまりと横断を、段階 7 の修正の確認のプロンプトで確かめる。欠陥が残り 0 件になるまで、段階 6・7 の流れで直す。
6. **仕上げる。** 変えた文書を 9-1 と同じ制約で推敲し、仕様確定を更新し、レビューの要旨に追記する。既存の文書の版は、1 回だけ上げる。
7. **報告する。** 9-7 の形で報告し、指定の関門を開けられたか（開けられないなら、残っている事項と、それを決める人）を先頭に書く。
