# 詳細設計の手順（detailed）

[SKILL.md](../SKILL.md) の共通の決まりに加えて、詳細設計では次の手順で進める。粒度は [granularity.md](granularity.md) の「機能ごとの詳細設計」の表に従う。

詳細設計は、基本設計の方針を前提に、実装とテストができるところまで具体化する。基本設計の方針を説明し直したり、変えたりしない。

## 段階 1. 前提の整理

1. **基本設計書があることを確かめる。** `02_基本設計/` に方式設計がなければ作業を止め、先に `/project-docs:system-design basic` を実行するよう伝える。
2. 次のものを読む。
   - 要件定義書（対象の機能の要件）
   - 基本設計書（`02_基本設計/`）と開発標準（`09_開発標準/開発標準.md`）
   - `98_レビュー記録/設計情報.md` と `98_レビュー記録/設計判断ログ.md`
   - `98_レビュー記録/基本設計/詳細設計への申し送り.md` のうち、対象の機能（または全機能）の行
   - 統合仕様（`04_API仕様/`、`05_DB設計/`）の現状
   - `00_プロジェクト概要/用語集.md`
   - 画面仕様は `07_画面仕様書/` の `.pen`（JSON 形式）から画面名や要素を読んでよいが、編集はしない
   - 既存のコードがある場合は、兄弟ディレクトリのリポジトリ（`../xxxxx_backend` など）を読んで、現状の実装と矛盾しないかを確認してよい。ただし **コードのリポジトリには書き込まない。**
3. **この機能で閉じる事項を一覧にする。** 次の 2 つを合わせたものが、この詳細設計で「決めるか `【要確認】` にする」事項になる。
   - 要件定義書で「詳細設計で定義」「別途定義」などとされた事項（grep で洗い出す）
   - 申し送りのうち、この機能が対象のもの
4. 設計情報と判断ログで決まっていない前提があれば、質問の一覧にして 1 回で聞く。答えは設計情報に書き足す。

## 段階 2. 文書の地図

詳細設計テンプレート（`99_テンプレート/詳細設計テンプレート.md`、なければ同梱の `assets/詳細設計テンプレート.md`）の章ごとに、この機能で決めることを表にして、ユーザーに 1 回で確認してもらう。統合仕様のどの節を追加・変更するかも含める。

| 章 | この機能で決めること | 扱わないこと（送り先） |
|---|---|---|
| 要件ごとの設計 FR-PLT-02 | 削除の処理の流れ、削除した植物の水やり記録の扱い（申し送り HS-01） | 削除の処理を置く層（タスクの「実装の配置」） |

## 段階 3. 判断事項

SKILL.md の「3. 判断事項の扱い」に従う。詳細設計で人に返すことの例は次のとおり。

- 段階 1-3 の事項のうち、要件定義書と基本設計から 1 通りに決まらないもの（例: 同じ日に 2 回目の水やりを記録したときの扱い）
- 業務ルールの境界（上限値、日付の境界、0 件のとき）で、要件から決まらないもの
- 利用者に見える振る舞いの選択（エラー時に入力を残すか、など）

## 段階 4. 作成

テンプレートに沿って、段階 2 の地図の範囲を書く。各処理について、少なくとも次をそろえる。

- 起点（何をきっかけに動くか）、入力、条件、更新の対象と順序
- 業務ルールと入力チェック（型、桁、必須、形式、範囲、相関）
- 異常系（エラーコード、利用者への表示、ログ、処理の継続か中断か）
- 同時実行、二重送信、やり直したときの扱い
- テストの観点（受け入れ条件に落とせる粒度か）

段階 1-3 の事項は、テンプレートの「要件定義で詳細設計に委ねられた事項」と「基本設計からの申し送り」の表に、決定内容と該当箇所を書く。決めたら、申し送りのファイルの「決めた詳細設計」欄にこの設計書を書く。

詳細設計で基本設計を変える必要があると判断したら、基本設計を勝手に変えず `【基本設計への差し戻し候補】` として記録する。

### 統合仕様への反映

API とテーブルの正は、統合仕様（`04_API仕様/API設計書.md`、`04_API仕様/openapi.yaml`、`05_DB設計/テーブル定義.md`、`05_DB設計/ER図.md`）とする。機能ごとの詳細設計書と統合仕様に同じ定義を二重に書くと、片方だけ直されてずれていくため、次のように分担する。

| 書く場所 | 内容 |
|---|---|
| 機能ごとの詳細設計書 | 設計方針、処理の流れ、業務ルール、異常系。追加・変更するテーブルやエンドポイントの **一覧と変更点** を書き、全項目の定義は統合仕様へのリンク（`[[05_DB設計/テーブル定義#ranks]]` など）にする |
| 統合仕様 | テーブルとエンドポイントの全項目の定義 |

- 統合仕様は、この機能で追加・変更する節だけを編集する。他の機能の節は書き換えない。
- `API設計書.md` と `openapi.yaml` は必ず両方を同じ内容に直す。片方だけの変更は禁止する。
- 既存のテーブルやエンドポイントを変更する場合は、影響する他の機能の設計書を grep で洗い出し、`【影響確認】` として一覧にする（他の機能の設計書は書き換えない）。

### 自己点検

- 要件 ID と、段階 1-3 の事項の対応表を `98_レビュー記録/<機能名>/traceability.md` に出力する。段階 1-3 の事項は、すべて決まっているか `【要確認】` になっていること。
- 本文が抽象的なままの箇所（「適切に」「考慮する」で終わる記述）がないこと。
- テンプレートの見出しがすべて残っていること。
- [markdown-rules.md](markdown-rules.md) の範囲外の記法を使っていないこと。

## 段階 5〜7. レビュー

SKILL.md の「4. レビュー」〜「6. 再レビューと終了条件」に従う。詳細設計では、ラウンドごとに次を並列に起動する。

| レビュアー | レビュー種別 | レビュー対象 |
|---|---|---|
| 詳細設計書に 1 体 | 詳細設計 | `03_詳細設計/<機能名>設計.md` |
| 横断 1 体 | 横断（詳細設計と統合仕様） | 詳細設計書と統合仕様の各ファイル（`API設計書.md`、`openapi.yaml`、`テーブル定義.md`、`ER図.md`） |

詳細設計では「詳細設計に送る」の仕分けは使わない。範囲の外（実装の配置、ライブラリの使い方など）の指摘は、送り先（開発標準、タスク、実装）を書いて「不採用」にする。

## 段階 8〜9

SKILL.md の「7. 反対役の確認」〜「9. 最終出力と報告」に従う。確認事項一覧は `98_レビュー記録/<機能名>/確認事項一覧.md` に出す。
