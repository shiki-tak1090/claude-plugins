# アーキテクチャの固定

開発標準で決めた実装の方針を、このコードリポジトリで**後から参画した人や AI が実装しても崩れない形**にする。

方針を文章で書いておくだけでは、実装は少しずつずれていく。そのため、このスキルは次の 3 つをそろえる。

| 何を | どこに | 役割 |
|---|---|---|
| 実装規約 | このリポジトリの `CLAUDE.md` の「アーキテクチャと実装規約」の節 | 実装する人と AI が、実装の前に必ず読む具体的なルール |
| 機械的な検査 | lint の設定やアーキテクチャテスト | 依存の向きなど、機械で確かめられるルールを、違反したら失敗させる |
| 検査のコマンド | `CLAUDE.md` の「テスト・lint・ビルド」の表 | `/project-dev:implement` と実装照合のレビュアーが、毎回実行する |

方針そのもの（何を採用し、なぜか）は、このスキルでは決めない。正本はドキュメントリポジトリの `09_開発標準/開発標準.md`（開発ガイドライン）であり、方針を変えるときはそちらを先に直す。

## 守ること

- **正本にないルールを足さない。** 開発標準.md に書かれていない方針を、このスキルが独自に決めて規約にしない。足りないと思ったら、開発標準.md の修正候補として報告する。
- **方式の名前だけの規約を作らない。** 「DDD を採用する」とだけ書くと、人によって解釈が分かれる。規約には、名前ではなく具体的なルール（どの層に何を置くか、何を参照してよいか）だけを書く。
- **守らせられないルールは採用しない。** 機械でも、レビューでも確かめられないルールは、形だけ残って無視される（例: 「すべての実装ファイルの隣に仕様書を書く」）。そうしたルールは規約に入れず、「採用しなかったルール」として理由とともに報告する。
- **既存の違反を、検査の除外設定で黙って隠さない。** 4 の手順で扱う。
- **ファイルの変更は、内容を見せて了承を得てから行う。** コミットは、ユーザーに指示されたときだけ行う。

## 0. 前提の確認

1. コードリポジトリの直下で実行されていること。親フォルダにドキュメントリポジトリ（`../<案件名>_document`）があること。
2. `../<案件名>_document/09_開発標準/開発標準.md` があり、このリポジトリの節（「リポジトリごとの決まり」の `<このリポジトリ>`）があること。
   - なければ止まる。開発標準は基本設計の段階で決めるものなので、先に `<案件名>_document` で `/project-docs:basic-design` を実行し、開発標準（`99_テンプレート/開発標準テンプレート.md`）を作ってもらう。
3. **着手を止める未決定事項がないこと。** 次のどれかに当たれば、一覧を見せて止まる（決まっていない方針を規約にすると、あとで作り直しになるため）。先に `<案件名>_document` で `/project-docs:basic-design 判断 setup-architecture` を実行して決めるよう伝える。
   - 開発標準の、このリポジトリの節と全リポジトリに共通の節に、`【未決定】` か `【要確認】` が残っている
   - `../<案件名>_document/98_レビュー記録/基本設計/未決定事項一覧.md` に、状態が「未決定」で、必要な関門に `setup-architecture` が入っている行がある。その行が依存する行（「依存」の列）も、未決定なら含める
   次のものは止める理由にしない。一覧にして報告だけする。
   - 必要な関門が「setup-architecture の中で決める」のように、この作業の中で決める行（決めたら、未決定事項一覧の状態を更新するようユーザーに伝える）
   - 必要な関門に `setup-architecture` が入っていない行
3-2. **API の方式を確かめる。** API の方式は、ドキュメントのリポジトリの `02_基本設計/方式設計.md`（「技術の選定」）を読んで決める。このプラグインが対応している方式は、REST と OpenAPI（正本は `openapi.yaml` と `API設計書.md`）と、GraphQL（正本は `schema.graphql` と `API設計書.md`）である。対応していない方式なら、API の取り決めとの一致を検査する仕組みは作らず、「プラグインがこの API の方式に未対応」と、判断待ちとは別の理由として報告する。それ以外の規約と検査は進める。
4. `git status` に未コミットの変更がないこと。あれば、進めてよいか確認する。

## 1. 読むもの

- 開発標準.md の、このリポジトリの節と「採用する方針（決定記録）」の表。開発標準.md の版（文書の「版」とドキュメントリポジトリのコミット）も控える
- このリポジトリの `CLAUDE.md`、版の指定ファイル、パッケージの設定（`package.json`、`pyproject.toml`、`Cargo.toml`、`go.mod` など）、lint の設定
- 既存のコード（あれば）。フォルダ構成と、層をまたぐ参照の実態を把握する

## 2. 実装規約を作る

`CLAUDE.md` に「アーキテクチャと実装規約」の節を作る。節は次の目印で囲み、このスキルを再実行したときに置き換えられるようにする。目印の外側（各リポジトリが独自に書いた部分）には触らない。

```markdown
<!-- setup-architecture: ここから（直接編集しない。変更は開発標準.md を直してから /project-dev:setup-architecture を再実行する） -->
## アーキテクチャと実装規約
...
<!-- setup-architecture: ここまで -->
```

節には、次の項目をこの順で書く。

1. **正本**：`../<案件名>_document/09_開発標準/開発標準.md`（版とコミット）。実装の前に、この節と正本を読むこと
2. **層と責務**：層、フォルダ、置くもの、置かないもの（正本の表を、このリポジトリの実際のパスで書く）
3. **依存してよい向き**：正本の表をそのまま写す。「○」以外は禁止と明記する
4. **迷いやすい配置の決め方**：正本の表を写す
5. **横断的なルール**：エラー、ログ、設定値、認証・認可、データがないときの扱い
6. **テストの方針**：進め方、テストの種類と置き場所、層ごとのテストの書き方
7. **お手本の実装**：後述の 5 で決めたパス（まだなければ「未定」）
8. **API の取り決め**：方式設計で決めた API の方式と、仕様の正本の場所（REST なら `../<案件名>_document/04_API仕様/openapi.yaml`、GraphQL なら `../<案件名>_document/04_API仕様/schema.graphql`。どちらも振る舞いは `API設計書.md`）。正本の中身は写さず、場所だけを書く。開発標準の「機械的な検査」に API の取り決めとの一致の検査（例: 正本から型を作る、実装の API と正本の差を検査する）が書かれていれば、方式に合わせて 3 で作る
9. **既存の違反**：4 で扱うもの（なければ「なし」）

各ルールの末尾に、どう確かめるかを付ける。

| 印 | 意味 |
|---|---|
| `[検査]` | 3 で作る機械的な検査で確かめる。違反すると検査のコマンドが失敗する |
| `[レビュー]` | 機械では確かめられないので、実装照合のレビュアー（`project-dev:impl-reviewer`）が確かめる |

`[検査]` にできるルールは、できるだけ `[検査]` にする。どちらも付けられないルールは、規約に入れない（「守ること」を参照）。

## 3. 機械的な検査を作る

`[検査]` のルール（少なくとも「依存してよい向き」）を、検査の仕組みに落とし込む。言語ごとの道具の選び方は [references/enforcement-tools.md](${CLAUDE_SKILL_DIR}/references/enforcement-tools.md) に従う。

- 検査の設定は、依存の表から機械的に作る。表と設定がずれないよう、設定ファイルの先頭に「正本: 開発標準.md の版」とコメントで書く。
- 検査を実行するコマンドを決め、`CLAUDE.md` の「テスト・lint・ビルド」の表に「アーキテクチャの検査」の行として追加する。
- 道具を追加する場合（開発用の依存パッケージなど）は、追加するものを見せて了承を得る。CI の設定があれば、CI でもこの検査を実行するよう追加することを提案する（追加は了承を得てから）。

**検査が本当に違反を見つけるかを確かめる。** 設定を作っただけで満足しない。

1. 禁止されている参照を 1 つ含む一時ファイルを作る（例: domain 層から infrastructure 層を import する）
2. 検査のコマンドを実行し、**失敗すること**を確かめる
3. 一時ファイルを削除し、検査のコマンドが成功することを確かめる

失敗しなければ、設定が効いていない。直してからやり直す。

## 4. 既存のコードの違反を扱う

既存のコードに違反があれば、一覧（ファイル、違反しているルール）にしてユーザーに見せ、扱いを決めてもらう。

| 扱い | 内容 |
|---|---|
| 直す（おすすめ） | 違反を直す実装タスクを、ドキュメントリポジトリで `/project-dev:design-to-tasks` を使って作る。直るまでは下の「一時的に許可」と同じ扱いにする |
| 一時的に許可 | 違反しているファイルを、検査の除外に**ファイル単位で**登録する。規約の「既存の違反」の欄に、ファイル、理由、解消の予定（課題キーなど）を書く。新しいファイルを除外に足すことはしない |

除外を、層やフォルダの単位でまとめて登録しない。新しい違反まで見逃すことになるため。

## 5. お手本の実装を決める

後から参画した人や AI が「どう書けばよいか」で迷ったときに真似できる、お手本の実装を 1 つ決める。お手本のためだけの、動かないサンプルコードは作らない（保守されずに古くなるため）。

- 既存のコードに、規約どおりに層をまたいで実装された機能があれば、それをお手本にする
- まだなければ、最初の実装タスクをお手本にする。そのタスクを `/project-dev:implement` で実装した後、人が規約に照らして重点的にレビューし、規約の「お手本の実装」の欄にパスを書く（このスキルを再実行して書いてもよい）

## 6. 報告

次の内容を報告する。

1. 作成・更新したもの（`CLAUDE.md` の節、検査の設定、追加した道具、検査のコマンド）
2. 検査が違反を見つけることを確かめた結果
3. 規約の一覧（`[検査]` と `[レビュー]` の数）
4. 採用しなかったルールと、その理由
5. 既存の違反と、その扱い
6. 開発標準.md の修正候補（正本で決まっていなかったこと、具体的でなかったこと）
7. 次の手順：コミットして PR を作ること。以後の実装は `/project-dev:implement` が規約と検査に従うこと
