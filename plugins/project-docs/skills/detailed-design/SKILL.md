# 詳細設計スキル

基本設計の方針を前提に、機能ごとの詳細設計書を Markdown で作り、統合仕様に反映する。目指す状態は、**根拠のある設計が書かれ、文書に残る欠陥は 0 件で、人が決める必要のある事項は未決定事項として管理されている** ことである。設計書の正本は Markdown とし、Word や Excel への変換は `design-export` スキルで行う。

詳細設計は、実装とテストができるところまで具体化する。基本設計の方針を説明し直したり、変えたりしない。

このスキルで AI がすることは、整理、執筆、レビューである。**前提、制約、方式の採用、リスクの受け入れは人が決める。AI は、人が明示した委任の範囲を超えて決めない。** 委任のない選択を、設計書に決定事項として書かない。決められないことは、質問で作業を止めずに未決定事項として残し、書き進めるのに要るものだけを人に聞く。

## 0. 前提とディレクトリ構成

このスキルは、ドキュメントのリポジトリ `xxxxx_document` の直下で起動する前提で書いている。このリポジトリは Obsidian の保管庫として閲覧する。コードのリポジトリは兄弟ディレクトリにある。

```
xxxxx/                          # ただのフォルダ（Git 管理しない）
├─ xxxxx_document/              # ← このスキルを起動するリポジトリ
│  ├─ CLAUDE.md                 # ドキュメント作成ルールと設計の決まり（このスキルより優先する）
│  ├─ 00_プロジェクト概要/        # 用語集.md（用語の統一に使う）
│  ├─ 01_要件定義/              # 要件定義書（入力）
│  ├─ 02_基本設計/              # 基本設計の文書（入力。変えない）
│  ├─ 03_詳細設計/              # 機能ごとの詳細設計（このスキルで作る）
│  ├─ 04_API仕様/               # API一覧.md（基本設計）と、API の仕様の正本（方式設計で決めた方式による）
│  ├─ 05_DB設計/                # テーブル一覧.md と ER図.md（基本設計）と、テーブル定義.md（全機能の統合仕様）
│  ├─ 07_画面仕様書/            # 画面仕様書.md（基本設計）と画面デザイン（.pen）
│  ├─ 09_開発標準/              # 開発標準.md（開発ガイドライン）
│  ├─ 98_レビュー記録/           # 設計情報、設計判断ログ（社内向け）
│  │  ├─ 基本設計/              # 未決定事項一覧（基本設計の分）
│  │  └─ <機能名>/              # 未決定事項一覧、レビューの要旨（この機能の分）。途中経過は作業中/に置き、完了時に消す
│  └─ 99_テンプレート/           # 各文書のテンプレート
├─ xxxxx_backend/
└─ xxxxx_frontend/
```

フォルダ名がこの構成と異なる場合は、`CLAUDE.md` に書かれた構成を優先する。どちらからも判断できないときは、推測で進めずにユーザーにパスを確認する。対象の機能や要件定義書が 1 つに決まらないときも、ユーザーに確認する。

作るものは、その機能の詳細設計（`03_詳細設計/<機能名>設計.md`）と、統合仕様（API の仕様の正本、`05_DB設計/`）への反映である。

### 社内向けのファイル

| ファイル | 内容 | 完了した後 |
|---|---|---|
| `98_レビュー記録/設計情報.md` | 設計の前提、設計を進める人の立場、委任、制約と決定済みのこと | 残す（書き足す） |
| `98_レビュー記録/設計判断ログ.md` | 人が決めた判断と、委任による選択 | 残す（書き足す） |
| `98_レビュー記録/基本設計/未決定事項一覧.md` | 基本設計の未決定事項。この機能で決めたら状態を更新する | 残す |
| `98_レビュー記録/<機能名>/未決定事項一覧.md` | この機能の詳細設計で決められなかった事項。基本設計の一覧と同じ形式（basic-design の「未決定事項一覧」）。ID は `U-<機能の略号>-01` から | 残す |
| `98_レビュー記録/<機能名>/レビューの要旨.md` | レビューのラウンドごとの件数、欠陥の ID と対応の結果、反対役が見つけた欠陥 | 残す |
| `98_レビュー記録/<機能名>/作業中/` | 欠陥の台帳、ラウンドごとのレビュー記録、修正の差分、トレーサビリティ、出典の照合、波及の点検、反対役の確認 | 完了したら消す（9-5） |

納品物（`01_`〜`09_`。`CLAUDE.md` の「納品物と社内向けの文書」を参照）から、社内向けのファイルへリンクしない。社内向けのファイルの番号（`DL-xx`、`U-xx`、`F-xx`、設計情報の No）も書かない。設計作業で AI を使った経緯（AI の推奨、AI への委任、おすすめ、選択肢の説明）は、設計情報と設計判断ログにだけ書き、納品物には書かない。製品の機能としての AI など、設計の対象として要る記述はこの限りでない。

途中で止まったとき（段階 7 の中断）は `作業中/` を消さない。`作業中/` が残っていることが、レビューが終わっていない印になる（`/project-dev:design-to-tasks` はこれを見て止まる）。

### API の方式

API の方式と仕様の正本の置き場所は、基本設計の方式設計（「技術の選定」）を読んで決める。`CLAUDE.md` やテンプレートの書き方から推定しない。

| API の方式 | このスキルの扱い |
|---|---|
| REST と OpenAPI（正本は `openapi.yaml`） | 対応している。API の定義は `04_API仕様/API設計書.md` と `openapi.yaml` に書く |
| それ以外（GraphQL など） | 対応していない。API の具体的な定義は書かず、「プラグインがこの方式に未対応」と報告する。API の定義に依存しない部分（処理の流れ、業務ルール、データ設計、画面の振る舞い）は進めてよい |
| 方式設計で決まっていない | API の定義は書かず、未決定事項として報告する |

### テンプレート

- テンプレートは `99_テンプレート/` から探す。
- 合うテンプレートがない場合は、このスキルに同梱の `assets/` のテンプレート（[詳細設計](${CLAUDE_SKILL_DIR}/assets/詳細設計テンプレート.md)、[設計情報](${CLAUDE_SKILL_DIR}/assets/設計情報テンプレート.md)、[設計判断ログ](${CLAUDE_SKILL_DIR}/assets/設計判断ログテンプレート.md)）を使う。`99_テンプレート/` に追加してチームで共有してよいか、ユーザーに確認する。統合仕様の節は `99_テンプレート/API仕様テンプレート.md`（REST と OpenAPI のとき）と `テーブル定義テンプレート.md` を雛形にする。
- テンプレートが Markdown 以外で渡された場合は、作業を始める前に、Markdown 版のテンプレートを作ってよいかユーザーに確認する。

### 出力形式

- 記法は [記法ルール](${CLAUDE_PLUGIN_ROOT}/skills/design-export/references/markdown-rules.md) の範囲に限る。
- `CLAUDE.md` のドキュメント作成ルールにも従う。

| 2. 文書の地図 | 章ごとの「決めること」と「扱わないこと（送り先）」、統合仕様で変える節を表にする | 確認する |
| 3. 初稿 | 確定できることだけで書き、統合仕様に反映する。決められないことを未決定事項一覧に入れる | — |

| 7. 修正の確認 | 新しいレビュアーが、台帳の欠陥が解消したかと、修正の影響を確かめる。欠陥が残り 0 件になるまで繰り返す | — |

## 2. 書くときの決まり

basic-design スキルの「2. 書くときの決まり」と同じ決まりに従う。要点は次のとおり。

- **粒度を守る。** [references/granularity.md](${CLAUDE_SKILL_DIR}/references/granularity.md) の「決めること」を書く。範囲の外のことは本文に書かず、未決定事項一覧に、決める工程を付けて入れる。
- **確定できることだけを、決定として書く。** 決定として書けるのは、要件定義書、基本設計、`CLAUDE.md` の設計の決まり、設計情報、設計判断ログ（委任による選択を含む）から導けることだけである。導くのに新しい前提や選択が要るなら、決定として書かずに未決定事項にする。
- **説明と、選んだ理由を分ける。** 決まった設計から説明できる性質や効果は書いてよいが、新しい選択、数値、この案件に固有の保証を足さない。人が選んだ目的や理由は、記録にない限り補わない。
- **すべての設計項目に根拠を付ける。** 要件 ID か、`[根拠: 発注者の決定（日付）]` / `[根拠: 開発チームの決定（日付）]` の形で書く。社内向けのファイルの番号は書かない。
- **決まっていない値を前提にしない。** 未決定事項がこの設計を制約するなら、制約されることを本文に書く。
- **同じことを 2 か所に書かない。** 基本設計に書いた方針は参照する。API とテーブルの全項目は統合仕様にだけ書く。
- **テンプレートの構造を変えず、「書き方のルール」を残さない。** 該当しない項目は「該当なし（理由: …）」と書く。
- **納品物に、設計作業で AI を使った経緯を書かない。**
- **版は実行中に上げない。** 既存の文書（統合仕様、基本設計の一覧）を更新した場合は、9-1 の後に 1 回だけ版を上げる。
- 新しく作った文書は、そのフォルダの `README.md` の表に 1 行追加する。

使うマーカーは次のとおり。

| マーカー | 意味 |
|---|---|
| `【未決定】` | この機能の詳細設計で決めることのうち、まだ決まっていないこと。未決定事項一覧に行がある |
| `【基本設計への差し戻し候補】` | 基本設計を変える必要があると判断したもの |
| `【影響確認】` | 既存のテーブルや API の変更で、影響を受ける他の機能 |
| `【仮定】` | 作成者が仮に置いた前提。設計情報にだけ書き、設計書の本文には書かない |

## 3. 人の答えの扱いと委任

basic-design スキルの「3. 人の答えの扱い」と「3-2. 委任」に従う。要点は次のとおり。

- 会社方針と、設計を進める人の答えは、制約として扱い、理由を聞き直さない。
- 答えが質問、異議、保留なら、決定として記録しない。まず答えるか説明する。
- 答えが要件、基本設計、`CLAUDE.md` の設計の決まり、ほかの答えと食い違ったら、確定せずに、設計の決まりで解消できるかを確かめ、解消しなければ人に聞く。それまで未決定事項として残す。
- 答えは、確定したらすぐに設計判断ログか設計情報に記録し、未決定事項一覧の状態を更新する。
- 委任は、設計情報の「委任」に記録がある範囲だけで有効である。範囲と守る条件と依存をすべて満たす選択だけを、AI が選ぶ。委任による選択は、設計判断ログに委任の記録とは別に書き、同じ承認を繰り返し求めない。

## 4. 人に聞くこと

人に聞くのは、**この機能の詳細設計を書き進めるのに答えが要り、決める人が設計を進める人である事項だけ** にする。答えがないと、この設計書の多くの節が書けない（その節を `【未決定】` にするだけでは済まない）ものが当てはまる。それ以外は聞かずに未決定事項一覧に残す。

- 1 つの事項を 1 つの質問にし、AskUserQuestion で聞く（1 回に 4 問まで。おすすめを先頭に置く）。選択肢ごとに、採ったときに何が変わるかを書く。
- 選択肢と候補案は、示す前に、決定済みの判断と基本設計と照らす。明らかに食い違う案は通常の選択肢から外し、示すなら「既存の判断を変える案」と明記する。食い違うか判断できない案は、確かめる必要がある条件を書き添える。
- 「今のまま」と「変える案」を並べるときは、今のままだと何が起きるか（前提、起きる失敗、満たせなくなる要件）を書く。書けないなら聞かない。
- 聞く数の目安は、段階 4 で 3〜5 問である。
- 発注者の回答が要るものは聞かずに、未決定事項一覧に「決める人: 発注者」として残す。

## 段階 1. 前提の整理

1. **基本設計があることを確かめる。** `02_基本設計/` に方式設計がなければ作業を止め、先に `/project-docs:basic-design` を実行するよう伝える。`98_レビュー記録/基本設計/作業中/` が残っていれば、基本設計のレビューが途中で止まっているので、作業を止めて伝える。
2. **着手を止める未決定事項を確かめる。** 基本設計とこれまでの機能の未決定事項一覧から、状態が「未決定」で、必要な関門に `詳細設計:<この機能>`（または全機能の詳細設計）が入っている行を集める。依存する行も含める。
   - そのうち、決める工程が「機能の詳細設計」でこの機能が対象のものは、この設計で決める事項である（手順 4）。止める理由にはしない。
   - それ以外（基本設計、統合仕様、インフラ・運用などで決める事項）が残っていれば、一覧にしてユーザーに見せる。各行の「未決定でも進められる範囲」を添え、その範囲だけで進めるか、先に `/project-docs:basic-design 判断 詳細設計:<機能名>` で決めるかを聞く。範囲だけで進めるなら、範囲の外の節は `【未決定】` にする。
3. **API の方式を確かめる。** 方式設計から、API の方式と仕様の正本の置き場所を読む（「0. API の方式」）。対応していない方式なら、API の定義の節は書かないことを、ここで伝える。
4. 次のものを読む。
   - 要件定義書（対象の機能の要件）
   - 基本設計の文書（`02_基本設計/`）、開発標準（`09_開発標準/開発標準.md`）
   - 基本設計の一覧（`04_API仕様/API一覧.md`、`05_DB設計/テーブル一覧.md`、`05_DB設計/ER図.md`、`02_基本設計/バッチ処理一覧.md`）と画面仕様書（`07_画面仕様書/画面仕様書.md`）
   - `98_レビュー記録/設計情報.md` と `98_レビュー記録/設計判断ログ.md`
   - 未決定事項一覧（基本設計と、これまでの機能）
   - 統合仕様の現状（API の仕様の正本、`05_DB設計/テーブル定義.md`）
   - `00_プロジェクト概要/用語集.md`
   - 画面のデザインは `07_画面仕様書/` の `.pen` から画面名や要素を読んでよいが、編集はしない
   - 既存のコードがある場合は、兄弟ディレクトリのリポジトリを読んで、現状の実装と矛盾しないかを確認してよい。ただし **コードのリポジトリには書き込まない。**
5. **この機能で決める事項を一覧にする。** 次を合わせたものが、この詳細設計で決めるか未決定事項にする事項である。
   - 要件定義書で「詳細設計で定義」「別途定義」などとされた事項（grep で洗い出す）
   - 未決定事項一覧のうち、決める工程が機能の詳細設計で、対象の機能がこの機能（または全機能で状態が「未決定」）の行

## 段階 2. 文書の地図

詳細設計テンプレートの章ごとに、この機能で決めることを表にして、ユーザーに 1 回で確認してもらう。統合仕様のどの節を追加・変更するかも含める。この表はファイルには保存しない。

| 章 | この機能で決めること | 扱わないこと（送り先） |
|---|---|---|
| 要件ごとの設計 FR-PLT-02 | 削除の処理の流れ、削除した植物の水やり記録の扱い（未決定事項一覧から） | 削除の処理を置く層（タスクの「実装の配置」） |

## 段階 3. 初稿

テンプレートに沿って、段階 2 の地図の範囲を書く。質問で作業を止めない。各処理について、少なくとも次をそろえる。決まらないものは `【未決定】` にし、未決定事項一覧に入れる。

- 起点（何をきっかけに動くか）、入力、条件、更新の対象と順序
- 業務ルールと入力チェック（型、桁、必須、形式、範囲、相関）
- 異常系（エラーの種類、利用者への表示、ログ、処理の継続か中断か）
- 同時実行、二重送信、やり直したときの扱い
- テストの観点（受け入れ条件に落とせる粒度か）

この機能で決めた事項は、テンプレートの「要件定義で詳細設計に委ねられた事項」と「基本設計からの未決定事項」の表に、決定内容と該当箇所を書く（社内の番号は書かない）。決めたら、未決定事項一覧の状態を「決定済み」にし、「決めた文書・判断」欄にこの設計書の節を書く。

詳細設計で基本設計を変える必要があると判断したら、基本設計を勝手に変えず `【基本設計への差し戻し候補】` として記録する。

### 統合仕様への反映

API とテーブルの正は、統合仕様（方式設計で決めた API の仕様の正本と、`05_DB設計/テーブル定義.md`）とする。

| 書く場所 | 内容 |
|---|---|
| 機能ごとの詳細設計書 | 設計方針、処理の流れ、業務ルール、異常系。追加・変更するテーブルや API の **一覧と変更点** を書き、全項目の定義は統合仕様へのリンクにする |
| 統合仕様 | テーブルと API の全項目の定義 |

- API の方式が REST と OpenAPI なら、`API設計書.md` と `openapi.yaml` を必ず両方同じ内容に直す。それ以外の方式なら、API の定義は書かない（「0. API の方式」）。
- 統合仕様は、この機能で追加・変更する節だけを編集する。他の機能の節は書き換えない。
- 統合仕様の API とテーブルは、基本設計の一覧と同じ ID と名前を使う。一覧にない API やテーブルを足すときは、一覧と図にも行を足す。基本設計で決めた行の意味を変えるときは、変えずに `【基本設計への差し戻し候補】` にする。
- 既存のテーブルや API を変更する場合は、影響する他の機能の設計書を grep で洗い出し、`【影響確認】` として一覧にする（他の機能の設計書は書き換えない）。

### 自己点検

- 要件 ID と、段階 1 の事項の対応表を `作業中/traceability.md` に出す。段階 1 の事項は、すべて決まっているか `【未決定】` として一覧に行があること。
- **出典の照合**：決定や値や理由の記述を集め、出典（要件 ID、基本設計の節、設計情報の行、設計判断ログの番号）と突き合わせて `作業中/出典の照合.md` に書く。出典のない決定は `【未決定】` にする。
- 本文の `【未決定】` と、この機能の未決定事項一覧の行が 1 対 1 で対応し、各行に必要な関門と進められる範囲があること。
- 本文が、決まっていない値を前提にしていないこと。本文が抽象的なまま（「適切に」「考慮する」で終わる記述）の箇所がないこと。
- 納品物に、社内の番号（`DL-`、`U-`、`F-`）、「本人」、設計作業で AI を使った経緯がないこと（grep で集め、文脈で確かめる）。
- テンプレートの見出しが残り、「書き方のルール」が残っていないこと。記法ルールの範囲を守っていること。

## 段階 4. 人に聞くこと

「4. 人に聞くこと」に従う。答えを反映し、`【未決定】` を決めた結果に置き換え、未決定事項一覧を更新する。反映した箇所に、段階 3 の自己点検をもう一度かける。

## 段階 5. レビュー（独立コンテキスト）

### 5-1. レビュアーの起動方法

| 役割 | エージェント | レビュー対象 | 出力先の名前 |
|---|---|---|---|
| 詳細設計書のレビュー | `project-docs:detailed-design-reviewer` | `03_詳細設計/<機能名>設計.md` | `<機能名>設計` |
| 横断レビュー | `project-docs:detailed-cross-reviewer` | 詳細設計書、統合仕様（API の仕様の正本、`テーブル定義.md`、`ER図.md`）、基本設計の一覧（`API一覧.md`、`テーブル一覧.md`） | 横断 |
| 反対役 | `project-docs:detailed-decision-challenger` | 段階 8 で 1 体 | — |

- Agent ツールで、上の名前のエージェントを起動する。この名前で起動できなければ、`general-purpose` を使い、`${CLAUDE_PLUGIN_ROOT}/agents/<エージェント名>.md` の本文（フロントマターを除く）をプロンプトの先頭に入れる。
- **`subagent_type: "fork"` は使わない。** 毎回、新しいコンテキストで起動する。同じレビュアーを SendMessage で使い回さない。
- 作成時の判断理由、作成者の見解、結論を誘導する言葉は渡さない。
- 詳細設計書のレビュアーと横断レビュアーは並列に起動し、全員の結果がそろってから仕分けに進む。

### 5-2. ラウンド 1 のプロンプト（雛形）

```
あなたは設計レビュアーです。指示はエージェント定義に従ってください。

モード: 初回のレビュー
作業ディレクトリ: {xxxxx_document の絶対パス}
レビュー対象: {文書のパス。横断レビューでは対象の全文書のパス}
API の方式: {方式設計で決めた方式と、仕様の正本のパス}
要件定義書: {要件定義書のパス}
設計情報: 98_レビュー記録/設計情報.md
設計判断ログ: 98_レビュー記録/設計判断ログ.md
未決定事項一覧: {基本設計と、この機能の未決定事項一覧のパス}
テンプレート: {詳細設計テンプレートのパス。横断レビューでは「なし」}
上位設計書: {基本設計の文書のパス}
用語集: {00_プロジェクト概要/用語集.md。なければ「なし」}

レビュー観点: ${CLAUDE_SKILL_DIR}/references/review-checklist.md

```

## 段階 6. 指摘の仕分けと修正

basic-design スキルの「段階 6」と同じ流れで扱う。要点は次のとおり。

- レビュアーは指摘を **欠陥・未決定事項の候補・改善の提案** に分けて返す。欠陥にだけ重大度を付け、`作業中/欠陥の台帳.md` に固定の ID（`F-01` から）で入れる。複数のレビュアーが同じ問題を指摘していたら 1 つにまとめる。
- 未決定事項の候補は未決定事項一覧に入れる。本文がそれを決定済みとして扱っていれば、根拠のない断定の欠陥として台帳にも入れる。改善の提案は、対応は任意とする。
- 誤検出は、根拠を書いて「対象外」にする。Critical を対象外にするときは人に確かめる。
- **実在する欠陥を、リスクとして受け入れたり後の工程に送ったりして、解消済みにしない。** 直すのに人の判断が要るなら、その判断を未決定事項にし、断定を外して解消する。
- 直し方が新しい判断を要するなら、作成者が決めない。書き進めるのに要るものだけを聞き、それ以外は `【未決定】` にする。
- 基本設計の方針を変えて直さない。変える必要があれば `【基本設計への差し戻し候補】` にする。
- レビュアーの指摘の文をそのまま採らない。
- **修正の後の点検**：直したら、変えた事実や判断ごとに、言い換えも含めて詳細設計書、統合仕様、基本設計の一覧、未決定事項一覧を grep し、古い記述を直す。修正の差分を `作業中/修正の差分_r{ラウンド番号}.md` に書き、段階 3 の自己点検をかける。新しいサブエージェント（`general-purpose`）を 1 体起動し、差分で変わった事実が、ほかの文書に古いまま残っていないか、食い違っていないかだけを探させる（出力先は `作業中/波及の点検_r{ラウンド番号}.md`）。見つかったものを直す。

## 段階 7. 修正の確認と終了条件

ラウンド 2 以降は、直したかどうかの確認を中心にする。レビュアーは毎回新しく起動し、5-2 のプロンプトの「モード」を「修正の確認」にして、次の 2 行を足す。

```
欠陥の台帳: 98_レビュー記録/{機能名}/作業中/欠陥の台帳.md
修正の差分: 98_レビュー記録/{機能名}/作業中/修正の差分_r{前のラウンド番号}.md
```

- 起動するのは、未解消の欠陥があるレビュアーと、修正の差分で変わった文書を見るレビュアーである。
- **完了：** 台帳のすべての欠陥（過去のラウンドと反対役のものを含み、Minor も含む）が「解消」か「対象外（根拠付き）」になり、最新の修正の確認でそれが確かめられたこと。未決定事項は、一覧で管理されていれば残ってよい。
- **進んでいないときは止めて相談する：** 解消したはずの欠陥が同じ箇所で 2 回再発した、レビュアーの基準が揺れている、直すには人の判断が要るがそれを未決定事項にできない、のどれかに当たったら、止めてユーザーに判断を仰ぐ。
- **上限：** 修正の確認は最大 4 ラウンドとする。上限に達しても欠陥が残っていたら「未収束で中断」として報告し、完了とは書かない。`作業中/` は消さない。

## 段階 8. 反対役の確認

欠陥が残り 0 件になったら、完了と判定する前に、`project-docs:detailed-decision-challenger` を新しく 1 体起動する。渡すのは、作業ディレクトリ、設計判断ログ、設計情報、未決定事項一覧、対象の文書のパスと、出力先（`作業中/反対役の確認.md`）だけにする。

- 対象は、この設計で新しく決めた影響の大きい判断（データの扱い、異常時の振る舞い、同時実行、業務ルールの境界など）と、リスクの受け入れ、先送りに限る。基本設計の決定、会社方針、制約として答えられたことは、具体的な矛盾がない限り対象にしない。
- 見つけたものは、欠陥・未決定事項・改善の提案に分けて返させる。欠陥は台帳に入れて段階 6・7 の流れで直す。
- 人に聞くのは、具体的なリスク（前提、起きる失敗、満たせなくなる要件）が示され、書き進めるのに答えが要るものだけにする。
- 反対役の確認は 1 回だけ行う。問題がなければ「問題なし」で終えてよい。

## 段階 9. 仕上げ

### 9-1. 日本語の推敲

レビューが終わった詳細設計書を、Skill ツールで `natural-japanese` スキルを呼び出して推敲する。統合仕様（`openapi.yaml` など）とレビュー記録は推敲しない。basic-design スキルの「9-1」と同じ制約（見出し・表の構造・ID・リンク・マーカー・人が答えた文言を変えない、記法ルールを守る、である調）を伝える。マーカーは `【未決定】` `【基本設計への差し戻し候補】` `【影響確認】` を残す。natural-japanese のスクリプトを Bash から実行するときは、`PYTHONIOENCODING=utf-8` を付ける。推敲前後で、ID の出現回数、見出しとリンクの一覧、表の数と行数・列数が一致することを確かめる。

### 9-2. 未決定事項一覧の更新

- この機能で決めた基本設計の未決定事項は、基本設計の一覧の状態を「決定済み」にし、「決めた文書・判断」を書く。
- この機能で決められなかった事項は、`98_レビュー記録/<機能名>/未決定事項一覧.md` に、必要な関門（`実装:<機能名>` を含む）、未決定でも進められる範囲、依存、決める人を書く。決める人が発注者のものは、確認をお願いする事項として報告に挙げる。

### 9-3. 改善を戻す

レビューで繰り返し出た種類の欠陥があれば、`references/review-checklist.md` の「プロジェクト固有」に足す観点か、テンプレートの記入ルールに足す内容の案として、報告に書く。

### 9-4. レビューの要旨

`98_レビュー記録/<機能名>/レビューの要旨.md` に、ラウンドごとの件数、欠陥の台帳の要旨（ID、重大度、箇所、問題の要旨、対応の結果、対象外の根拠、再指摘の理由）、反対役が初めて見つけた欠陥、終わり方を書く。`作業中/` へのリンクは書かない。

### 9-5. 作業中フォルダの片付け

完了したときだけ、`98_レビュー記録/<機能名>/作業中/` をフォルダごと消す。消す前に、残すファイルと納品物に `作業中/` への参照がないことを grep で確かめる。未収束で中断したときは消さない。

### 9-6. コミット

コミットは `xxxxx_document` リポジトリで行い、コードのリポジトリの変更と混ぜない。コミットや PR の作成は、ユーザーに指示されたときだけ行う。指示されたら、`develop` から作業用のブランチ（例: `feature/<担当者>/<機能名>-design`）を切って作業し、PR の向き先は `develop` にする。

### 9-7. 報告

```
文書品質レビュー：完了（または「未収束で中断」）。残っている欠陥 Critical 0／Major 0／Minor 0
実装タスクへの分解（design-to-tasks）：着手できる（または「判断待ち n 件」と事項、進められる範囲）
プラグインの対応：API の方式「…」は、API の定義と API のタスク・照合が未対応（対応している方式なら書かない）
未決定事項：n 件（決める工程ごと、決める人ごと）
```

そのうえで、次を箇条書きで短く書く。

1. 作成・更新した文書（統合仕様で変えた節と、基本設計の一覧に足した行を含む）と、`作業中/` を消したこと
2. 人に聞いた事項の数と、委任の範囲で選んだこと
3. レビューのラウンド数と、ラウンドごとの欠陥の件数の推移
4. 人が決めた判断（設計判断ログの番号と結論）と、反対役の確認の結果
5. この機能で決めた基本設計の未決定事項と、この機能で残った未決定事項
6. `【影響確認】` と `【基本設計への差し戻し候補】` の一覧
7. 改善を戻す案（9-3）

次の工程として、実装タスクへの分解は `/project-dev:design-to-tasks <機能名>` で行うことを添える。Word や Excel での納品が必要な場合は、`/project-docs:design-export` で変換できることを最後に 1 行で添える。
