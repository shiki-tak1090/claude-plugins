# 詳細設計スキル

基本設計の方針を前提に、機能ごとの詳細設計書を Markdown で作り、統合仕様に反映する。独立したレビュアーのレビューと人の判断を経て、自然な日本語に整えた最終版を出す。設計書の正本は Markdown とし、Word や Excel への変換は `design-export` スキルで行う。

詳細設計は、実装とテストができるところまで具体化する。基本設計の方針を説明し直したり、変えたりしない。

このスキルで AI がすることは、整理、案出し、執筆、レビューである。**前提、制約、方式の採用、リスクの受け入れは人が決める。** AI が決めたことを、設計書に決定事項として書かない。

## 0. 前提とディレクトリ構成

このスキルは、ドキュメントのリポジトリ `xxxxx_document` の直下で起動する前提で書いている。このリポジトリは Obsidian の保管庫として閲覧する。コードのリポジトリは兄弟ディレクトリにある。

```
xxxxx/                          # ただのフォルダ（Git 管理しない）
├─ xxxxx_document/              # ← このスキルを起動するリポジトリ
│  ├─ CLAUDE.md                 # ドキュメント作成ルール（このスキルより優先する）
│  ├─ 00_プロジェクト概要/        # 用語集.md（用語の統一に使う）
│  ├─ 01_要件定義/              # 要件定義書（入力）
│  ├─ 02_基本設計/              # 基本設計の文書（入力。変えない）
│  ├─ 03_詳細設計/              # 機能ごとの詳細設計（このスキルで作る）
│  ├─ 04_API仕様/               # API一覧.md（基本設計）と、API設計書.md と openapi.yaml（全機能の統合仕様）
│  ├─ 05_DB設計/                # テーブル一覧.md と ER図.md（基本設計）と、テーブル定義.md（全機能の統合仕様）
│  ├─ 07_画面仕様書/            # 画面仕様書.md（基本設計）と画面デザイン（.pen）
│  ├─ 09_開発標準/              # 開発標準.md（開発ガイドライン）
│  ├─ 98_レビュー記録/           # 設計情報、設計判断ログ、申し送り、確認事項一覧（社内向け）。レビューの途中経過は作業中/に置き、完了時に消す
│  └─ 99_テンプレート/           # 各文書のテンプレート
├─ xxxxx_backend/
└─ xxxxx_frontend/
```

フォルダ名がこの構成と異なる場合は、`CLAUDE.md` に書かれた構成を優先する。どちらからも判断できないときは、推測で進めずにユーザーにパスを確認する。対象の機能や要件定義書が 1 つに決まらないときも、ユーザーに確認する。

作るものは、その機能の詳細設計（`03_詳細設計/<機能名>設計.md`）と、統合仕様（`04_API仕様/`、`05_DB設計/`）への反映である。

### 社内向けの作業ファイル

設計の前提と判断の理由は、納品物とは別のファイルに残す。基本設計で作ったものに書き足す。

| ファイル | 内容 | テンプレート |
|---|---|---|
| `98_レビュー記録/設計情報.md` | 目的、利用者と運用者、対象と対象外、制約と決定済みのこと、失敗したときの扱い、判断の優先順位 | `99_テンプレート/設計情報テンプレート.md` |
| `98_レビュー記録/設計判断ログ.md` | 人が決めた判断の結論、選択肢、理由、受け入れるリスク、前提、再検討の条件 | `99_テンプレート/設計判断ログテンプレート.md` |
| `98_レビュー記録/基本設計/基本設計からの申し送り.md` | 基本設計から送られた事項。この機能で決めたら「決めた文書」を記入する | — |

納品物（`01_`〜`09_`。`CLAUDE.md` の「納品物と社内向けの文書」を参照）から、これらの社内向けのファイルへリンクしない。社内向けのファイルの番号（設計判断ログの `DL-xx`、申し送りの `HS-xx`、設計情報の「制約と決定済みのこと」の No、レビュー記録の指摘の No）も書かない。顧客はこれらのファイルを読めないため、番号を見ても中身が分からない。納品物には決めた結果と、顧客に説明する理由だけを書く。

### レビューの途中経過（作業中フォルダ）

レビューの途中経過は、`98_レビュー記録/<機能名>/作業中/` に置き、スキルが完了したら消す（9-4）。完了した後に残すのは、後の工程が読むファイルだけにする。

| 区分 | ファイル |
|---|---|
| 完了した後も残す | `98_レビュー記録/設計情報.md`、`98_レビュー記録/設計判断ログ.md`、`98_レビュー記録/基本設計/基本設計からの申し送り.md`、`98_レビュー記録/<機能名>/確認事項一覧.md` |
| `作業中/` に置き、完了したら消す | ラウンドごとのレビュー記録（`*_review_r<ラウンド番号>.md`）、トレーサビリティ（`traceability.md`）、反対役の確認（`反対役の確認.md`） |

- 残すファイルから、`作業中/` のファイルへリンクしない。ファイル名や指摘の No も書かない。消えた後に参照が切れるため。設計判断ログの「背景」には、レビューの指摘から来たことと、指摘の要旨を書く。
- 途中で止まったとき（段階 7 の「止まって相談する条件」や、3 ラウンド後の打ち切り）は `作業中/` を消さない。`作業中/` が残っていることが、レビューが終わっていない印になる（`/project-dev:design-to-tasks` はこれを見て止まる）。

### テンプレート

- テンプレートは `99_テンプレート/` から探す。
- 合うテンプレートがない場合は、このスキルに同梱の `assets/` のテンプレート（[詳細設計](${CLAUDE_SKILL_DIR}/assets/詳細設計テンプレート.md)、[設計情報](${CLAUDE_SKILL_DIR}/assets/設計情報テンプレート.md)、[設計判断ログ](${CLAUDE_SKILL_DIR}/assets/設計判断ログテンプレート.md)）を使う。`99_テンプレート/` に追加してチームで共有してよいか、ユーザーに確認する。統合仕様の節は `99_テンプレート/API仕様テンプレート.md` と `テーブル定義テンプレート.md` を雛形にする。勝手に章立てを決めて書き始めない。
- テンプレートが Markdown 以外（Excel や Word）で渡された場合は、作業を始める前に、Markdown 版のテンプレートを作ってよいかユーザーに確認する。

### 出力形式

- 記法は [記法ルール](${CLAUDE_PLUGIN_ROOT}/skills/design-export/references/markdown-rules.md) の範囲に限る。このルールは `design-export` スキルでの変換と照合の前提になっているため、必ず守る。
- `CLAUDE.md` のドキュメント作成ルール（Mermaid の使用、`[[]]` リンクの活用など）にも従う。

## 1. 進め方

次の段階で進める。設計書全体を一度に書かない。一度に書くと、AI は分からないことを一般論で埋め、仮定が決定事項のように見えてしまうため。

| 段階 | すること | 人がすること |
|---|---|---|
| 1. 前提の整理 | 入力を読み、この機能で閉じる事項を一覧にする。決まっていない前提を質問する | 質問に答える |
| 2. 文書の地図 | 章ごとの「決めること」と「扱わないこと（送り先）」、統合仕様で変える節を表にする | 確認する |
| 3. 判断事項 | 本文の前に、人が決めることを選択肢付きで一覧にする | 決める |
| 4. 作成 | 決まったことと地図の範囲だけで書き、統合仕様に反映する | — |
| 5. レビュー | 新しいレビュアーで、詳細設計書と、統合仕様をまたいでレビューする | — |
| 6. 指摘の仕分け | 指摘ごとに扱いの案を出す | 確認・受け入れ・将来に送るものを決める |
| 7. 再レビュー | 「今すぐ直す」を直し、新しいレビュアーで再レビューする | — |
| 8. 反対役の確認 | 人の判断に見落としがないかを、反対の立場から確かめる | 必要なら判断し直す |
| 9. 仕上げ | 推敲、確認事項一覧、作業中フォルダの片付け、報告 | — |

段階 1〜3 の人の確認は、それぞれ 1 回にまとめて行う（章ごとに確認を求めない）。

## 2. 書くときの決まり

- **粒度を守る。** [references/granularity.md](${CLAUDE_SKILL_DIR}/references/granularity.md) の「決めること」を書く。範囲の外のことは本文に書かず、送り先を未決事項か報告に書く。
- **テンプレートの構造を変えない。** 章立て・見出し・表の列は削除も並べ替えもしない。該当しない項目は削らずに「該当なし（理由: …）」と書く。
- **テンプレート内の記入指示や記入例（`{{…}}` や `（…を記述）`）は、本文で置き換える。** 指示文を残したままにしない。
- **すべての設計項目に根拠を付ける。** 各項目に対応する要件 ID を記載する（テンプレートにトレーサビリティ欄があればそこへ、なければ項目末尾に `[根拠: FR-FAV-01]` の形式で）。要件 ID がなく、人が決めたことが根拠なら、`[根拠: 発注者の決定（2026-05-01）]` のように、誰がいつ決めたかを書く。社内向けのファイルの番号（`DL-xx` など）は書かない。
- **要件にないことを作らない。AI が決めない。** 要件定義書、基本設計、設計情報、判断ログから決められないことは推測で埋めず、段階 3 の判断事項にして人に決めてもらう。`【要確認】` は、その場にいない関係者（顧客、運用部門など）の回答が要るものにだけ使い、確認先と理由を添える。スキルを実行している人が決められることは、`【要確認】` にせずに判断事項として聞く。
- **用語・ID・名称を統一する。** 用語集、基本設計の一覧（画面 ID、API ID、テーブル名）、統合仕様の表記に合わせる。
- **同じことを 2 か所に書かない。** 基本設計に書いた方針を詳細設計で書き写さず、参照する。API とテーブルの全項目は統合仕様にだけ書く。片方だけ直されてずれていくため。
- 文書の先頭（作成日・版）と末尾の変更履歴は、記法ルールの形にそろえる。既存の文書を更新する場合は、版を上げて変更履歴に追記する。納品物の変更履歴には、文書の内容がどう変わったかを書き、社内の作業の名前（レビューのラウンド、反対役の確認など）や社内向けのファイルの番号は書かない。
- 新しく作った文書は、そのフォルダの `README.md` の「ドキュメント一覧」の表に 1 行追加する。

使うマーカーは次のとおり。

| マーカー | 意味 |
|---|---|
| `【要確認】` | 人（顧客や関係者を含む）の回答を待っている |
| `【仮定】` | 作成者が仮に置いた前提。確かめる時期を添える。設計情報にだけ書き、設計書の本文には書かない |
| `【基本設計への差し戻し候補】` | 基本設計を変える必要があると判断したもの |
| `【影響確認】` | 既存のテーブルや API の変更で、影響を受ける他の機能 |

人が決めた判断は、設計書の本文に決めた結果を書き、理由は設計判断ログに書く。AI が決めたことを示すマーカー（`【設計判断】` など）は使わない。

## 3. 判断事項の扱い

段階 3 では、本文を書く前に、要件定義書、基本設計、設計情報から 1 通りに決まらないことを一覧にする。

| 項目 | 内容 |
|---|---|
| 判断事項 | 何を決めるか |
| 選択肢 | 2〜4 個 |
| おすすめ | どれか 1 つと、その理由（設計情報の「判断の優先順位」と結び付ける） |
| 採らなかった場合の影響 | おすすめ以外を選んだときに何が変わるか |
| 関係者 | 本人だけで決められるか、顧客や運用部門などに確認が要るか |

- 一覧はまとめて 1 回で示す。選択肢から選べるものは AskUserQuestion で聞く（1 回に 4 問まで。おすすめを先頭に置く）。選択肢に収まらないものは、チャットで番号を付けて聞く。
- その場にいない関係者の確認が要るものは、本人が決めずに `【要確認】` として確認事項一覧に回してよい。スキルを実行している人に確認先を向けた `【要確認】`（「確認先: 本人」）は作らない。その場で聞く。
- 決まったら、設計判断ログに記録する。判断した人が述べていない理由を、推測で書き足さない。

詳細設計で人に返すことの例は次のとおり。

- 段階 1-3 の事項のうち、要件定義書と基本設計から 1 通りに決まらないもの（例: 同じ日に 2 回目の水やりを記録したときの扱い）
- 業務ルールの境界（上限値、日付の境界、0 件のとき）で、要件から決まらないもの
- 利用者に見える振る舞いの選択（エラー時に入力を残すか、など）

## 段階 1. 前提の整理

1. **基本設計があることを確かめる。** `02_基本設計/` に方式設計がなければ作業を止め、先に `/project-docs:basic-design` を実行するよう伝える。`98_レビュー記録/基本設計/作業中/` が残っていれば、基本設計のレビューが途中で止まっているので、作業を止めて伝える。
2. 次のものを読む。
   - 要件定義書（対象の機能の要件）
   - 基本設計の文書（`02_基本設計/`）と開発標準（`09_開発標準/開発標準.md`）
   - 基本設計の一覧（`04_API仕様/API一覧.md`、`05_DB設計/テーブル一覧.md`、`05_DB設計/ER図.md`、`02_基本設計/バッチ処理一覧.md`）と画面仕様書（`07_画面仕様書/画面仕様書.md`）
   - `98_レビュー記録/設計情報.md` と `98_レビュー記録/設計判断ログ.md`
   - `98_レビュー記録/基本設計/基本設計からの申し送り.md` のうち、送り先が機能の詳細設計で、対象がこの機能（または全機能で「決めた文書」が空）の行。送り先が統合仕様の行のうち、この機能の API やテーブルに関係するもの
   - 統合仕様（`04_API仕様/API設計書.md`、`openapi.yaml`、`05_DB設計/テーブル定義.md`）の現状
   - `00_プロジェクト概要/用語集.md`
   - 画面のデザインは `07_画面仕様書/` の `.pen`（JSON 形式）から画面名や要素を読んでよいが、編集はしない
   - 既存のコードがある場合は、兄弟ディレクトリのリポジトリ（`../xxxxx_backend` など）を読んで、現状の実装と矛盾しないかを確認してよい。ただし **コードのリポジトリには書き込まない。**
3. **この機能で閉じる事項を一覧にする。** 次の 2 つを合わせたものが、この詳細設計で「決めるか `【要確認】` にする」事項になる。
   - 要件定義書で「詳細設計で定義」「別途定義」などとされた事項（grep で洗い出す）
   - 申し送りのうち、上で読んだ行
4. 設計情報と判断ログで決まっていない前提があれば、質問の一覧にして 1 回で聞く。答えは設計情報に書き足す。

## 段階 2. 文書の地図

詳細設計テンプレートの章ごとに、この機能で決めることを表にして、ユーザーに 1 回で確認してもらう。統合仕様のどの節を追加・変更するかも含める。

| 章 | この機能で決めること | 扱わないこと（送り先） |
|---|---|---|
| 要件ごとの設計 FR-PLT-02 | 削除の処理の流れ、削除した植物の水やり記録の扱い（申し送りから） | 削除の処理を置く層（タスクの「実装の配置」） |

この表は確認のためのもので、ファイルには保存しない。

## 段階 3. 判断事項

「3. 判断事項の扱い」に従う。

## 段階 4. 作成

テンプレートに沿って、段階 2 の地図の範囲を書く。各処理について、少なくとも次をそろえる。

- 起点（何をきっかけに動くか）、入力、条件、更新の対象と順序
- 業務ルールと入力チェック（型、桁、必須、形式、範囲、相関）
- 異常系（エラーコード、利用者への表示、ログ、処理の継続か中断か）
- 同時実行、二重送信、やり直したときの扱い
- テストの観点（受け入れ条件に落とせる粒度か）

段階 1-3 の事項は、テンプレートの「要件定義で詳細設計に委ねられた事項」と「基本設計からの申し送り」の表に、決定内容と該当箇所を書く。決めたら、申し送りのファイルの「決めた文書」欄にこの設計書（統合仕様で決めたものは、その文書と節）を書く。

詳細設計で基本設計を変える必要があると判断したら、基本設計を勝手に変えず `【基本設計への差し戻し候補】` として記録する。

### 統合仕様への反映

API とテーブルの正は、統合仕様（`04_API仕様/API設計書.md`、`04_API仕様/openapi.yaml`、`05_DB設計/テーブル定義.md`）とする。機能ごとの詳細設計書と統合仕様に同じ定義を二重に書くと、片方だけ直されてずれていくため、次のように分担する。

| 書く場所 | 内容 |
|---|---|
| 機能ごとの詳細設計書 | 設計方針、処理の流れ、業務ルール、異常系。追加・変更するテーブルやエンドポイントの **一覧と変更点** を書き、全項目の定義は統合仕様へのリンク（`[[05_DB設計/テーブル定義#ranks]]` など）にする |
| 統合仕様 | テーブルとエンドポイントの全項目の定義 |

- 統合仕様は、この機能で追加・変更する節だけを編集する。他の機能の節は書き換えない。
- 統合仕様の API とテーブルは、基本設計の一覧と同じ ID と名前を使う。
- 基本設計の API一覧、テーブル一覧、ER図にない API やテーブルを足すときは、一覧と図にも行を足し、版を上げて変更履歴に書く。報告にも足した行を挙げる。基本設計で決めた行の意味（API の役割、テーブルが持つ情報、関係の多重度）を変えるときは、変えずに `【基本設計への差し戻し候補】` にする。
- `API設計書.md` と `openapi.yaml` は必ず両方を同じ内容に直す。片方だけの変更は禁止する。
- 既存のテーブルやエンドポイントを変更する場合は、影響する他の機能の設計書を grep で洗い出し、`【影響確認】` として一覧にする（他の機能の設計書は書き換えない）。

### 自己点検

- 要件 ID と、段階 1-3 の事項の対応表を `98_レビュー記録/<機能名>/作業中/traceability.md` に出力する（完了時に消す）。段階 1-3 の事項は、すべて決まっているか `【要確認】` になっていること。
- 本文が抽象的なままの箇所（「適切に」「考慮する」で終わる記述）がないこと。
- テンプレートの見出しがすべて残っていること。
- 納品物に、社内向けのファイルの番号（`DL-`、`HS-`、設計情報の No）がないこと（grep で確かめる）。
- 記法ルールの範囲外の記法を使っていないこと。

## 段階 5. レビュー（独立コンテキスト）

### 5-1. レビュアーの起動方法

レビューは **作成者（このセッション）とは文脈を共有しないサブエージェント** に任せる。

| 役割 | エージェント | レビュー対象 | 出力先の名前 |
|---|---|---|---|
| 詳細設計書のレビュー | `project-docs:detailed-design-reviewer` | `03_詳細設計/<機能名>設計.md` | `<機能名>設計` |
| 横断レビュー | `project-docs:detailed-cross-reviewer` | 詳細設計書と統合仕様の各ファイル（`API設計書.md`、`openapi.yaml`、`テーブル定義.md`、`ER図.md`）と、基本設計の一覧（`API一覧.md`、`テーブル一覧.md`） | 横断 |
| 反対役 | `project-docs:detailed-decision-challenger` | 人が決めた判断（採用、リスク受容、将来対応）に見落としがないか | 段階 8 で 1 体 |

- 詳細設計書のレビュアーと横断レビュアーは、ラウンドごとに 1 つのメッセージで並列に起動する。全員の結果がそろってから仕分けに進む（読んでいる途中で文書を書き換えない）。
- Agent ツールで、上の名前のエージェントを起動する。この名前で起動できなければ、`general-purpose` を使い、`${CLAUDE_PLUGIN_ROOT}/agents/<エージェント名>.md` の本文（フロントマターを除く）をプロンプトの先頭に入れる。どちらの場合も、`fork` ではなく新しいコンテキストで起動する。
- **`subagent_type: "fork"` は使わない。** fork は作成時の会話や判断を引き継ぐため、作成者の思い込みまでレビュアーに移ってしまう。
- レビュアーに渡すのは **ファイルパスとレビュー範囲だけ** にする。作成時の判断理由、作成者の見解、結論を誘導する言葉、前のラウンドの指摘と対応は渡さない。設計情報と設計判断ログは、ファイルパスとして渡してよい。
- 同じレビュアーを SendMessage で使い回さない。**ラウンドごとに新しいエージェントを起動する。**

### 5-2. レビュアーへのプロンプト（雛形）

以下の `{}` を埋めて渡す。これ以外の情報は足さない。

```
あなたは設計レビュアーです。指示はエージェント定義に従ってください。

作業ディレクトリ: {xxxxx_document の絶対パス}
レビュー対象: {文書のパス。横断レビューでは対象の全文書のパス}
要件定義書: {要件定義書のパス（複数可）}
設計情報: 98_レビュー記録/設計情報.md
設計判断ログ: 98_レビュー記録/設計判断ログ.md
テンプレート: {詳細設計テンプレートのパス。横断レビューでは「なし」}
上位設計書: {基本設計の文書のパスと、申し送りのパス}
用語集: {00_プロジェクト概要/用語集.md。なければ「なし」}
粒度の決まり: ${CLAUDE_SKILL_DIR}/references/granularity.md
レビュー観点: ${CLAUDE_SKILL_DIR}/references/review-checklist.md
指摘の出力先: 98_レビュー記録/{機能名}/作業中/{出力先の名前}_review_r{ラウンド番号}.md
```

## 段階 6. 指摘の仕分け

レビューは指摘を全部消すためのものではない。指摘されたリスクを、どう扱うかを決めるためのものである。指摘ごとに次のどれかに仕分け、レビュー記録の「対応」欄に書く。

| 仕分け | 条件 | 決める人 | 書くこと |
|---|---|---|---|
| 今すぐ直す | 設計が成り立たない、要件を満たさない、後から直すと影響が大きい | 作成者が案を出し、まとめて報告する | 直した箇所 |
| 関係者に確認 | 業務、費用、運用体制などの判断が要り、本人や作成者だけでは決められない | 人 | `【要確認】` にした箇所と確認先 |
| リスクとして受け入れる | 問題はあるが、発生しやすさ、影響、代わりの手段から、今回は対応しない | 人 | 受け入れる理由（設計判断ログの番号） |
| 将来に送る | 今は要らないが、条件が変われば必要になる | 人 | 何が起きたら見直すか（設計判断ログの番号） |
| 不採用 | 指摘が誤り、要件の範囲外、または詳細設計の範囲の外 | 作成者。Critical は人 | 根拠（要件 ID、テンプレートの規定、粒度の決まりなど）。範囲の外なら送り先（統合仕様、インフラ・運用、開発標準、タスク、実装）。「問題ないと考える」だけの理由は認めない |

- 仕分けは、まず作成者が全件の案を作る。各指摘について、想定される問題、影響、起きやすさ、今直す場合と後で直す場合の違い、仕分けの案、その理由を短く書く。
- 「関係者に確認」「リスクとして受け入れる」「将来に送る」と、Critical の「不採用」は、人に決めてもらう。案を一覧にして 1 回で示す。
- **指摘を直すときに、基本設計の方針を変えない。** 変える必要があれば `【基本設計への差し戻し候補】` にする。
- 指摘に反論したくなったときほど、要件定義書と基本設計を読み直してから判断する。作成者は自分の書いたものを正しいと思い込みやすい。
- Minor は、作成者の判断で直すか、不採用にしてよい。

## 段階 7. 再レビューと終了条件

- 「今すぐ直す」を直したら、新しいレビュアーで再レビューする（段階 5 と同じ構成）。
- **終わる条件：** 最新のラウンドで、粒度の範囲内の Critical と Major のうち「今すぐ直す」に仕分けたものが 0 件になったこと。それ以外の仕分け（確認、受け入れ、将来、不採用）は、人の判断が記録されていれば残ってよい。
- **止まって相談する条件：** 前のラウンドより「今すぐ直す」の件数が減っていないとき。3 ラウンドを待たずに止め、残件と、減らない理由を見せて、ユーザーに判断を仰ぐ。
- 最大 3 ラウンドで打ち切る。3 ラウンド後も「今すぐ直す」が残る場合は、残件を一覧にしてユーザーに判断を仰ぎ、次の段階には進まない。
- 再レビューのレビュアーにも、前のラウンドの指摘内容や対応内容は渡さない。前のラウンドの指摘が解消されたかどうかは、作成者が前回のレビュー記録と照らし合わせて自分で確認する。

## 段階 8. 反対役の確認

レビューが終わったら、`project-docs:detailed-decision-challenger` を新しく 1 体起動し、人が決めた判断に見落としがないかを確かめる。渡すのは、作業ディレクトリ、設計判断ログ、設計情報、対象の文書のパスと、出力先（`98_レビュー記録/<機能名>/作業中/反対役の確認.md`）だけにする。対象は、今回の設計で記録・変更した判断に限る。

- 結果の指摘は、関係する判断ごとにユーザーに見せる。判断を変えるかどうかは人が決める。変えたら、設計判断ログと設計書を直す。
- 反対役の確認は 1 回だけ行う。判断を変えて設計書を直した場合は、詳細設計書のレビュアーと横断レビュアーを新しく起動し、1 回だけレビューする。
- このレビューで出た「今すぐ直す」は直す。直したあとは再レビューしない代わりに、直した指摘の一覧を報告に入れ、人が確かめられるようにする。人の判断が要る指摘が出たら、判断事項として聞く。

## 段階 9. 仕上げ

### 9-1. 日本語の推敲

レビューが終わった詳細設計書を、Skill ツールで `natural-japanese` スキルを呼び出して推敲する。統合仕様（`openapi.yaml` など）とレビュー記録は推敲しない。呼び出すときは、次の制約を必ず伝える。

- 見出し、章番号、表の構造（行・列）、テンプレートの項目名は変えない
- 要件 ID、画面 ID、API ID、テーブル名、カラム名、API パス、コード、数値、単位は一字も変えない
- `[[リンク]]` の中身は変えない
- `【要確認】` `【基本設計への差し戻し候補】` `【影響確認】` のマーカーは残す
- 推敲は文体と読みやすさに限る。設計内容の追加・削除・解釈の変更はしない
- 設計書の文体は「である調」で統一する（テンプレートや `CLAUDE.md` に指定があればそれに従う）
- Markdown の記法は記法ルールの範囲を守る

推敲後、次の機械的な確認を行う。

- 推敲前後で、要件 ID・各種 ID の出現回数が一致すること（grep で数えて比較する）
- 見出しの一覧と `[[リンク]]` の一覧が一致すること
- 表の数と、各表の行数・列数が一致すること
- 一致しなければ、推敲で消えた・変わった箇所を元に戻す
- 納品物（`01_`〜`09_`）に、社内向けのファイルの番号（`DL-`、`HS-`）や名前（設計情報、設計判断ログ、レビュー記録、反対役）が出てこないこと（grep で確かめる）

### 9-2. 確認事項一覧

設計書に残った `【要確認】` を、`98_レビュー記録/<機能名>/確認事項一覧.md` に表で書き出す。顧客や社内の関係者にそのまま渡して回答をもらえる形にする。

| No | 確認事項 | 背景（なぜ決められないか） | 設計書の該当箇所 | 根拠の要件 | 確認先 | 回答 |
|---|---|---|---|---|---|---|

回答をもらったら、設計書を直して版を上げ、この表の「回答」欄を埋め、設計判断ログに記録する。

### 9-3. 改善を戻す

レビューで繰り返し出た種類の指摘（ラウンドをまたいで 2 回以上出たもの）があれば、`references/review-checklist.md` の「プロジェクト固有」に足す観点か、テンプレートの記入ルールに足す内容の案として、報告に書く。追加するかどうかはユーザーが決める。

### 9-4. 作業中フォルダの片付け

9-1〜9-3 を終え、9-6 の報告に使う件数（ラウンドごとの仕分けの件数、反対役の確認の結果、反対役の確認の後のレビューで直した指摘）を控えたら、`98_レビュー記録/<機能名>/作業中/` をフォルダごと消す。

- 消す前に、残すファイル（設計情報、設計判断ログ、申し送り、確認事項一覧）と納品物に `作業中/` のファイルへの参照が残っていないことを grep で確かめる。残っていれば、指摘の要旨に書き換えてから消す。
- 消すのは、段階 7 の終わる条件を満たし、段階 8 と 9-1〜9-3 を終えたときだけにする。途中で止まったときは消さない。
- `作業中/` の中にコミット済みのファイルがあれば、消したことを報告に書く（`git status` に削除として出るため）。

### 9-5. コミット

コミットは `xxxxx_document` リポジトリで行い、コードのリポジトリの変更と混ぜない。コミットや PR の作成は、ユーザーに指示されたときだけ行う。指示されたら、`develop` から作業用のブランチ（例: `feature/<担当者>/<機能名>-design`）を切って作業し、PR の向き先は `develop` にする。ブランチ運用が `CLAUDE.md` に書かれていれば、それに従う。

### 9-6. 報告

ユーザーには次の内容を報告する。結論から書き、各項目は箇条書きで短くまとめる。

1. 作成・更新した文書の一覧（統合仕様で変えた節と、基本設計の一覧に足した行を含む）と、`作業中/` を消したこと
2. レビューのラウンド数と、仕分けごとの件数の推移。反対役の確認の後のレビューで直した指摘の一覧
3. 人が決めた判断（設計判断ログの番号と結論）と、反対役の確認の結果
4. `【要確認】` の件数と、確認事項一覧のパス
5. 申し送りと委ねられた事項を、すべて閉じたか
6. `【影響確認】` と `【基本設計への差し戻し候補】` の一覧
7. 改善を戻す案（9-3）

次の工程として、実装タスクへの分解は `/project-dev:design-to-tasks <機能名>` で行うことを添える。Word や Excel での納品が必要な場合は、`/project-docs:design-export` で変換できることを最後に 1 行で添える。
