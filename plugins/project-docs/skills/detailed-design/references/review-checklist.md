# 詳細設計のレビュー観点

レビュアーは、「共通」と「詳細設計」の観点をすべて確認する。横断レビュアーは、エージェント定義の「見るテーマ」に加えて「統合仕様との整合性」を確認する。プロジェクト固有の観点は末尾の「プロジェクト固有」に追記して使う。

各観点で見つけたものは、エージェント定義の「指摘の種類」で、欠陥・未決定事項の候補・改善の提案に分ける。観点が「決まっているか」と問うものは、決定として書かれているか、`【未決定】` として未決定事項一覧に行があれば満たしている。どちらでもない（何も書かれていない）か、出典なしに決定として書かれていれば欠陥である。

どの観点も、粒度の決まり（`granularity.md`）の範囲で確認する。

## 共通

- [ ] **納品物と社内向けの分離**: `01_`〜`08_` の設計書に、開発チームの内部の内容（開発手法の名前、層の細かな決まり、実装の配置）が混ざっていないか。これらは `09_開発標準/`（開発ガイドライン）やタスクファイルに書く。`01_`〜`09_` の納品物に、社内向けのファイル（設計情報、設計判断ログ、未決定事項一覧、レビュー記録）へのリンクや番号がないか

- [ ] **粒度**: 「適切に」「考慮する」で終わり、実装・テストできない記述がないか（粗すぎないか）。基本設計で決めた方針を説明し直したり変えたりしていないか
- [ ] **前提と判断**: 設計情報の制約・決定済みのことと、設計判断ログの結論に従っているか。設計情報にない前提を、設計書が一般論で補っていないか
- [ ] **網羅性**: 要件定義書の要件で、この設計書が扱うべきものがすべて扱われているか。対象外にした要件に理由が書かれているか
- [ ] **根拠**: 各設計項目に要件 ID などの根拠があるか。要件にない機能・仕様が根拠なく追加されていないか
- [ ] **テンプレート準拠**: 必須の章・項目がすべて埋まっているか。記入指示や記入例が残っていないか
- [ ] **一意性**: 実装者が 2 通り以上に解釈できる記述がないか（「適切に」「必要に応じて」「など」「等」で範囲がぼかされていないか）
- [ ] **矛盾**: 同じ設計書の中で、数値・名称・振る舞いが食い違っていないか
- [ ] **用語**: 同じものを違う名前で呼んでいないか。`00_プロジェクト概要/用語集.md` に従っているか
- [ ] **版管理**: 先頭の作成日・版と、末尾の変更履歴があるか。detailed-design の実行中は版を上げない決まりなので、版が上がっていないことは指摘しない
- [ ] **出典**: 決定、値、選んだ理由に、出典（要件定義書、基本設計、設計情報、設計判断ログ）があるか。決まった設計から説明できる性質は書いてよいが、新しい選択、数値、案件に固有の保証を足していないか
- [ ] **AI を使った経緯**: 納品物に、設計作業で AI を使った経緯が書かれていないか（製品の機能としての AI は対象外）
- [ ] **未決定事項**: 本文の `【未決定】` に、何が決まっていないかが書かれ、未決定事項一覧に対応する行（決める工程、必要な関門）があるか。未決定のことが、決まったかのように書かれていないか。本文が、決まっていない値を前提にしていないか。要件や人の回答で決まっていることが `【未決定】` になっていないか

## 詳細設計

- [ ] **委ねられた事項と未決定事項**: 要件定義書で委ねられた事項と、基本設計の未決定事項一覧のうち、決める工程が機能の詳細設計でこの機能が対象のものが、すべて決まっているか、`【未決定】` として一覧に行があるか（要件定義書と未決定事項一覧を自分で数える）
- [ ] **上位設計との整合**: 基本設計で定義した機能・画面・データ・ID がすべて詳細化されているか。基本設計と矛盾していないか
- [ ] **入力チェック**: 各入力項目の型、桁数、必須・任意、形式、範囲、相関チェックが決まっているか
- [ ] **境界値**: 0 件、1 件、上限件数、最大桁、日付の境界（月末・年末・うるう年・タイムゾーン）が考慮されているか
- [ ] **異常系**: 例外ごとのエラーコード、メッセージ、ログ出力、ユーザーへの表示、処理の継続・中断が決まっているか
- [ ] **トランザクション**: トランザクション境界、排他制御（楽観・悲観）、同時更新時の振る舞い、ロールバック範囲が決まっているか
- [ ] **冪等性**: 二重送信、リトライ、バッチの再実行で、データが重複・破損しないか
- [ ] **API**: 方式設計で決めた API の方式が REST と OpenAPI なら、エンドポイントごとにリクエスト・レスポンスの全項目、ステータスコード、エラー形式、認証方式が定義されているか。それ以外の方式なら、このプラグインは API の定義に対応していないので、API の定義が書かれていないことは指摘しない
- [ ] **DB**: テーブル定義（型、桁、NULL 可否、デフォルト値、制約）、インデックス、検索条件とインデックスの対応があるか
- [ ] **バッチ**: 起動条件、処理順序、対象データの抽出条件、件数見積もり、途中失敗時の再開方法があるか
- [ ] **セキュリティ**: 入力値のエスケープ、SQL インジェクション・XSS・CSRF 対策、機密情報のマスキング・暗号化、ログに個人情報を出さない設計か
- [ ] **テスト可能性**: 各処理の期待結果が、テストケースに落とせる粒度で書かれているか

## 統合仕様との整合性（横断レビュー）

横断レビュアーは、エージェント定義の「見るテーマ」に加えて、詳細設計のときは次も確かめる。

- [ ] 統合仕様の API とテーブルが、すべて基本設計の API一覧、テーブル一覧、ER図に、同じ ID と名前で載っているか
- [ ] 詳細設計書に「新規・変更」と書かれたテーブルとエンドポイントが、すべて統合仕様（`05_DB設計/テーブル定義.md` と、方式設計で決めた API の仕様の正本）に反映されているか。逆に、統合仕様にだけある変更がないか
- [ ] API の方式が REST と OpenAPI なら、`API設計書.md` と `openapi.yaml` で、パス、メソッド、パラメータ、型、必須、ステータスコードが一致しているか（それ以外の方式なら照合しない）
- [ ] `テーブル定義.md` と `ER図.md` で、テーブル、主キー、外部キー、多重度が一致しているか
- [ ] 詳細設計書が統合仕様と重複して全項目の定義を書いていないか（重複していれば、どちらかが古くなる）
- [ ] 既存のテーブルやエンドポイントを変更している場合、影響する他の機能が `【影響確認】` として挙がっているか
- [ ] 同じ ID・名称が、すべての文書で同じ意味・同じ表記で使われているか。参照している ID（画面 ID、テーブル名など）が定義元に実在するか
- [ ] `[[リンク]]` の参照先が実在するか
- [ ] トレーサビリティマトリクスと設計書本文の対応が一致しているか
