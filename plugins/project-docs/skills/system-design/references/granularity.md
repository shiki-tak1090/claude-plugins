# 設計の粒度

基本設計と詳細設計で、それぞれ何を決め、何を決めないかの決まり。作成者はこの範囲で書き、レビュアーはこの範囲で指摘する。

範囲を決めておかないと、AI は親切に細部まで書き、レビュアーはその細部の抜けを指摘し、作成者がそれをまた書き足す。指摘が減らないまま文書だけが細かくなる。

## 基本と詳細の違い

| | 基本設計 | 詳細設計 |
|---|---|---|
| 答える問い | 何を、なぜ、どの範囲で実現するか | それを、どう作り、どの条件で動かし、失敗したらどうするか |
| 読み手が判断すること | この方式で作ってよいか（採用してよいか） | この仕様で実装・テストできるか |
| 変えるときに要る合意 | 顧客、責任者、運用部門など | 設計・実装のチームの中で済む |
| レビューで探すもの | 細かすぎる記述、方式の妥当性、前提の抜け | 抽象的なままの記述、方針の蒸し返し、テストできない記述 |

## 迷ったときの 3 つの問い

1. **実装の方法が変わっても、この記述は残るか。** 残るなら基本設計、消えるなら詳細設計か実装。
2. **この記述を読んで、採用してよいかを判断するのか、作れるかを判断するのか。** 前者なら基本設計、後者なら詳細設計。
3. **この記述を変えるとき、誰の合意が要るか。** 顧客や運用部門なら基本設計、チームの中で済むなら詳細設計。

製品名やテーブル名が出てくるかどうかでは決めない。「データベースは PostgreSQL」は方式の判断なので基本設計に書く。「`plants` テーブルの `name` は `varchar(50)`」は詳細設計に書く。

## 文書ごとの範囲

基本設計の文書は、`CLAUDE.md` の「納品物の一覧」の基本設計の行と、開発標準である。一覧がない場合は [basic.md](basic.md) の既定の一覧を使う。同じことを 2 つの文書に書かないよう、文書ごとに決めることを分ける。

### システム概要（基本設計、納品物）

| 決めること | 決めないこと（送り先） |
|---|---|
| 目的と背景、利用者、範囲（対象と対象外）、機能の一覧、業務の流れ、顧客と合意した前提と制約 | 要件の書き写し（要件定義書へのリンクにする）、構成要素の説明（システム構成図）、技術の選定（方式設計） |

### システム構成図（基本設計、納品物）

| 決めること | 決めないこと（送り先） |
|---|---|
| システムの構成要素と役割、要素どうしのつながり、稼働する場所 | 技術を選んだ理由（方式設計）、環境の数とネットワークの方針（インフラ方針設計）。IP アドレス、インスタンスの種類、ネットワークの細かな設定（インフラ・運用） |
| 監視、ログ、バックアップなど、運用のための構成要素 | 監視の閾値、ログの送り方と保存の設定（インフラ・運用） |

### 方式設計（基本設計、納品物。アプリケーション方式設計）

| 決めること | 決めないこと（送り先） |
|---|---|
| 技術の選定と、選んだ理由 | ライブラリの版、設定ファイルの値（実装）。主なライブラリの選定（開発標準） |
| アプリケーションをどう分けるかと、その利点 | 層の具体的な決まり（開発標準） |
| データの扱い（何を正とするか、日付と時刻の基準、削除の方針） | テーブルごとの保持の期間（テーブル一覧）、カラムの定義（統合仕様） |
| 外部との連携の方式と、障害時の基本的な扱い | 連携の項目の対応、電文の形式（詳細設計） |
| 品質の確保の方針（何を、何に照らして確かめるか） | テストの書き方（開発標準）。承認の体制（どの設計書でも決めないこと） |

### 非機能要件定義（基本設計、納品物）

| 決めること | 決めないこと（送り先） |
|---|---|
| 項目ごとに顧客に約束する水準（可用性、性能・拡張性、運用・保守性、移行性、セキュリティ、システム環境）と、実現する文書 | 水準を守る仕組みの説明（方式設計、インフラ方針設計）。時間切れの秒数、再試行の回数（機能の詳細設計、または API 仕様の共通の節） |

約束しない項目は、削らずに「目標を置かない」と理由を書く。要件定義書にない水準を、作成者が決めて書かない（判断事項にする）。

### インフラ方針設計（基本設計、納品物）

| 決めること | 決めないこと（送り先） |
|---|---|
| 環境（本番、検証など）と、その用途と置く場所 | アカウントや環境を作る手順（インフラ・運用） |
| ネットワークの方針（公開するもの、直接つながらない場所に置くもの、外へ出る通信） | IP アドレス、サブネット、セキュリティグループの設定（インフラ・運用） |
| 可用性の構成、バックアップと復旧、監視と通知の方針（何を監視し、何を残すか） | ヘルスチェックの経路、監視の閾値、ログの保存の設定（インフラ・運用） |
| 運用の体制（誰が通知を受け、誰が本番の環境に入れ、誰が障害から復旧するか） | 運用手順書の手順、コマンド（インフラ・運用） |
| 本番への反映の方針、費用の見込み | デプロイの手順、CI/CD の作り（インフラ・運用、setup-architecture） |

### 画面一覧・画面遷移（基本設計、納品物）

| 決めること | 決めないこと（送り先） |
|---|---|
| 画面とダイアログの一覧、各画面の役割と主な操作、根拠の要件 | 領域の並びと表示する情報（画面仕様書）。項目の型・桁、文言、色（詳細設計） |
| 画面どうしの主な遷移と、その条件 | ボタンの活性・非活性の細かな条件、フォーカスの移動（詳細設計） |
| 異常時の振る舞いの方針（入力エラーで留まる、失敗を利用者に伝える、など） | どのメッセージを出すかの対応表、メッセージの文言、表示する時間（詳細設計） |
| 権限や状態による表示の違いの有無と、その方針 | 再読み込みの時機、キャッシュの扱い、並び順の照合規則の細部（詳細設計） |

### 画面仕様書（基本設計、納品物）

| 決めること | 決めないこと（送り先） |
|---|---|
| 画面ごとの領域の並び、表示する情報と元のデータ、できる操作 | 項目の型、桁、入力チェック、メッセージの文言（詳細設計の画面定義書）。色、大きさ、余白（画面のデザイン） |

画面の役割、遷移、状態による違いは、画面一覧と画面遷移に書き、画面仕様書では繰り返さない。

### API一覧（基本設計、納品物）

| 決めること | 決めないこと（送り先） |
|---|---|
| API 全体の共通の方針（形式、パスの付け方、利用者の確認） | エラーコードの体系、時間切れ（統合仕様の共通の節） |
| API の一覧（ID、名前、メソッド、パス、概要、使う画面、根拠の要件） | 要求と応答の項目、型、入力チェック、ステータスコード（詳細設計の統合仕様。API定義書） |

### テーブル一覧・ER図（基本設計、納品物）

| 決めること | 決めないこと（送り先） |
|---|---|
| テーブルの一覧（テーブル名、論理名、概要、主に持つ情報、保持の期間、削除の方針、個人情報の有無） | カラムの型、桁、NULL、既定値、制約、インデックス（詳細設計の統合仕様。テーブル定義書） |
| テーブル、主キー、外部キー、関係の多重度（ER図） | 主キーと外部キー以外のカラム（テーブル定義書） |

### バッチ処理一覧（基本設計、納品物）

| 決めること | 決めないこと（送り先） |
|---|---|
| バッチ処理の一覧（ID、名前、概要、動くきっかけ、対象のデータ、失敗したときの扱いの方針） | 処理の手順、抽出の条件、件数の見積もり、再開の方法（詳細設計。バッチ処理定義書） |

バッチ処理がない場合も文書を作り、「該当なし」と理由を書く。

### 仕様確定（基本設計、納品物）

基本設計の最後に、設計判断ログと `【要確認】` から作る（[basic.md](basic.md) の段階 9）。新しいことは決めない。レビューの対象にもしない。

### 開発標準（基本設計の段階、納品物。開発ガイドライン）

| 決めること | 決めないこと（送り先） |
|---|---|
| リポジトリごとの層と責務、置くもの・置かないもの | 個々の機能のクラスや関数の名前（タスクの「実装の配置」） |
| 依存してよい向き | 検査の道具の設定ファイルの中身（`/project-dev:setup-architecture`） |
| 迷いやすい配置の決め方（種類ごとの置き場所） | 個々の画面や API の処理の置き場所（タスクの「実装の配置」） |
| 横断的なルールの方針（エラーの分類、ログに出さないもの、設定値の読み方、認証・認可を確かめる層） | ライブラリの API の個別の使い方や設定値（`useMutation` の状態の使い方、クエリキーの付け方など）（実装・お手本の実装） |
| テストの進め方、種類と置き場所、層ごとの書き方 | 個々のテストケース（タスクの受け入れ条件） |
| 主なフレームワークとライブラリ（Web フレームワーク、データベースへのアクセス、画面のビルドとデータの取得など）、テストと機械的な検査に使う道具 | ライブラリの版、検査の具体的なルールの記述（`/project-dev:setup-architecture`） |
| 開発者の手元の環境と、テストを自動で動かす環境の方針 | 環境を作る手順、CI の設定ファイルの中身（`/project-dev:setup-architecture`、インフラ・運用） |

開発標準は開発チーム向けなので、方式の名前を使って具体的に書いてよいが、「方式とルール」までにとどめる。ライブラリの使い方の細部は、実装とお手本の実装で決まる。開発ガイドラインとして納品するため、社内向けのファイルへのリンクと番号は書かない。

### 機能ごとの詳細設計（詳細設計、納品物）

| 決めること | 決めないこと（送り先） |
|---|---|
| 処理ごとの起点、入力、条件、更新の対象、更新の順序 | 関数、クラス、変数の名前（実装） |
| 業務ルール、入力チェック（型、桁、必須、形式、範囲） | 層のどこに置くか（タスクの「実装の配置」） |
| 異常系ごとのエラーコード、利用者への表示、ログ、処理の継続 | ライブラリの選び方と使い方（開発標準・実装） |
| 同時実行、二重送信、やり直したときの扱い | |
| テーブルとエンドポイントの変更点（全項目は統合仕様）。基本設計の API一覧、テーブル一覧、ER図にない API やテーブルを足すときは、一覧と図にも行を足す | 一覧の行の意味の変更（基本設計への差し戻し候補にする） |
| 基本設計から送られた事項と、要件定義で委ねられた事項の決定 | 基本設計の方針の変更（変えるなら基本設計への差し戻し候補にする） |

詳細設計は、基本設計の方針を前提にする。方針を説明し直したり、一般論で終えたりしない（「保守性を考慮する」で終えず、どう考慮するかを書く）。

## どの設計書でも決めないこと

開発の進め方の取り決めは、システムの設計ではない。設計書に書かず、レビューでも指摘にしない。

| 事項 | 送り先 |
|---|---|
| PR や設計書を誰が承認するか、レビューの体制 | 案件の運営の取り決め（`CLAUDE.md`、`00_プロジェクト概要/` など） |
| 公開してよいかを誰が判断するか、公開の担当と手順 | インフラ・運用（`06_インフラ・運用/`） |
| 課題の管理、ブランチの運用 | `CLAUDE.md`、`06_インフラ・運用/` |

役割のうち、システムの作りが変わるもの（誰が通知を受けるか、誰が本番の環境に入れるか、誰が障害から復旧するか）は、インフラ方針設計の「運用の体制」で決める。

## 送り先

範囲の外のことは、次のどれかに送る。

| 送り先 | 送るもの |
|---|---|
| 機能の詳細設計（`03_詳細設計/`） | 機能に固有の振る舞い（削除の扱い、二重送信、境界値、画面の表示など）。複数の機能に共通するものは、対象の機能を「全機能」とし、最初に作る機能の詳細設計で決める |
| 統合仕様（`04_API仕様/`、`05_DB設計/`） | API 全体に共通する決まり（エラーコードの体系、時間切れ、認証の確かめ方など）、テーブルの定義 |
| インフラ・運用（`06_インフラ・運用/`） | インフラの構成の細部、監視とログの設定、デプロイと CI/CD、運用手順書の手順 |
| 開発標準・setup-architecture | 開発の環境、検査とテストの道具の設定 |
| 案件の運営の取り決め | 上の「どの設計書でも決めないこと」 |

## 範囲の外のことを見つけたとき

| 立場 | 扱い |
|---|---|
| 作成者 | 本文に書かない。基本設計なら `98_レビュー記録/基本設計/基本設計からの申し送り.md` に、送り先を付けて書く。詳細設計なら、送り先（統合仕様、インフラ・運用、開発標準、タスク、実装）を未決事項か報告に書く。「どの設計書でも決めないこと」は申し送りにせず、報告に送り先を書くだけにする |
| レビュアー | 指摘一覧に入れない。「申し送り」の欄に、送り先を付けて書く（件数に数えない）。「どの設計書でも決めないこと」は書かない |
| 作成者（指摘を直すとき） | 細部を書き足して直さない。この文書の粒度で決めるか、申し送りに移すか、判断事項として人に返す |

ただし、セキュリティの事故、データの消失、要件を満たさないことにつながるものは、段階によらず範囲の中として扱う。
