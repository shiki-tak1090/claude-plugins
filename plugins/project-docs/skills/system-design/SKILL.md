# 設計書作成スキル（基本設計 / 詳細設計）

要件定義書を入力に、テンプレートに沿って設計書を Markdown で作り、独立したレビュアーの敵対的レビューを経て、自然な日本語に整えた最終版を出す。設計書の正本は Markdown とし、Word や Excel への変換は `design-export` スキルで行う。

## 0. 前提とディレクトリ構成

このスキルは、ドキュメントのリポジトリ `xxxxx_document` の直下で起動する前提で書いている。このリポジトリは Obsidian の保管庫として閲覧する。コードのリポジトリは兄弟ディレクトリにある。

```
xxxxx/                          # ただのフォルダ（Git 管理しない）
├─ xxxxx_document/              # ← このスキルを置き、起動するリポジトリ
│  ├─ CLAUDE.md                 # ドキュメント作成ルール（このスキルより優先する）
│  ├─ 00_プロジェクト概要/        # 用語集.md（用語の統一に使う）
│  ├─ 01_要件定義/phaseN/        # 要件定義書（入力）
│  ├─ 02_基本設計/              # 基本設計書（アーキテクチャ、画面一覧、画面遷移など）
│  ├─ 03_詳細設計/              # 詳細設計書（機能ごとに 1 文書）
│  ├─ 04_API仕様/               # API設計書.md と openapi.yaml（全機能の統合仕様）
│  ├─ 05_DB設計/                # テーブル定義.md と ER図.md（全機能の統合仕様）
│  ├─ 07_画面仕様書/            # 画面デザイン（.pen）
│  ├─ 98_レビュー記録/           # レビュー記録、トレーサビリティ、確認事項一覧
│  └─ 99_テンプレート/           # 各文書のテンプレート
├─ xxxxx_backend/
├─ xxxxx_frontend/
└─ xxxxx_infra/
```

フォルダ名がこの構成と異なる場合は、`CLAUDE.md` に書かれた構成を優先する。どちらからも判断できないときは、推測で進めずにユーザーにパスを確認する。

### 引数

- `basic` → 基本設計を `02_基本設計/` に作る。対象は、引数で指定された文書（例: `画面一覧`）か、指定がなければ要件定義書から必要と判断した文書。
- `detailed <機能名または要件定義書のパス>` → その機能の詳細設計を `03_詳細設計/<機能名>設計.md` に作る。
  - **基本設計書も入力に含める。** 基本設計書がなければ作業を止め、先に基本設計を作るようユーザーに伝える。
  - API とテーブルの追加・変更は、`04_API仕様/` と `05_DB設計/` の統合仕様にも反映する（2-2 を参照）。
  - 既存のコードがある場合は、兄弟ディレクトリのリポジトリ（`../xxxxx_backend` など）を読んで、現状の実装と矛盾しないかを確認してよい。ただし **コードのリポジトリには書き込まない。**

### テンプレート

- テンプレートは `99_テンプレート/` から探す。
- 作る文書の種類に合うテンプレートがない場合は、次の順で決める。勝手に章立てを決めて書き始めない。
  1. 詳細設計なら、このスキルに同梱の [assets/詳細設計テンプレート.md](${CLAUDE_SKILL_DIR}/assets/詳細設計テンプレート.md) を使う。`99_テンプレート/` に追加してチームで共有してよいか、ユーザーに確認する。
  2. それ以外は、同じフォルダにある既存の文書の構成を調べ、テンプレート案を作ってユーザーに確認する。
- テンプレートが Markdown 以外（Excel や Word）で渡された場合は、作業を始める前に、Markdown 版のテンプレートを作ってよいかユーザーに確認する。

### 出力形式

- 記法は [references/markdown-rules.md](${CLAUDE_SKILL_DIR}/references/markdown-rules.md) の範囲に限る。このルールは `design-export` スキルでの変換と照合の前提になっているため、必ず守る。
- `CLAUDE.md` のドキュメント作成ルール（Mermaid の使用、`[[]]` リンクの活用など）にも従う。

## 1. 準備（入力の読み込みと作業計画）

1. 要件定義書を読む。要件 ID の体系（例: `FR-FAV-01`, `NFR-FAV-01`, `UC-FAV-01`）と、画面 ID の体系（例: `HOME-01`, `ADM-NEWS-01`）を把握する。ID がない場合は、見出し番号を要件の参照キーとして使い、その旨を最終報告に書く。
2. `00_プロジェクト概要/用語集.md` があれば読み、設計書の用語をそろえる。
3. 要件定義書の中で **「詳細設計で定義」「詳細設計で決める」「別途定義」** など、判断を設計に委ねている箇所を grep で洗い出し、一覧にする。詳細設計では、これらをすべて決めるか `【要確認】` にする。
4. 関連する既存の設計書を読む。詳細設計では、基本設計書（`02_基本設計/`）と、統合仕様（`04_API仕様/`、`05_DB設計/`）の現状を必ず読む。画面仕様は `07_画面仕様書/` の `.pen`（JSON 形式）から画面名や要素を読んでよいが、編集はしない。
5. 対象テンプレートを読み、章立て・記入ルール・記入例・必須項目を把握する。
6. 作業計画をユーザーに提示する。内容は次の 4 点に絞る。
   - 作成・更新する文書の一覧（統合仕様のどの節を変えるかを含む）
   - 要件定義書から読み取れなかった、または矛盾していると判断した点
   - 3 で洗い出した「設計に委ねられた事項」の件数
   - 進め方に影響する前提（例: 対象外とする要件）
   重大な矛盾や欠落があれば、ここでユーザーに確認してから進む。軽微なものは確認事項として記録し、作業を続ける。

## 2. 作成フェーズ

### 2-1. 設計書の作成

テンプレートに沿って設計書を作成する。守るべきルールは次のとおり。

- **テンプレートの構造を変えない。** 章立て・見出し・表の列は削除も並べ替えもしない。該当しない項目は削らずに「該当なし（理由: …）」と書く。
- **テンプレート内の記入指示や記入例（`{{…}}` や `（…を記述）`）は、本文で置き換える。** 指示文を残したままにしない。
- **すべての設計項目に根拠を付ける。** 各項目に対応する要件 ID を記載する（テンプレートにトレーサビリティ欄があればそこへ、なければ項目末尾に `[根拠: FR-FAV-01]` の形式で）。
- **要件にないことを作らない。** 要件定義書から決められない事項は推測で埋めず、`【要確認】` と書いて理由を添える。設計上の判断で補った事項は `【設計判断】` と明記し、判断理由を書く。
- **用語・ID・名称を統一する。** 用語集、既存の設計書、統合仕様の表記に合わせる。新しい画面 ID や API を採番するときは、既存の体系に従う。
- 詳細設計では、基本設計書の内容と矛盾させない。基本設計の変更が必要だと判断したら、詳細設計側で勝手に変えず `【基本設計への差し戻し候補】` として記録する。
- 文書の先頭（作成日・版）と末尾の変更履歴は、記法ルールの形にそろえる。既存の文書を更新する場合は、版を上げて変更履歴に追記する。

### 2-2. 統合仕様への反映（詳細設計のみ）

API とテーブルの正は、統合仕様（`04_API仕様/API設計書.md`、`04_API仕様/openapi.yaml`、`05_DB設計/テーブル定義.md`、`05_DB設計/ER図.md`）とする。機能ごとの詳細設計書と統合仕様に同じ定義を二重に書くと、片方だけ直されてずれていくため、次のように分担する。

| 書く場所 | 内容 |
|---|---|
| 機能ごとの詳細設計書 | 設計方針、処理の流れ、業務ルール、異常系。追加・変更するテーブルやエンドポイントの **一覧と変更点** を書き、全項目の定義は統合仕様へのリンク（`[[05_DB設計/テーブル定義#ranks]]` など）にする |
| 統合仕様 | テーブルとエンドポイントの全項目の定義 |

- 統合仕様は、この機能で追加・変更する節だけを編集する。他の機能の節は書き換えない。
- `API設計書.md` と `openapi.yaml` は必ず両方を同じ内容に直す。片方だけの変更は禁止する。
- 既存のテーブルやエンドポイントを変更する場合は、影響する他の機能の設計書を grep で洗い出し、`【影響確認】` として一覧にする（他の機能の設計書は書き換えない）。

### 2-3. 索引の更新

新しく作った文書は、そのフォルダの `README.md` の「ドキュメント一覧」の表に 1 行追加する。

### 2-4. 自己点検

書き終えたら、次の自己点検を行ってからレビューへ進む。

- 要件 ID を一覧化し、設計書のどこで扱ったかの対応表（トレーサビリティマトリクス）を `98_レビュー記録/<機能名>/traceability.md` に出力する。どこにも対応しない要件があれば、意図的な対象外か漏れかを判定し、漏れなら設計書に追記する。
- 1-3 で洗い出した「設計に委ねられた事項」が、すべて決まっているか `【要確認】` になっているかを、対応表に含めて確認する。
- テンプレートの見出しがすべて残っていることを確認する。
- [references/markdown-rules.md](${CLAUDE_SKILL_DIR}/references/markdown-rules.md) の範囲外の記法を使っていないか確認する。特に、図（Mermaid）にしか書かれていない ID や名称がないか、閉じの `**` の直前が括弧・句読点になっていないかを確認する。

## 3. 敵対的レビューフェーズ（独立コンテキスト）

### 3-1. レビュアーの起動方法

レビューは **作成者（このセッション）とは文脈を共有しないサブエージェント** に任せる。

- Agent ツールで、このプラグインのレビュー用エージェント（`subagent_type: "project-docs:design-reviewer"`）を起動する。この名前で起動できなければ、`general-purpose` を使い、`${CLAUDE_PLUGIN_ROOT}/agents/design-reviewer.md` の本文（フロントマターを除く）をプロンプトの先頭に入れる。どちらの場合も、`fork` ではなく新しいコンテキストで起動する。
- **`subagent_type: "fork"` は使わない。** fork は作成時の会話や判断を引き継ぐため、作成者の思い込みまでレビュアーに移ってしまう。
- レビュアーに渡すのは **ファイルパスとレビュー範囲だけ** にする。次のものは渡さない。
  - 作成時の判断理由、苦労した点、「ここは自信がある」などの作成者の見解
  - 「おおむね問題ないはず」「軽く見て」など、結論を誘導する言葉
  - 前ラウンドの指摘に対する作成者の回答
- 同じレビュアーを SendMessage で使い回さない。**ラウンドごとに新しいエージェントを起動する。** 前ラウンドの自分の指摘に引きずられないようにするため。
- 文書が複数あれば、文書ごとのレビュアーを 1 つのメッセージで並列に起動する。詳細設計では、これに加えて、詳細設計書と統合仕様（API設計書・openapi.yaml・テーブル定義・ER図）の整合性だけを見るレビュアーを 1 体起動する。

### 3-2. レビュアーへのプロンプト（雛形）

以下の `{}` を埋めて渡す。これ以外の情報は足さない。

```
あなたは設計レビュアーです。指示はエージェント定義に従ってください。

レビュー対象: {設計書のパス（統合仕様の整合性レビューでは、詳細設計書と統合仕様の各ファイル）}
レビュー種別: {基本設計 | 詳細設計 | 統合仕様との整合性}
要件定義書: {要件定義書のパス（複数可）}
テンプレート: {対応するテンプレートのパス}
上位設計書: {詳細設計の場合のみ、基本設計書のパス。基本設計なら「なし」}
用語集: {00_プロジェクト概要/用語集.md。なければ「なし」}
レビュー観点: ${CLAUDE_SKILL_DIR}/references/review-checklist.md
指摘の出力先: 98_レビュー記録/{機能名}/{文書名}_review_r{ラウンド番号}.md
```

### 3-3. 指摘への対応（作成者側）

レビュー結果を読み、指摘ごとに次のどれかを決めて、レビュー記録ファイルの「対応」欄に追記する。

| 対応 | 条件 |
|---|---|
| 修正 | 指摘が妥当。設計書を直し、修正箇所を書く |
| 不採用 | 指摘が誤り、または要件の範囲外。**根拠（要件 ID・テンプレートの規定など）を必ず書く**。「問題ないと考える」だけの理由は認めない |
| 要確認 | 要件定義書だけでは判断できない。`【要確認】` として設計書にも残し、最終報告でユーザーに渡す |

- 重大度 Critical の指摘を「不採用」にする場合は、自分で決めずにユーザーに確認する。
- 指摘に反論したくなったときほど、要件定義書を読み直してから判断する。作成者は自分の書いたものを正しいと思い込みやすい。

### 3-4. 終了条件

- 新しいレビュアーによる再レビューで **Critical と Major の指摘が 0 件** になったら終了する。
- 最大 3 ラウンドで打ち切る。3 ラウンド後も Critical / Major が残る場合は、残件を一覧にしてユーザーに判断を仰ぎ、次のフェーズには進まない。
- 再レビューのレビュアーにも、前ラウンドの指摘内容や対応内容は渡さない。前ラウンドの指摘が解消されたかどうかは、作成者が前回のレビュー記録と照らし合わせて自分で確認する。

## 4. 日本語の推敲フェーズ

レビューが終わった設計書を、Skill ツールで `natural-japanese` スキルを呼び出して推敲する。対象は 2-1 で作った設計書だけとし、統合仕様（`openapi.yaml` など）は推敲しない。呼び出すときは、次の制約を必ず伝える。

- 見出し、章番号、表の構造（行・列）、テンプレートの項目名は変えない
- 要件 ID、画面 ID、機能 ID、テーブル名、カラム名、API パス、コード、数値、単位は一字も変えない
- `[[リンク]]` の中身は変えない
- `【要確認】` `【設計判断】` `【基本設計への差し戻し候補】` `【影響確認】` のマーカーは残す
- 推敲は文体と読みやすさに限る。設計内容の追加・削除・解釈の変更はしない
- 設計書の文体は「である調」で統一する（テンプレートや `CLAUDE.md` に指定があればそれに従う）
- Markdown の記法は [references/markdown-rules.md](${CLAUDE_SKILL_DIR}/references/markdown-rules.md) の範囲を守る

推敲後、次の機械的な確認を行う。

- 推敲前後で、要件 ID・各種 ID の出現回数が一致すること（grep で数えて比較する）
- 見出しの一覧と `[[リンク]]` の一覧が一致すること
- 表の数と、各表の行数・列数が一致すること
- 一致しなければ、推敲で消えた・変わった箇所を元に戻す

## 5. 最終出力と報告

### 5-1. 確認事項一覧の出力

設計書に残った `【要確認】` を、`98_レビュー記録/<機能名>/確認事項一覧.md` に表で書き出す。顧客や社内の関係者にそのまま渡して回答をもらえる形にする。

| No | 確認事項 | 背景（なぜ決められないか） | 設計書の該当箇所 | 根拠の要件 | 回答 |
|---|---|---|---|---|---|

回答をもらったら、設計書を直して版を上げ、この表の「回答」欄を埋める。

### 5-2. コミット

コミットは `xxxxx_document` リポジトリで行い、コードのリポジトリの変更と混ぜない。コミットや PR の作成は、ユーザーに指示されたときだけ行う。指示されたら、`develop` から作業用のブランチ（例: `feature/<担当者>/<機能名>-design`）を切って作業し、PR の向き先は `develop` にする。ブランチ運用が `CLAUDE.md` に書かれていれば、それに従う。

### 5-3. 報告

ユーザーには次の内容を報告する。

1. 作成・更新した文書の一覧（統合仕様で変えた節を含む）
2. レビューのラウンド数と、指摘件数の推移（重大度別）
3. 不採用にした指摘とその理由（Major 以上のもの）
4. `【要確認】` の件数と、確認事項一覧のパス
5. `【設計判断】` の一覧（要件にないが設計で決めたこと）
6. `【影響確認】` の一覧（既存のテーブルや API の変更で影響を受ける他の機能）
7. 詳細設計の場合、`【基本設計への差し戻し候補】` の一覧

報告は結論から書き、各項目は箇条書きで短くまとめる。Word や Excel での納品が必要な場合は、`/design-export` で変換できることを最後に 1 行で添える。
