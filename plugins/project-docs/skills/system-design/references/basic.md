# 基本設計の手順（basic）

[SKILL.md](../SKILL.md) の共通の決まりに加えて、基本設計では次の手順で進める。粒度は [granularity.md](granularity.md) の「文書ごとの範囲」のうち、基本設計の文書の表に従う。

## 段階 1. 前提の整理

1. 要件定義書を読む。要件 ID の体系（例: `FR-FAV-01`, `NFR-FAV-01`, `UC-FAV-01`）と、画面 ID の体系（例: `HOME-01`, `ADM-NEWS-01`）を把握する。ID がない場合は、見出し番号を要件の参照キーとして使い、その旨を最終報告に書く。
2. `CLAUDE.md` の「納品物の一覧」、`00_プロジェクト概要/用語集.md`、`00_プロジェクト概要/リポジトリ一覧.md`、既存の基本設計書、`98_レビュー記録/設計情報.md` と `98_レビュー記録/設計判断ログ.md`（あれば）を読む。
3. 要件定義書の中で **「詳細設計で定義」「詳細設計で決める」「別途定義」** など、判断を設計に委ねている箇所と、`【要確認】` を grep で洗い出す。基本設計では決めず、申し送りの最初の行にする（基本設計の方式に影響するものは、段階 3 の判断事項にする）。
4. 設計情報テンプレートに沿って、`98_レビュー記録/設計情報.md` を作る（あれば更新する）。要件定義書から書けることは要件 ID で参照し、書けないことを質問の一覧にする。
5. 質問を 1 回にまとめて聞く。基本設計では、少なくとも次のことが決まっていないと方式を書けない。要件定義書や設計情報で決まっていなければ聞く。
   - コードリポジトリの構成（例: 画面とサーバーを分けるか、1 つにまとめるか）
   - 各リポジトリの言語・フレームワーク。**サーバー側の言語を選択肢で聞くときは、Rust を先頭に置く**
   - データベース
   - 稼働させる場所（クラウドの種類など）
   - 判断の優先順位（データの保全、運用の手間、費用、開発の速さ など）
   - 役割のうち、システムの作りが変わるもの：監視の通知を受ける人、本番の環境に入れる人、障害から復旧する人（利用者本人、運用部門、開発チームなど）。答えは設計情報の「利用者と運用者」に書く
   開発の進め方の取り決め（PR や設計書の承認、公開の許可と担当など）は聞かない。設計書で決めることではないため（[granularity.md](granularity.md) の「どの設計書でも決めないこと」）。
   答えを設計情報の「制約と決定済みのこと」に書く。答えが「未定」で、その場にいない関係者に確かめる必要があるなら `【要確認】` にし、確認先を書く。作成者が仮に置く前提は `【仮定】` として設計情報にだけ書き、ユーザーに伝える。

## 段階 2. 文書の地図

### 作る文書

作る文書は、`CLAUDE.md` の「納品物の一覧」のうち工程が基本設計の行と、開発標準（開発ガイドライン）である。一覧がなければ、次の既定の一覧を使い、`CLAUDE.md` に一覧を足してよいかユーザーに確認する。

| 納品物 | ファイル | テンプレート | 書く順 |
|---|---|---|---|
| システム概要 | `02_基本設計/システム概要.md` | システム概要テンプレート | 1 |
| 非機能要件定義 | `02_基本設計/非機能要件定義.md` | 非機能要件定義テンプレート | 2 |
| システム構成図 | `02_基本設計/システム構成図.md` | システム構成図テンプレート | 3 |
| アプリケーション方式設計 | `02_基本設計/方式設計.md` | 方式設計テンプレート | 4 |
| インフラ方針設計 | `02_基本設計/インフラ方針設計.md` | インフラ方針設計テンプレート | 5 |
| 画面一覧 | `02_基本設計/画面一覧.md` | 画面一覧テンプレート | 6 |
| 画面遷移図 | `02_基本設計/画面遷移.md` | 画面遷移テンプレート | 7 |
| テーブル一覧 | `05_DB設計/テーブル一覧.md` | テーブル一覧テンプレート | 8 |
| ER図 | `05_DB設計/ER図.md` | ER図テンプレート | 9 |

- 一覧の文書は、すべて作る。該当するものがない文書（バッチ処理がない、外部との連携がない、など）も、文書を作って「該当なし」と理由を書く。納品物の数を、案件ごとの判断で減らさない。
- 書く順は、後の文書が前の文書を参照できる順である。前の文書を書き終えてから次に進む。
- テンプレートが `99_テンプレート/` になければ、SKILL.md の「テンプレート」に従う（ひな型の最新の `99_テンプレート/` から取り込んでよいか、ユーザーに確認するのがよい）。

### 章ごとの範囲

作る文書ごとに、章ごとの「この章で決めること」と「扱わないこと（送り先）」を表にして、ユーザーに 1 回で確認してもらう。粒度の決まりを、この案件の文書に当てはめたものである。

| 文書 | 章 | この章で決めること | 扱わないこと（送り先） | 関係する章 |
|---|---|---|---|---|
| 非機能要件定義 | 可用性 | 稼働時間の目標と、障害で失いうるデータの範囲 | 時間切れの秒数（API 仕様の共通の節）、監視の閾値（インフラ・運用） | インフラ方針設計「可用性の構成」 |

- この表は確認のためのもので、ファイルには保存しない（必要ならユーザーの指示で保存する）。

### 同じことを 2 か所に書かない

基本設計の文書は数が多く、同じことを複数の文書に書くと、片方だけ直されてずれていく。次のものは、正とする文書にだけ書き、ほかの文書からはリンクで参照する。

| 内容 | 正とする文書 |
|---|---|
| 構成要素とそのつながり | システム構成図 |
| 技術の選定と理由 | 方式設計 |
| 約束する水準（数値、条件） | 非機能要件定義 |
| 環境、ネットワーク、バックアップ、監視、運用の体制 | インフラ方針設計 |
| 画面の役割と遷移 | 画面一覧、画面遷移 |
| 画面の領域の並びと表示する情報 | 画面仕様書 |
| テーブルごとの保持の期間と削除の方針 | テーブル一覧 |
| テーブルの関係 | ER図 |
| 主なライブラリと層の決まり | 開発標準 |

## 段階 3. 判断事項

SKILL.md の「3. 判断事項の扱い」に従う。基本設計で人に返すことの例は次のとおり。

- 方式の選択（構成、稼働場所、データベース、認証の方式）
- 非機能要件の水準。要件定義書にない項目は、おすすめの水準を項目ごとに並べ、まとめて 1 つの判断事項にする（項目ごとに 1 問にしない）。要件定義書で `【要確認】` のものが決まるまでの暫定の扱いも含める
- 環境の数、本番への反映の方針、費用の見込みの前提
- 対象外にすること、将来に備えるかどうか（例: Phase 2 に今から備えるか）
- 開発標準の方針（層の分け方、テストの進め方などの採用する方式）
- 開発標準で使う主なフレームワークとライブラリ、テストと機械的な検査の道具（要件と方式から候補を挙げ、おすすめを示して選んでもらう）。`/project-dev:setup-architecture` は、開発標準に `【要確認】` が残っていると止まるため、ここで決める

スキルを実行している人が決められることは、`【要確認】` にせず、ここで聞く。

## 段階 4. 作成

テンプレートに沿って、段階 2 の書く順に、地図の範囲だけを書く。

- **システム概要**：要件定義書を書き写さず、要約と要件 ID とリンクにする。機能の一覧の「主な画面」は、画面一覧を書いた後で埋める。
- **非機能要件定義**：テンプレートの項目を削らない。水準は確かめられる形（数値、条件）で書き、約束しない項目は「目標を置かない」と理由を書く。「実現の方針」は 1 行にし、詳しくは方式設計かインフラ方針設計の章を示す。
- **システム構成図**：利用者の通信の経路の図と、運用のための構成を分ける。
- **方式設計**：技術の選定、アプリケーションの構成、データの扱い、外部との連携、品質の確保の方針を、方式の名前ではなく顧客にとっての利点（保守性、品質など）で書く。構成要素の説明と非機能の水準は書き写さない。
- **インフラ方針設計**：方針までを書く。設定値や手順は申し送り（インフラ・運用）に回す。運用の体制は、段階 1 で答えてもらった役割を書く。
- **画面一覧・画面遷移**：画面 ID を採番する。
- **テーブル一覧・ER図**：テーブル名は、要件の用語を英語の複数形の snake_case にする（既存の統合仕様があれば、その体系に従う）。ER図には、主キーと外部キーのほかのカラムを書かない。
- **画面仕様書**：画面一覧と同じ画面 ID で、同じ順に書く。「元のデータ」はテーブル一覧のテーブル名で書く。
- **API一覧**：API ID は `API-<機能の略号>-<2 桁の連番>` で採番する。「使う画面」は画面一覧の画面 ID で書く。画面仕様書の「できる操作」のうち、データを読み書きするものに、対応する API があること。
- **バッチ処理一覧**：バッチ処理 ID は `BAT-<2 桁の連番>` で採番する。
- **開発標準**（開発ガイドライン）：コードリポジトリごとに、層と責務・依存してよい向き・迷いやすい配置の決め方・横断的なルール・テストの方針・機械的な検査の方法を具体的に決める。これが `/project-dev:setup-architecture` で各コードリポジトリの実装規約に落とし込まれる正本になる。ライブラリの使い方の細部までは書かない（粒度の決まりを参照）。
- 開発手法やアーキテクチャの方式の名前（TDD、DDD、クリーンアーキテクチャなど）と具体的な決まりは、開発標準にだけ書く。`01_`〜`08_` の文書には混ぜない。
- 図は、1 つの図で 1 つのことを伝える。図の前の文で、何を伝える図かを書く。構成、データの流れ、処理の流れ、人の運用の流れを 1 つの図に混ぜない。
- 作った文書は、それぞれのフォルダの `README.md` の表に 1 行ずつ足す。

### 申し送り

範囲の外として本文に書かなかったことを、`98_レビュー記録/基本設計/基本設計からの申し送り.md` に、送り先を付けて書く。レビューで「申し送る」と仕分けた指摘も、ここに足す。送り先は [granularity.md](granularity.md) の「送り先」から選ぶ。

```markdown
# 基本設計からの申し送り

基本設計の範囲の外として、ほかの文書で決める事項の一覧。送り先の文書を作るときに、すべてを決めるか【要確認】にする。

作成日：2026-05-01
版：v0.1

---

| No | 事項 | 出どころ | 関係する基本設計の箇所 | 送り先 | 対象の機能 | 決めた文書 |
|---|---|---|---|---|---|---|
| HS-01 | （例: 削除した植物の水やり記録の扱い） | （例: 要件定義書 FR-PLT-02「詳細設計で定義」） | （例: 画面一覧「DLG-01」） | 機能の詳細設計 | （例: 植物管理） | （送り先で記入） |
| HS-02 | （例: 通信が時間切れになるまでの秒数） | （例: 非機能要件定義のレビューで、時間切れの秒数が決まっていないと指摘された） | （例: 非機能要件定義「性能・拡張性」） | 統合仕様 | — | （送り先で記入） |
| HS-03 | （例: 監視の閾値と通知の設定） | （例: インフラ方針設計のレビューで、監視の閾値が決まっていないと指摘された） | （例: インフラ方針設計「監視と通知」） | インフラ・運用 | — | （送り先で記入） |

- 「出どころ」には、レビューの記録のファイル名や指摘の No を書かず、指摘の要旨を書く。レビューの記録は `作業中/` に置き、完了時に消すため。
- 「対象の機能」は、送り先が機能の詳細設計のときだけ書く。複数の機能に共通するものは「全機能」とし、最初に作る機能の詳細設計で決める。
- 「決めた文書」は、送り先の文書を作った人が記入する。送り先が機能の詳細設計の行は、`/project-dev:design-to-tasks` がこの欄を確かめる。

---

## 変更履歴

| 日付 | 変更者 | 変更内容 |
|---|---|---|
| 2026-05-01 | — | 初版 |
```

### 自己点検

書き終えたら、レビューへ進む前に次を確かめる。

- 段階 2 の「作る文書」がすべてあり、それぞれのフォルダの `README.md` の表に載っていること。
- 要件 ID を一覧化し、設計書のどこで扱ったかの対応表（トレーサビリティマトリクス）を `98_レビュー記録/基本設計/作業中/traceability.md` に出力する（完了時に消す）。どこにも対応しない要件があれば、意図的な対象外か、申し送りか、漏れかを判定し、漏れなら設計書に追記する。
- 段階 2 の地図の「扱わないこと」が本文に書かれていないこと。
- 文書どうしで ID と名前がそろっていること。画面 ID（画面一覧、画面遷移、画面仕様書、API一覧、システム概要）、テーブル名（テーブル一覧、ER図、画面仕様書）、構成要素の名前（システム構成図、方式設計、インフラ方針設計）を grep で突き合わせる。
- 段階 2 の「同じことを 2 か所に書かない」の内容が、正とする文書のほかに書き写されていないこと。
- 納品物（`01_`〜`09_`）に、社内向けのファイルの番号（`DL-`、`HS-`、設計情報の No）がないこと（grep で確かめる）。
- テンプレートの見出しがすべて残っていること。
- [markdown-rules.md](markdown-rules.md) の範囲外の記法を使っていないこと。特に、図（Mermaid）にしか書かれていない ID や名称がないか、閉じの `**` の直前が括弧・句読点になっていないかを確認する。

## 段階 5〜7. レビュー

SKILL.md の「4. レビュー」〜「6. 再レビューと終了条件」に従う。基本設計では、ラウンドごとに次を並列に起動する。

| レビュアー | レビュー種別 | レビュー対象 | 出力先の名前 |
|---|---|---|---|
| 1 体 | 基本設計 | システム概要、システム構成図、方式設計、非機能要件定義、インフラ方針設計 | 概要と方式 |
| 1 体 | 基本設計 | 画面一覧、画面遷移、画面仕様書 | 画面 |
| 1 体 | 基本設計 | テーブル一覧、ER図、API一覧、バッチ処理一覧 | データとAPI |
| 1 体 | 基本設計 | 開発標準 | 開発標準 |
| 1 体 | 横断（基本設計） | 基本設計の全文書（仕様確定を除く）と、用語集 | 横断 |

- 文書が多いため、関係の深い文書をまとめて 1 体のレビュアーに渡す。レビュアーは、まとまりの中の文書を 1 つずつレビューし、1 つの出力先に書く。テンプレートは、まとまりの中の文書のテンプレートをすべて渡す。
- 仕様確定は段階 9 で作るため、レビューの対象にしない。
- ラウンド 2 以降も、すべてのまとまりと横断を、新しいレビュアーでレビューする。

## 段階 8〜9

SKILL.md の「7. 反対役の確認」〜「9. 最終出力と報告」に従う。基本設計では、9-1 で次のように仕様確定を作る。

### 仕様確定

`99_テンプレート/仕様確定テンプレート.md` に沿って、`02_基本設計/仕様確定.md` を作る。新しいことは決めず、すでに決まったことと `【要確認】` を、発注者が読める形に写す。

| 章 | 写す元 | 写し方 |
|---|---|---|
| 確定した仕様 | 設計判断ログのうち、「反映した文書」が `01_`〜`08_` の判断と、設計情報の「制約と決定済みのこと」のうち発注者が決めたもの | 事項、確定した内容、発注者に説明する理由、決めた人、決めた日、反映した文書の章。開発チームが決め、発注者の了承をまだ得ていないものは、決めた人を「開発チーム（ご確認ください）」とする |
| 確認をお願いする事項 | 基本設計の文書の `【要確認】` のうち、確認先が発注者のもの | 確認事項、背景、設計書の該当箇所、根拠の要件 |

- 判断の番号（`DL-xx`）や設計情報の No は書かない。
- 確認先が発注者でない `【要確認】`（運用部門など社内の関係者）は、仕様確定ではなく `98_レビュー記録/基本設計/確認事項一覧.md` に書く。該当がなければ確認事項一覧は作らない。
- 作ったら、段階 8 の推敲と同じ制約で推敲し、次を grep で確かめる。設計判断ログの判断のうち「反映した文書」が `01_`〜`08_` のものがすべて載っていること。確認先が発注者の `【要確認】` がすべて載っていること。社内向けのファイルの番号がないこと。
