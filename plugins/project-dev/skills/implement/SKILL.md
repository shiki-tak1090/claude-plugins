# 設計どおりの実装

`<案件名>_document/97_タスク分解/` にあるタスクを、設計書どおりに実装して PR を作る。**設計書が正であり、実装中に設計と違うことをしない。**

Backlog には接続しない。課題のステータス変更やコメントは人が行い、このスキルは貼り付ける文面を用意する。

## 守ること

- **設計と食い違う実装をしない。** 設計の誤りや決め漏れを見つけたら、4 の手順で扱う。「設計はこうだが、こちらのほうが良さそうなので変えた」はしない。
- **設計から一意に決まらない振る舞いを、自分の解釈で決めない。** 「設計書の表から合理的に推測できる」と思えても、書かれていなければ決め漏れとして扱い、止まって確認する。解釈で埋めて、報告で「設計での明記をお願いします」と伝えるだけにはしない。
- **タスクの範囲の外を変えない。** 気づいた別の問題は、報告に「範囲外で気づいたこと」として書く。
- **アーキテクチャの規約に従い、規約と検査を変えない。** `CLAUDE.md` の「アーキテクチャと実装規約」の節に従って実装する。アーキテクチャの検査に違反したら、コードを直す。検査の設定、除外の登録、規約の節を変えて違反を通すことはしない。規約どおりに実装できない場合は、止まってユーザーに確認する（規約を変えるには、ドキュメントリポジトリの開発標準.md を直してから `/project-dev:setup-architecture` を再実行する必要がある）。
- **push と PR の作成は、内容を見せて了承を得てから行う。**
- テスト・lint・ビルドの方法は、このリポジトリの `CLAUDE.md` に従う。書かれていなければ、推測で決めずにユーザーに聞き、`CLAUDE.md` への追記を提案する。

## 0. 前提の確認

1. コードリポジトリの直下で実行されていること。親フォルダにドキュメントリポジトリ（`../<案件名>_document`）があること。
2. `git status` に未コミットの変更がないこと。あれば、進めてよいか確認する。
3. **Git の置き場所を判定する。** `git remote get-url origin` の URL で判定し、以降の PR の操作に使うツールを決める。

   | URL に含まれるもの | 置き場所 | PR のツール | ログインの確認 |
   |---|---|---|---|
   | `github.com` | GitHub | GitHub CLI（`gh`） | `gh auth status` |
   | `dev.azure.com` または `visualstudio.com` | Azure DevOps | Azure CLI（`az repos`） | `az account show` と `az extension show --name azure-devops` |

   どちらでもなければ止まり、ユーザーに置き場所を聞く。ログインしていなければ、本人に `gh auth login` または `az login` を実行してもらう（代わりに実行しない）。

## 1. タスクを読む

引数の形で読み方を変える。

| 引数 | 読み方 |
|---|---|
| タスク ID（`T-FAV-01` など） | `../<案件名>_document/97_タスク分解/` を grep して、その ID の節を読む |
| 課題の本文の貼り付け | 貼り付けられた本文を読む。本文にタスク ID があれば、タスクファイルの節も読んで突き合わせる |

読んだら、次のことを確認する。

- **「未決事項」が「なし」であること。** 未決事項が残っていれば、実装に着手せずに止まり、未決事項の一覧を見せる。ユーザーには、設計書を直してから `design-to-tasks` でタスクを更新するよう伝える。ユーザーがその場で決めた内容を示した場合も、その内容を設計書に反映してから着手する（設計書が正であるため）。
- **対象リポジトリが、このリポジトリと一致すること。** 違えば止まり、正しいリポジトリを伝える。
- **依存するタスクが終わっていること。** 依存先のブランチが `develop` にマージされているかを、`git log` や PR の状態で確かめる。PR の状態は、GitHub なら `gh pr list --state all --search <タスク ID>`、Azure DevOps なら `az repos pr list --status all --query "[?contains(title, '<タスク ID>')].{id:pullRequestId, status:status, title:title}"` で調べる。終わっていなければ、進めてよいか確認する。
- **Backlog の課題キーがあれば控える。** タスク一覧の表に記入されていれば、それを使う。なければユーザーに聞く（まだ起票していなければ、タスク ID で代用してよい）。

## 2. 設計を読む

1. タスクの「設計の参照」に書かれた節を、すべて読む。
2. **設計の版を確認する。** タスクに書かれた「設計の版（コミット）」と、ドキュメントリポジトリの現在の版を比べる。

   ```bash
   git -C ../<案件名>_document diff --stat <設計の版> HEAD -- 03_詳細設計 04_API仕様 05_DB設計
   ```

   参照している設計書が、分解した後に変わっていれば、差分を見せて、どちらの版で実装するかをユーザーに確認する。黙って新しい版で実装しない（タスクの受け入れ条件と食い違うことがあるため）。
3. **アーキテクチャの規約を読む。** このリポジトリの `CLAUDE.md` の「アーキテクチャと実装規約」の節と、そこに書かれた正本（`../<案件名>_document/09_開発標準/開発標準.md`）を読む。
   - 節がなければ止まり、先に `/project-dev:setup-architecture` で規約を作るよう伝える（規約なしで実装すると、方針がばらつくため）。
   - 節に書かれた正本の版と、開発標準.md の今の版が違えば、規約が古い可能性がある。差分を見せて、`/project-dev:setup-architecture` を再実行してから実装するかを確認する。
4. **配置を決める。** タスクの「実装の配置」から、このリポジトリのどの層に何を作るかを読む。表にない部品を作る必要があれば、規約の「迷いやすい配置の決め方」に従う。それでも決まらなければ、設計の決め漏れとして 4 の手順で扱う。
5. 規約の「お手本の実装」があれば読み、書き方（命名、層の分け方、テストの書き方）をそろえる。
6. このリポジトリの既存のコードを読み、設計書の名称（テーブル、カラム、エンドポイント、エラーコード）が、コード上でどう表現されているかを把握する。

## 3. ブランチとテスト

1. `develop` を最新にして、作業ブランチを切る。ブランチ名は `feature/<課題キーまたはタスク ID>-<英語の短い説明>` にする（例: `feature/ACME-123-favorite-api`）。
2. **受け入れ条件から、先にテストを書く。** 受け入れ条件の 1 項目に、少なくとも 1 つのテストを対応させる。異常系と境界値は、設計書の「入力チェック」「異常系」の表から 1 行ずつ拾う。
3. テストを実行し、**失敗することを確かめる**（まだ実装していないので失敗するはず。通ってしまうなら、テストが条件を確かめていない）。

## 4. 実装

テストが通るように実装する。リポジトリのテスト・lint・ビルドと、**アーキテクチャの検査**（「テスト・lint・ビルド」の表の「アーキテクチャの検査」の行）をすべて通す。アーキテクチャの検査に違反したら、検査ではなくコードを直す。

実装中に設計の問題を見つけたら、次のように扱う。

| 問題の種類 | 例 | 対応 |
|---|---|---|
| 振る舞いに影響しない誤り | 誤字、明らかな表記ゆれ | 実装は設計の意図どおりに進め、報告に「設計の修正候補」として書く |
| 振る舞いに影響する誤り・決め漏れ | 異常時の扱いが書かれていない、API と DB の型が食い違う、複数の入力が同時に不正なときにどのエラーを返すか書かれていない、想定外の型が渡されたときの扱いが書かれていない | **実装を止めてユーザーに確認する。** 設計書の修正が必要なら、ドキュメントリポジトリで先に直してもらう |

止まるかどうか迷ったら止まる。止まらずに進めてよいのは、設計書の記述から振る舞いが 1 通りに決まる場合だけである。

## 5. 設計との照合レビュー（独立コンテキスト）

実装が終わったら、作成者（このセッション）とは文脈を共有しないレビュアーに、設計との照合をさせる。

- Agent ツールで `subagent_type: "project-dev:impl-reviewer"` を起動する。この名前で起動できなければ、`general-purpose` を使い、`${CLAUDE_PLUGIN_ROOT}/agents/impl-reviewer.md` の本文（フロントマターを除く）をプロンプトの先頭に入れる。`fork` は使わない。
- レビュアーに渡すのは、次の雛形の情報だけにする。実装時の判断理由や「ここは問題ないはず」といった見解は渡さない。

```
あなたは実装レビュアーです。指示はエージェント定義に従ってください。

タスク: {タスクファイルのパス}「{タスク ID}」の節
設計書: {タスクの「設計の参照」に書かれたファイルと節}
設計の版: {実装に使った設計のコミット}（ドキュメントリポジトリ: ../<案件名>_document）
差分: このリポジトリの `git diff develop...HEAD`（未コミットの変更があれば `git diff develop` も）
実装規約: このリポジトリの CLAUDE.md の「アーキテクチャと実装規約」の節
テストの実行方法: {CLAUDE.md に書かれたコマンド}
アーキテクチャの検査: {CLAUDE.md に書かれたコマンド}
```

- 指摘のうち Critical と Major はすべて対応する（修正するか、設計を根拠に不採用の理由を書く）。ただし、**指摘に対応するために、設計書に書かれていない振る舞いを決める必要がある場合は、修正せずに止まってユーザーに確認する**（4 の決め漏れと同じ扱い）。対応したら、**新しいレビュアーを起動して** 再レビューする。同じレビュアーを使い回さない。
- Critical と Major が 0 件になったら終える。3 ラウンドで終わらなければ、残件を見せてユーザーに判断を仰ぐ。

## 6. コミット・push・PR

1. コミットの前に、実装した振る舞いがすべて設計書か受け入れ条件に書かれていることを確かめる。書かれていない振る舞いが 1 つでもあれば、コミットせずに止まって確認する。
2. 変更をコミットする。コミットメッセージの先頭に課題キー（なければタスク ID）を付ける（例: `ACME-123 お気に入り登録 API を追加`）。
3. PR の内容を下書きし、push 先のブランチと一緒にユーザーに見せて了承を得る。
4. 了承を得たら、push して、置き場所に合わせたコマンドで `develop` 向けの PR を作る。

   | 置き場所 | PR を作るコマンド |
   |---|---|
   | GitHub | `gh pr create --base develop --title "<タイトル>" --body-file <本文のファイル>` |
   | Azure DevOps | `az repos pr create --target-branch develop --source-branch <作業ブランチ> --title "<タイトル>" --description "<本文>"` |

   Azure DevOps の PR の説明は 4,000 文字までなので、本文が長くなる場合は、テスト結果などを要約して収める。

PR の本文は次の形にする。

```markdown
## 概要
（何を実装したか）

## 課題
- Backlog: {課題キー}（{Backlog の課題 URL が分かれば記載}）
- タスク: {タスク ID}（`<案件名>_document/97_タスク分解/{ファイル名}`）

## 設計の参照
- {設計書のパスと節}（設計の版: {コミット}）

## 受け入れ条件
- [x] （条件）… テスト: `{テスト名}`
- [x] （条件）… テスト: `{テスト名}`

## テスト結果
（実行したコマンドと結果の要約）

## 設計との照合レビュー
- ラウンド数: {N}
- 対応した指摘: {件数と要約}
- 不採用にした指摘: {あれば、理由とともに}
```

## 7. 報告と Backlog に貼る文面

最後に、次の内容を出す。

1. PR の URL
2. **Backlog の課題に貼るコメント**（そのまま貼れる形。Markdown の記法に頼らない）

   ```
   PR を作成しました。
   {PR の URL}

   ■ 実装内容
   （2〜3 行）

   ■ 受け入れ条件
   すべてテストで確認済み（{件数} 件）

   ■ レビュー
   設計との照合レビュー {N} ラウンドで、Critical・Major の指摘なし
   ```

3. 課題のステータスは、社内の運用フローに従って本人が変更するよう伝える（このスキルは変更しない）
4. 「設計の修正候補」と「範囲外で気づいたこと」があれば、その一覧
