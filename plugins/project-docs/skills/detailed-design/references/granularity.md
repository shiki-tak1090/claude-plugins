# 詳細設計の粒度

機能ごとの詳細設計で何を決め、何を決めないかの決まり。作成者はこの範囲で書き、レビュアーはこの範囲で指摘する。

範囲を決めておかないと、AI は分からないことを一般論で埋め、レビュアーは基本設計で決めた方針を蒸し返す。詳細設計は、基本設計の方針を前提に、実装とテストができるところまで具体化する。

## 基本と詳細の違い

| | 基本設計 | 詳細設計 |
|---|---|---|
| 答える問い | 何を、なぜ、どの範囲で実現するか | それを、どう作り、どの条件で動かし、失敗したらどうするか |
| 読み手が判断すること | この方式で作ってよいか（採用してよいか） | この仕様で実装・テストできるか |
| 変えるときに要る合意 | 顧客、責任者、運用部門など | 設計・実装のチームの中で済む |
| レビューで探すもの | 細かすぎる記述、方式の妥当性、前提の抜け | 抽象的なままの記述、方針の蒸し返し、テストできない記述 |

## 迷ったときの 3 つの問い

1. **実装の方法が変わっても、この記述は残るか。** 残るなら基本設計、消えるなら詳細設計か実装。
2. **この記述を読んで、採用してよいかを判断するのか、作れるかを判断するのか。** 前者なら基本設計、後者なら詳細設計。
3. **この記述を変えるとき、誰の合意が要るか。** 顧客や運用部門なら基本設計、チームの中で済むなら詳細設計。

製品名やテーブル名が出てくるかどうかでは決めない。「データベースは PostgreSQL」は方式の判断なので基本設計に書く。「`plants` テーブルの `name` は `varchar(50)`」は詳細設計に書く。

## 機能ごとの詳細設計で決めること（納品物）

| 決めること | 決めないこと（送り先） |
|---|---|
| 処理ごとの起点、入力、条件、更新の対象、更新の順序 | 関数、クラス、変数の名前（実装） |
| 業務ルール、入力チェック（型、桁、必須、形式、範囲） | 層のどこに置くか（タスクの「実装の配置」） |
| 異常系ごとのエラーコード、利用者への表示、ログ、処理の継続 | ライブラリの選び方と使い方（開発標準・実装） |
| 同時実行、二重送信、やり直したときの扱い | |
| テーブルとエンドポイントの変更点（全項目は統合仕様）。基本設計の API一覧、テーブル一覧、ER図にない API やテーブルを足すときは、一覧と図にも行を足す | 一覧の行の意味の変更（基本設計への差し戻し候補にする） |
| 基本設計から送られた事項と、要件定義で委ねられた事項の決定 | 基本設計の方針の変更（変えるなら基本設計への差し戻し候補にする） |

詳細設計は、基本設計の方針を前提にする。方針を説明し直したり、一般論で終えたりしない（「保守性を考慮する」で終えず、どう考慮するかを書く）。

## 基本設計で決めたこと

次のものは基本設計で決めている。詳細設計では前提にし、書き写さずにリンクで参照する。変える必要があると判断したら、変えずに `【基本設計への差し戻し候補】` にする。

| 内容 | 決めた文書 |
|---|---|
| 構成要素、技術の選定、アプリケーションの構成、データの扱い | システム構成図、方式設計 |
| 約束する水準、環境と運用の方針 | 非機能要件定義、インフラ方針設計 |
| 画面の一覧、役割、遷移、領域の並びと表示する情報 | 画面一覧、画面遷移、画面仕様書 |
| API とテーブルとバッチ処理の一覧、テーブルの関係 | API一覧、テーブル一覧、ER図、バッチ処理一覧 |
| 層の決まり、主なライブラリ | 開発標準 |

## どの設計書でも決めないこと

開発の進め方の取り決めは、システムの設計ではない。設計書に書かず、レビューでも指摘にしない。

| 事項 | 送り先 |
|---|---|
| PR や設計書を誰が承認するか、レビューの体制 | 案件の運営の取り決め（`CLAUDE.md`、`00_プロジェクト概要/` など） |
| 公開してよいかを誰が判断するか、公開の担当と手順 | インフラ・運用（`06_インフラ・運用/`） |
| 課題の管理、ブランチの運用 | `CLAUDE.md`、`06_インフラ・運用/` |

役割のうち、システムの作りが変わるもの（誰が通知を受けるか、誰が本番の環境に入れるか、誰が障害から復旧するか）は、インフラ方針設計の「運用の体制」で決める。

## 送り先

詳細設計の範囲の外のことで、決める必要があるものは、この機能の未決定事項一覧の「決める工程」に、次のどれかを書いて送る。

| 送り先 | 送るもの |
|---|---|
| 統合仕様（`04_API仕様/`、`05_DB設計/`） | API 全体に共通する決まり（エラーコードの体系、時間切れ、認証の確かめ方など）。ほかの機能と共有するテーブルの定義 |
| インフラ・運用（`06_インフラ・運用/`） | インフラの構成の細部、監視とログの設定、デプロイと CI/CD、運用手順書の手順 |
| 開発標準・setup-architecture | 開発の環境、検査とテストの道具の設定 |
| タスクの「実装の配置」（`/project-dev:design-to-tasks`） | 層のどこに置くか |
| 実装 | 関数、クラス、変数の名前、ライブラリの使い方 |
| 案件の運営の取り決め | 上の「どの設計書でも決めないこと」 |

## 範囲の外のことを見つけたとき

| 立場 | 扱い |
|---|---|
| 作成者 | 本文に書かない。決める必要があることは、この機能の未決定事項一覧に、決める工程を付けて書く。「どの設計書でも決めないこと」は一覧に入れない |
| レビュアー | 本文に範囲の外のことが書かれていれば、「粒度を超えた記述」の欠陥にする。書かれていないことは欠陥にしない。決める必要があれば「未決定事項の候補」に、決める工程の案を付けて書く |
| 作成者（指摘を直すとき） | 基本設計の方針を変えて直さない。変える必要があれば `【基本設計への差し戻し候補】` にする |

ただし、セキュリティの事故、データの消失、要件を満たさないことにつながる記述の誤りは、範囲によらず欠陥として扱う。
