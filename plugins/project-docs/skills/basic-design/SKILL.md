# 基本設計スキル

要件定義書を入力に、テンプレートに沿って基本設計の文書を Markdown で作り、独立したレビュアーのレビューと人の判断を経て、自然な日本語に整えた最終版を出す。設計書の正本は Markdown とし、Word や Excel への変換は `design-export` スキルで行う。機能ごとの詳細設計は、このスキルの後に `/project-docs:detailed-design` で作る。

このスキルで AI がすることは、整理、案出し、執筆、レビューである。**前提、制約、方式の採用、リスクの受け入れは人が決める。** AI が決めたことを、設計書に決定事項として書かない。

## 0. 前提とディレクトリ構成

このスキルは、ドキュメントのリポジトリ `xxxxx_document` の直下で起動する前提で書いている。このリポジトリは Obsidian の保管庫として閲覧する。コードのリポジトリは兄弟ディレクトリにある。

```
xxxxx/                          # ただのフォルダ（Git 管理しない）
├─ xxxxx_document/              # ← このスキルを起動するリポジトリ
│  ├─ CLAUDE.md                 # ドキュメント作成ルールと納品物の一覧（このスキルより優先する）
│  ├─ 00_プロジェクト概要/        # 用語集.md（用語の統一に使う）
│  ├─ 01_要件定義/              # 要件定義書（入力。サブフォルダの分け方は案件による）
│  ├─ 02_基本設計/              # システム概要、システム構成図、方式設計、非機能要件定義、インフラ方針設計、画面一覧、画面遷移、バッチ処理一覧、仕様確定
│  ├─ 04_API仕様/               # API一覧.md（このスキルで作る）
│  ├─ 05_DB設計/                # テーブル一覧.md と ER図.md（このスキルで作る）
│  ├─ 07_画面仕様書/            # 画面仕様書.md（このスキルで作る）と画面デザイン（.pen）
│  ├─ 09_開発標準/              # 開発標準.md（開発ガイドラインとして納品する。実装規約の正本）
│  ├─ 98_レビュー記録/           # 設計情報、設計判断ログ、申し送り、確認事項一覧（社内向け）。レビューの途中経過は作業中/に置き、完了時に消す
│  └─ 99_テンプレート/           # 各文書のテンプレート
├─ xxxxx_backend/
└─ xxxxx_frontend/
```

フォルダ名がこの構成と異なる場合は、`CLAUDE.md` に書かれた構成を優先する。どちらからも判断できないときは、推測で進めずにユーザーにパスを確認する。要件定義書が 1 つに決まらないとき（引数がなく、フォルダに複数あるときなど）も、どれを使うかをユーザーに確認する。

### 社内向けの作業ファイル

設計の前提と判断の理由は、納品物とは別のファイルに残す。設計情報と設計判断ログは案件全体で 1 つずつ持ち、基本設計で作り、詳細設計で書き足していく。

| ファイル | 内容 | テンプレート |
|---|---|---|
| `98_レビュー記録/設計情報.md` | 目的、利用者と運用者、対象と対象外、制約と決定済みのこと、失敗したときの扱い、判断の優先順位 | `99_テンプレート/設計情報テンプレート.md` |
| `98_レビュー記録/設計判断ログ.md` | 人が決めた判断の結論、選択肢、理由、受け入れるリスク、前提、再検討の条件 | `99_テンプレート/設計判断ログテンプレート.md` |
| `98_レビュー記録/基本設計/基本設計からの申し送り.md` | 基本設計の範囲の外として、ほかの文書（機能の詳細設計、統合仕様、インフラ・運用、開発標準）に送った事項と送り先 | （段階 4 の「申し送り」の形式） |

納品物（`01_`〜`09_`。`CLAUDE.md` の「納品物と社内向けの文書」を参照）から、これらの社内向けのファイルへリンクしない。社内向けのファイルの番号（設計判断ログの `DL-xx`、申し送りの `HS-xx`、設計情報の「制約と決定済みのこと」の No、レビュー記録の指摘の No）も書かない。顧客はこれらのファイルを読めないため、番号を見ても中身が分からない。納品物には決めた結果と、顧客に説明する理由だけを書く。判断がどの文書に反映されたかは、設計判断ログの「反映した文書」で追う。

### レビューの途中経過（作業中フォルダ）

レビューの途中経過は、`98_レビュー記録/基本設計/作業中/` に置き、スキルが完了したら消す（9-4）。完了した後に残すのは、後の工程が読むファイルだけにする。

| 区分 | ファイル |
|---|---|
| 完了した後も残す | `98_レビュー記録/設計情報.md`、`98_レビュー記録/設計判断ログ.md`、`98_レビュー記録/基本設計/基本設計からの申し送り.md`、`98_レビュー記録/基本設計/確認事項一覧.md`（作った場合） |
| `作業中/` に置き、完了したら消す | 問いの一覧（`問いの一覧.md`）、ラウンドごとのレビュー記録（`*_review_r<ラウンド番号>.md`）、トレーサビリティ（`traceability.md`）、出典の照合（`出典の照合.md`）、波及の点検（`波及の点検_r*.md`）、反対役の確認（`反対役の確認.md`） |

- 残すファイルから、`作業中/` のファイルへリンクしない。ファイル名や指摘の No も書かない。消えた後に参照が切れるため。設計判断ログの「背景」や申し送りの「出どころ」には、レビューの指摘から来たことと、指摘の要旨を書く（例: 「非機能要件定義のレビューで、時間切れの秒数が決まっていないと指摘された」）。
- 途中で止まったとき（段階 7 の「止まって相談する条件」や、3 ラウンド後の打ち切り）は `作業中/` を消さない。`作業中/` が残っていることが、レビューが終わっていない印になる。

### テンプレート

- テンプレートは `99_テンプレート/` から探す。
- 合うテンプレートがない場合は、次の順で決める。勝手に章立てを決めて書き始めない。
  1. 設計情報、設計判断ログなら、このスキルに同梱の `assets/` のテンプレート（[設計情報](${CLAUDE_SKILL_DIR}/assets/設計情報テンプレート.md)、[設計判断ログ](${CLAUDE_SKILL_DIR}/assets/設計判断ログテンプレート.md)）を使う。`99_テンプレート/` に追加してチームで共有してよいか、ユーザーに確認する。
  2. 納品物のテンプレートがなければ、ひな型（project-template）の最新の `99_テンプレート/` から取り込んでよいか、ユーザーに確認する。取り込めない場合は、同じフォルダにある既存の文書の構成を調べ、テンプレート案を作ってユーザーに確認する。
- テンプレートが Markdown 以外（Excel や Word）で渡された場合は、作業を始める前に、Markdown 版のテンプレートを作ってよいかユーザーに確認する。

### 出力形式

- 記法は [記法ルール](${CLAUDE_PLUGIN_ROOT}/skills/design-export/references/markdown-rules.md) の範囲に限る。このルールは `design-export` スキルでの変換と照合の前提になっているため、必ず守る。
- `CLAUDE.md` のドキュメント作成ルール（Mermaid の使用、`[[]]` リンクの活用など）にも従う。

## 1. 進め方

次の段階で進める。設計書全体を一度に書かない。一度に書くと、AI は分からないことを一般論で埋め、仮定が決定事項のように見えてしまうため。

| 段階 | すること | 人がすること |
|---|---|---|
| 1. 前提の整理 | 入力を読み、設計情報を作る・更新する。設計を進める人の立場と、方式を書くのに欠かせない前提を質問する | 質問に答える |
| 2. 文書の地図 | 作る文書と、章ごとの「決めること」と「扱わないこと（送り先）」を表にする | 確認する |
| 3. 問いの一覧 | 聞きたいことを先に全部、問いの一覧にし、工程と優先度で仕分ける。工程が基本設計で優先度が高い問いだけを聞く | 決める |
| 4. 作成 | 決まったことと地図の範囲だけで書く。書いている途中で新しい選択が要ったら `【未決】` を置く。最後に、残った基本設計の問いをまとめて聞き、反映する | 決める |
| 5. レビュー | 新しいレビュアーで、文書のまとまりごとと文書をまたいでレビューする | — |
| 6. 指摘の仕分け | 重なった指摘をまとめ、指摘ごとに扱いの案を出す。直したら、修正の後の点検をする | 確認・受け入れ・将来に送るものと、新しい判断が要る直し方を決める |
| 7. 再レビュー | 「今すぐ直す」を直し、新しいレビュアーで再レビューする | — |
| 8. 反対役の確認 | 人の判断に見落としがないかと、出典のない決定がないかを、反対の立場から確かめる | 必要なら判断し直す |
| 9. 仕上げ | 推敲、仕様確定、確認事項一覧、作業中フォルダの片付け、報告 | — |

人に聞くのは、段階 1、段階 2、段階 3、段階 4 の最後、段階 6、段階 8 だけにし、それぞれ 1 回にまとめる（章ごと、文書ごとに確認を求めない）。それ以外の場面で人の判断が要ることに気づいたら、問いの一覧に足し、次に聞く場面まで本文には書かない。

## 2. 書くときの決まり

- **粒度を守る。** [references/granularity.md](${CLAUDE_SKILL_DIR}/references/granularity.md) の「決めること」だけを書く。範囲の外のことは本文に書かず、申し送りに書く。親切のつもりで細部や実装例を足さない。
- **テンプレートの構造を変えない。** 章立て・見出し・表の列は削除も並べ替えもしない。該当しない項目は削らずに「該当なし（理由: …）」と書く。
- **テンプレート内の記入指示や記入例（`{{…}}` や `（…を記述）`）は、本文で置き換える。** 指示文を残したままにしない。テンプレートの「**書き方のルール**」の箇条書きは作成者への指示なので、作った文書には残さない（見出しではないので、見出しの照合には影響しない）。
- **すべての設計項目に根拠を付ける。** 各項目に対応する要件 ID を記載する（テンプレートにトレーサビリティ欄があればそこへ、なければ項目末尾に `[根拠: FR-FAV-01]` の形式で）。要件 ID がなく、人が決めたことが根拠なら、`[根拠: 発注者の決定（2026-05-01）]` か `[根拠: 開発チームの決定（2026-05-01）]` のように、誰がいつ決めたかを書く。誰は、設計情報の「設計を進める人」の立場で、「発注者」か「開発チーム」のどちらかにする。「本人」「開発チームの選定」などのほかの書き方はしない。社内向けのファイルの番号（`DL-xx` など）は書かない。
- **決定と理由には、必ず出典がある。** 「〜の決定」「選んだ理由」「理由」に書けるのは、要件定義書に書かれたこと、設計情報に書かれた人の答え、設計判断ログに記録した人の判断と、その人が述べた理由か選んだ選択肢の説明だけである。人が理由を述べていなければ「—（未確認）」と書き、作成者が理由を考えて補わない。
- **人が答えた文言は、そのまま使う。** 水準や用語（「平日」など）を言い換えない。言い換えが要るなら、問いの一覧に足して確かめる。
- **書いている途中で、AI が決めない。** 構成要素やサービスを足す、用語の意味を解釈する、環境ごとに扱いを変える、理由を書く、など、出典のない選択が要ったら、本文には書かずに `【未決: Q-xx】` を置き、問いの一覧に足す（段階 4）。
- **要件にないことを作らない。AI が決めない。** 要件定義書、設計情報、判断ログから決められないことは推測で埋めず、問いの一覧に足して人に決めてもらう（「3. 問いの一覧と仕分け」）。`【要確認】` は、その場にいない関係者（発注者、運用部門など）の回答が要るものにだけ使い、確認先と理由を添える。設計を進める人が決められることは、`【要確認】` にせずに問いとして聞く。
- **用語・ID・名称を統一する。** 用語集と既存の文書の表記に合わせる。新しい画面 ID や API ID を採番するときは、既存の体系に従う。
- **同じことを 2 か所に書かない。** 段階 2 の「同じことを 2 か所に書かない」の表で、正とする文書にだけ書き、ほかの文書からはリンクで参照する。片方だけ直されてずれていくため。
- 文書の先頭（作成日・版）と末尾の変更履歴は、記法ルールの形にそろえる。このスキルの実行中は版を上げない。新しく作った文書は v0.1 のまま、変更履歴は「初版」の 1 行だけにする。既存の文書を更新した場合は、9-1 の後に 1 回だけ版を上げて変更履歴に追記する。レビューのラウンドごとに版を上げない。納品物の変更履歴には、文書の内容がどう変わったか（例: 「バックアップから戻す範囲を追加」）を書き、社内の作業の名前（レビューのラウンド、反対役の確認など）や社内向けのファイルの番号は書かない。
- 新しく作った文書は、そのフォルダの `README.md` の「ドキュメント一覧」の表に 1 行追加する。

使うマーカーは次のとおり。

| マーカー | 意味 |
|---|---|
| `【要確認】` | 人（顧客や関係者を含む）の回答を待っている |
| `【仮定】` | 作成者が仮に置いた前提。確かめる時期を添える。設計情報にだけ書き、設計書の本文には書かない |
| `【未決: Q-xx】` | 書いている途中で出た、人に聞いていない選択。問いの一覧の番号を添える。段階 4 の最後に聞いて消す。レビューに進む前に 0 件にする |

人が決めた判断は、設計書の本文に決めた結果を書き、理由は設計判断ログに書く。AI が決めたことを示すマーカー（`【設計判断】` など）は使わない。

## 3. 問いの一覧と仕分け

人に聞くことは、思いついたときにその場で聞かず、`98_レビュー記録/基本設計/作業中/問いの一覧.md` に集め、工程と優先度で仕分けてから聞く。仕分けないと、詳細設計やインフラ・運用で決めることまで基本設計で聞いてしまい、問いの数が増えて、人が本当に決めるべきことに集中できなくなるため。

### 問いの出し方

- 段階 1〜3 で、[references/question-checklist.md](${CLAUDE_SKILL_DIR}/references/question-checklist.md) の観点と立場を使い、要件定義書と設計情報から決まらないことを、先に全部、問いとして出す。
- 段階 4 の `【未決】`、段階 6 の仕分けで人の判断が要るもの、段階 8 の反対役の結果も、同じ一覧に足す。
- 問いは具体的に書き、なぜ要るかの根拠と、2〜4 個の選択肢を付ける。

| 列 | 内容 |
|---|---|
| No | `Q-01` から順に |
| 問い | 何を決めるか。具体的に（例: 「本番のほかに検証の環境を置くか」） |
| 根拠 | なぜ決める必要があるか（要件 ID、文書と章、レビューの指摘の要旨） |
| 選択肢 | 2〜4 個 |
| おすすめ | どれか 1 つと、その理由（設計情報の「判断の優先順位」と結び付ける） |
| 採らなかった場合の影響 | おすすめ以外を選んだときに何が変わるか |
| 工程 | 基本設計 / 機能の詳細設計 / 統合仕様 / インフラ・運用 / 開発標準・setup-architecture / 実装 |
| 優先度 | 高 / 中 / 低（下の基準） |
| 関係者 | 設計を進める人が決められるか、発注者やその場にいない関係者に確認が要るか |
| 扱い | 段階 3 で聞く / 段階 4 の最後に聞く / 申し送り（HS-xx） / 【要確認】 |
| 回答の原文 | 人が選んだ選択肢のラベルか、人が書いた答え。言い換えない |
| 記録 | 設計判断ログの番号か、設計情報の行 |

### 工程と優先度

工程は、[granularity.md](${CLAUDE_SKILL_DIR}/references/granularity.md) の文書ごとの範囲と送り先で決める。[question-checklist.md](${CLAUDE_SKILL_DIR}/references/question-checklist.md) の「基本設計では問いにしないもの」に当たるものは、基本設計の工程にしない。

優先度は、次のどれか 1 つでも当てはまれば「高」にする。

1. 答えがないと、基本設計の文書の章を書けない（構成、方式、環境、守る水準など）
2. 後で答えが変わると、複数の文書の書き直しや、発注者との合意のやり直しが要る
3. 契約、費用、法令、発注者の受け入れられないリスクにかかわり、進める前に合意が要る

当てはまらないものは「中」か「低」にする。

### 扱い

| 工程 | 優先度 | 扱い |
|---|---|---|
| 基本設計 | 高 | 段階 3 で、まとめて 1 回で聞く |
| 基本設計 | 中・低 | 段階 3 では聞かない。本文の該当箇所に `【未決: Q-xx】` を置いて書き進め、段階 4 の最後にまとめて 1 回で聞く |
| 基本設計以外 | — | 聞かない。申し送りに、送り先を付けて入れる |

- どの扱いでも、AI が代わりに決めない。聞くまでの間、本文には決めた結果を書かない。
- 聞くときは、選択肢から選べるものを AskUserQuestion で聞く（1 回に 4 問まで。おすすめを先頭に置く）。4 問を超えるときは、続けて AskUserQuestion を使う。選択肢に収まらないものは、チャットで番号を付けて聞く。選択肢の中で使う用語（「平日」など）は、聞くときに意味を書いておく。
- **1 つの問いは 1 つの質問として聞く。** 優先度が高い問いと、設計情報の「判断の優先順位」の上位（データの保全など）にかかわる問いは、まとめない。それぞれの選択肢に、採ったときの影響を description で書く。
- **まとめて「おすすめどおりでよいか」と聞いてよいのは、優先度が中・低の問いだけにする。** その場合も、聞く前にチャットに表を出し、問いごとに、すべての選択肢、おすすめとその理由、採らなかった場合の影響を見せる。おすすめだけの表で承認をもらわない。「一部を変える」を選べるようにし、変えたい問いの番号を書いてもらう。
- **答えが質問、異議、保留なら、決定として記録しない。** 「その他」の記入や返事が、問いへの質問（「なぜ今それを聞くのか」「違いは何か」など）、異議、保留だったら、まず答えるか説明し、同じ問いを聞き直す。問いを申し送りに回す、取り下げるときも、そう伝えて了承をもらう。
- **答えは、聞いたらすぐに記録する。** 次の作業に進む前に、設計判断ログ（「回答の原文」を含む）か設計情報に書き、問いの一覧の「記録」に番号を書く。問いの一覧にだけ答えを書いたままにしない（問いの一覧は作業中のもので、出典にならない）。
- 人がおすすめを選んだときは、おすすめに添えた理由を、選んだ選択肢の説明として設計判断ログの「理由」に書いてよい。その場合は「おすすめの理由として示したもの」と添える。
- その場にいない関係者の確認が要るものは、設計を進める人が決めずに `【要確認】` にしてよい。設計を進める人に確認先を向けた `【要確認】` は作らない。その場で聞く。
- 設計判断ログに残すのは、後から変えると影響が大きいもの、標準から外したもの、意見が割れたもの、制約で妥協したもの、暫定の対応である。それ以外の答えは設計情報に書く。判断した人が述べていない理由を、推測で書き足さない。
- 段階 3 で聞く問い（工程が基本設計で優先度が高いもの）が 10 件を超えるときは、粒度が細かすぎる可能性が高い。地図を見直し、詳細設計に送れるものを送る。

基本設計で、優先度が高くなりやすい問いの例は次のとおり。

- 方式の選択（構成、稼働場所、データベース、認証の方式）
- 非機能要件の水準。要件定義書にない項目は、おすすめの水準を項目ごとに並べ、まとめて 1 つの問いにする（項目ごとに 1 問にしない）。要件定義書で `【要確認】` のものが決まるまでの暫定の扱いも含める
- 環境の数と、本番への反映を自動にするか承認を挟むか、費用の見込みの前提
- 対象外にすること、将来に備えるかどうか（例: Phase 2 に今から備えるか）
- 開発標準の方針（層の分け方、テストの進め方などの採用する方式）
- 開発標準で使う主なフレームワークとライブラリ、テストと機械的な検査の道具（要件と方式から候補を挙げ、おすすめを示して選んでもらう）。`/project-dev:setup-architecture` は、開発標準に `【要確認】` が残っていると止まるため、基本設計で決める

## 段階 1. 前提の整理

1. 要件定義書を読む。要件 ID の体系（例: `FR-FAV-01`, `NFR-FAV-01`, `UC-FAV-01`）と、画面 ID の体系（例: `HOME-01`, `ADM-NEWS-01`）を把握する。ID がない場合は、見出し番号を要件の参照キーとして使い、その旨を最終報告に書く。
2. `CLAUDE.md` の「納品物の一覧」、`00_プロジェクト概要/用語集.md`、`00_プロジェクト概要/リポジトリ一覧.md`、既存の基本設計書、`98_レビュー記録/設計情報.md` と `98_レビュー記録/設計判断ログ.md`（あれば）を読む。
3. 要件定義書の中で **「詳細設計で定義」「詳細設計で決める」「別途定義」** など、判断を設計に委ねている箇所と、`【要確認】` を grep で洗い出す。基本設計では決めず、申し送りの最初の行にする（基本設計の方式に影響するものは、問いの一覧に足す）。
4. 設計情報テンプレートに沿って、`98_レビュー記録/設計情報.md` を作る（あれば更新する）。要件定義書から書けることは要件 ID で参照し、書けないことを質問の一覧にする。
5. 質問を 1 回にまとめて聞く。まず、設計を進める人の立場（発注者 / 開発チーム / 発注者と開発チームを兼ねる）を聞き、設計情報の「設計を進める人」に書く。根拠や仕様確定の「決めた人」は、この立場で書くため。次に、基本設計では、少なくとも次のことが決まっていないと方式を書けない。要件定義書や設計情報で決まっていなければ聞く。選んでもらったものは、選んだ理由も聞く（理由の選択肢を示し、複数選択と自由記入を許す）。理由を答えてもらえなければ「未確認」として記録し、理由を補わない。
   - コードリポジトリの構成（例: 画面とサーバーを分けるか、1 つにまとめるか）
   - 各リポジトリの言語・フレームワーク。**サーバー側の言語を選択肢で聞くときは、Rust を先頭に置く**
   - データベース
   - 稼働させる場所（クラウドの種類など）
   - 判断の優先順位（データの保全、運用の手間、費用、開発の速さ など）
   - 役割のうち、システムの作りが変わるもの：監視の通知を受ける人、本番の環境に入れる人、障害から復旧する人（利用者、運用部門、開発チームなど）。答えは設計情報の「利用者と運用者」に書く
   開発の進め方の取り決め（PR や設計書の承認、公開の許可と担当など）は聞かない。設計書で決めることではないため（[granularity.md](${CLAUDE_SKILL_DIR}/references/granularity.md) の「どの設計書でも決めないこと」）。
   答えを設計情報の「制約と決定済みのこと」に書く。答えが「未定」で、その場にいない関係者に確かめる必要があるなら `【要確認】` にし、確認先を書く。作成者が仮に置く前提は `【仮定】` として設計情報にだけ書き、ユーザーに伝える。

### 章ごとの範囲

作る文書ごとに、章ごとの「この章で決めること」と「扱わないこと（送り先）」を表にして、ユーザーに 1 回で確認してもらう。粒度の決まりを、この案件の文書に当てはめたものである。

基本設計の文書は数が多く、同じことを複数の文書に書くと、片方だけ直されてずれていく。次のものは、正とする文書にだけ書き、ほかの文書からはリンクで参照する。

| 主なライブラリと層の決まり | 開発標準 |

## 段階 3. 問いの一覧

「3. 問いの一覧と仕分け」に従って、問いの一覧を作り、仕分ける。この段階で聞くのは、工程が基本設計で優先度が高い問いだけである。仕分けた結果（工程ごと・優先度ごとの問いの数と、申し送りに回した問い）も、聞くときに 1 行で見せる。

## 段階 4. 作成

テンプレートに沿って、段階 2 の書く順に、地図の範囲だけを書く。

書いている途中で、出典のない選択が要ったら、本文には書かずに `【未決: Q-xx】` を置き、問いの一覧に足して書き進める。典型的なのは次の場面である。

- 構成要素やサービスを足す（例: 振り分けの仕組み、証明書、通知のサービス）
- 技術や方式を選んだ理由、仕様確定の理由を書く
- 人が答えた用語や水準を、別の言葉にする（例: 「平日」を「営業日」にする）
- 環境ごとに扱いを変える（例: 検証の環境では削除の保護をしない）
- 要件や答えにない振る舞いを決める（例: 削除の対象がないときの扱い）

全文書を書き終えたら、問いの一覧のうち、工程が基本設計で、まだ聞いていない問い（段階 3 で中・低にしたものと `【未決】`）を 1 回の機会にまとめて聞く（「扱い」の聞き方に従う。優先度が高くなった問いは 1 問ずつ聞く）。答えを反映して `【未決】` を消し、grep で 0 件になるまで段階 5 に進まない。

- **システム概要**：要件定義書を書き写さず、要約と要件 ID とリンクにする。機能の一覧の「主な画面」は、画面一覧を書いた後で埋める。
- **非機能要件定義**：テンプレートの項目を削らない。水準は確かめられる形（数値、条件）で書き、約束しない項目は「目標を置かない」と理由を書く。「実現の方針」は 1 行にし、詳しくは方式設計かインフラ方針設計の章を示す。
- **システム構成図**：利用者の通信の経路の図と、運用のための構成を分ける。
- **方式設計**：技術の選定、アプリケーションの構成、データの扱い、外部との連携、品質の確保の方針を、方式の名前ではなく顧客にとっての利点（保守性、品質など）で書く。構成要素の説明と非機能の水準は書き写さない。
- **インフラ方針設計**：方針までを書く。設定値や手順は申し送り（インフラ・運用）に回す。運用の体制は、段階 1 で答えてもらった役割を書く。
- **画面一覧・画面遷移**：画面 ID を採番する。
- **テーブル一覧・ER図**：テーブル名は、要件の用語を英語の複数形の snake_case にする（既存の統合仕様があれば、その体系に従う）。ER図には、主キーと外部キーのほかのカラムを書かない。
- **画面仕様書**：画面一覧と同じ画面 ID で、同じ順に書く。「元のデータ」はテーブル一覧のテーブル名で書く。
- **API一覧**：API ID は `API-<機能の略号>-<2 桁の連番>` で採番する。「使う画面」は画面一覧の画面 ID で書く。画面仕様書の「できる操作」のうち、データを読み書きするものに、対応する API があること。
- **バッチ処理一覧**：バッチ処理 ID は `BAT-<2 桁の連番>` で採番する。
- **開発標準**（開発ガイドライン）：コードリポジトリごとに、層と責務・依存してよい向き・迷いやすい配置の決め方・横断的なルール・テストの方針・機械的な検査の方法を具体的に決める。これが `/project-dev:setup-architecture` で各コードリポジトリの実装規約に落とし込まれる正本になる。ライブラリの使い方の細部と、検査の道具の設定（lint の規則、ビルドの設定）は書かない。方式設計、非機能要件定義、API一覧の方針は書き写さず、リンクで参照して、それを実装する決まりだけを書く。
- 開発手法やアーキテクチャの方式の名前（TDD、DDD、クリーンアーキテクチャなど）と具体的な決まりは、開発標準にだけ書く。`01_`〜`08_` の文書には混ぜない。
- 図は、1 つの図で 1 つのことを伝える。図の前の文で、何を伝える図かを書く。構成、データの流れ、処理の流れ、人の運用の流れを 1 つの図に混ぜない。
- 作った文書は、それぞれのフォルダの `README.md` の表に 1 行ずつ足す。

### 申し送り

範囲の外として本文に書かなかったことを、`98_レビュー記録/基本設計/基本設計からの申し送り.md` に、送り先を付けて書く。レビューで「申し送る」と仕分けた指摘と、問いの一覧で工程が基本設計以外になった問いも、ここに足す（「出どころ」には、問いの要旨を書く）。送り先は [granularity.md](${CLAUDE_SKILL_DIR}/references/granularity.md) の「送り先」から選ぶ。


- 「出どころ」には、レビューの記録のファイル名や指摘の No を書かず、指摘の要旨を書く。レビューの記録は `作業中/` に置き、完了時に消すため。
- 「対象の機能」は、送り先が機能の詳細設計のときだけ書く。複数の機能に共通するものは「全機能」とし、最初に作る機能の詳細設計で決める。
- 「決めた文書」は、送り先の文書を作った人が記入する。送り先が機能の詳細設計の行は、`/project-dev:design-to-tasks` がこの欄を確かめる。

### 自己点検

書き終えたら、レビューへ進む前に次を確かめる。

- 段階 2 の「作る文書」がすべてあり、それぞれのフォルダの `README.md` の表に載っていること。
- 要件 ID を一覧化し、設計書のどこで扱ったかの対応表（トレーサビリティマトリクス）を `98_レビュー記録/基本設計/作業中/traceability.md` に出力する（完了時に消す）。どこにも対応しない要件があれば、意図的な対象外か、申し送りか、漏れかを判定し、漏れなら設計書に追記する。
- 段階 2 の地図の「扱わないこと」が本文に書かれていないこと。
- 文書どうしで ID と名前がそろっていること。画面 ID（画面一覧、画面遷移、画面仕様書、API一覧、システム概要）、テーブル名（テーブル一覧、ER図、画面仕様書）、構成要素の名前（システム構成図、方式設計、インフラ方針設計）を grep で突き合わせる。
- 段階 2 の「同じことを 2 か所に書かない」の内容が、正とする文書のほかに書き写されていないこと。
- `【未決】` が 0 件で、「本人」が納品物と設計判断ログに出てこないこと（grep で確かめる）。
- **出典の照合**：納品物の「の決定（」「選んだ理由」「理由」の列と、根拠が要件 ID でない記述を grep で集め、1 件ずつ出典（要件 ID、設計情報の行、設計判断ログの番号）と突き合わせて、`98_レビュー記録/基本設計/作業中/出典の照合.md` に表で書く。出典のないものは、本文から外して `【未決】` にし、問いとして聞く。
- 納品物（`01_`〜`09_`）に、社内向けのファイルの番号（`DL-`、`HS-`、設計情報の No）がないこと（grep で確かめる）。
- テンプレートの見出しがすべて残っていること。
- 記法ルールの範囲外の記法を使っていないこと。特に、図（Mermaid）にしか書かれていない ID や名称がないか、閉じの `**` の直前が括弧・句読点になっていないかを確認する。

## 段階 5. レビュー（独立コンテキスト）

### 5-1. レビュアーの起動方法

レビューは **作成者（このセッション）とは文脈を共有しないサブエージェント** に任せる。

| 役割 | エージェント | 見るもの | 起動する数 |
|---|---|---|---|
| 文書のレビュー | `project-docs:basic-design-reviewer` | 文書を 1 つずつ、要件、テンプレート、粒度に照らす | 下の表のまとまりごとに 1 体 |
| 横断レビュー | `project-docs:basic-cross-reviewer` | 文書をまたいで、用語、数値、責任、データの正、正常と異常、図と本文、一覧どうしの整合を見る | 1 体 |
| 反対役 | `project-docs:basic-decision-challenger` | 人が決めた判断（採用、リスク受容、将来対応）に見落としがないか | 段階 8 で 1 体 |

ラウンドごとに、次を並列に起動する。

| レビュアー | レビュー対象 | 出力先の名前 |
|---|---|---|
| 文書のレビュー 1 体 | システム概要、システム構成図、方式設計 | 概要と構成 |
| 文書のレビュー 1 体 | 非機能要件定義、インフラ方針設計 | 非機能とインフラ |
| 文書のレビュー 1 体 | 画面一覧、画面遷移、画面仕様書 | 画面 |
| 文書のレビュー 1 体 | テーブル一覧、ER図、API一覧、バッチ処理一覧 | データとAPI |
| 文書のレビュー（コードリポジトリごとに 1 体） | 開発標準の、そのリポジトリの節。全リポジトリに共通の節は、最初のリポジトリのレビュアーだけが見る | 開発標準_<リポジトリ名> |
| 横断 1 体 | 基本設計の全文書（仕様確定を除く）と、用語集 | 横断 |

- 文書が多いため、関係の深い文書をまとめて 1 体のレビュアーに渡す。レビュアーは、まとまりの中の文書を 1 つずつレビューし、1 つの出力先に書く。まとまりの外の文書との食い違いは、横断レビュアーに任せる。
- 仕様確定は段階 9 で作るため、レビューの対象にしない。
- ラウンド 2 以降も、すべてのまとまりと横断を、新しいレビュアーでレビューする。
- Agent ツールで、上の名前のエージェントを起動する。この名前で起動できなければ、`general-purpose` を使い、`${CLAUDE_PLUGIN_ROOT}/agents/<エージェント名>.md` の本文（フロントマターを除く）をプロンプトの先頭に入れる。どちらの場合も、`fork` ではなく新しいコンテキストで起動する。
- **`subagent_type: "fork"` は使わない。** fork は作成時の会話や判断を引き継ぐため、作成者の思い込みまでレビュアーに移ってしまう。
- レビュアーに渡すのは **ファイルパスとレビュー範囲だけ** にする。作成時の判断理由、作成者の見解、結論を誘導する言葉、前のラウンドの指摘と対応は渡さない。設計情報と設計判断ログは、ファイルパスとして渡してよい（人が決めた前提であり、作成者の見解ではないため）。
- 同じレビュアーを SendMessage で使い回さない。**ラウンドごとに新しいエージェントを起動する。**
- 全員の結果がそろってから仕分けに進む（読んでいる途中で文書を書き換えない）。

### 5-2. レビュアーへのプロンプト（雛形）

以下の `{}` を埋めて渡す。これ以外の情報は足さない。

```
あなたは設計レビュアーです。指示はエージェント定義に従ってください。

作業ディレクトリ: {xxxxx_document の絶対パス}
レビュー対象: {まとまりの全文書のパス。横断レビューでは対象の全文書のパス}

設計判断ログ: 98_レビュー記録/設計判断ログ.md
テンプレート: {まとまりの全文書のテンプレートのパス。横断レビューでは「なし」}
申し送り: 98_レビュー記録/基本設計/基本設計からの申し送り.md
用語集: {00_プロジェクト概要/用語集.md。なければ「なし」}

```

## 段階 6. 指摘の仕分け

レビューは指摘を全部消すためのものではない。指摘されたリスクを、どう扱うかを決めるためのものである。指摘ごとに次のどれかに仕分け、レビュー記録の「対応」欄に書く。

| 仕分け | 条件 | 決める人 | 書くこと |
|---|---|---|---|
| 今すぐ直す | 設計が成り立たない、要件を満たさない、後から直すと影響が大きい | 作成者が案を出し、まとめて報告する | 直した箇所 |
| 関係者に確認 | 業務、費用、運用体制などの判断が要り、設計を進める人や作成者だけでは決められない | 人 | `【要確認】` にした箇所と確認先 |
| リスクとして受け入れる | 問題はあるが、発生しやすさ、影響、代わりの手段から、今回は対応しない | 人 | 受け入れる理由（設計判断ログの番号） |
| 将来に送る | 今は要らないが、条件が変われば必要になる | 人 | 何が起きたら見直すか（設計判断ログの番号） |
| 申し送る | 粒度の決まりで、基本設計では決めないことに当たる。人が決めた判断の、もう一段細かい点（判断の適用の細部）もここに入れる | 作成者（粒度の決まりに従う） | 申し送りの番号と送り先 |
| 不採用 | 指摘が誤り、または要件の範囲外 | 作成者。Critical は人 | 根拠（要件 ID、テンプレートの規定、粒度の決まりなど）。「問題ないと考える」だけの理由は認めない |

- **まず、重なった指摘をまとめる。** 複数のレビュアーが同じ問題を指摘していたら、1 つの問題として扱い、どのレビュアーの指摘をまとめたかを書く。ラウンドの件数（段階 7 の終わる条件を含む）は、まとめた後の問題の数で数える。
- 仕分けは、まず作成者が全件の案を作る。各指摘について、想定される問題、影響、起きやすさ、今直す場合と後で直す場合の違い、仕分けの案、その理由を短く書く。
- 「関係者に確認」「リスクとして受け入れる」「将来に送る」と、Critical の「不採用」は、人に決めてもらう。案を一覧にして 1 回で示す。
- **人が決めた判断の一段細かい点は、申し送るのを既定にする。** 設計判断ログと設計情報で人が決めたことについて、「では、その下の○○は」と求める指摘は、その判断が要件、ほかの記述、セキュリティ、データの消失と矛盾していない限り、基本設計では新しく決めずに申し送る。決めるたびに次のラウンドがさらに一段下を掘り、指摘が減らなくなるため。
- **新しい判断が要る直し方は、問いにする。** 直し方が、値、用語、対象の範囲、構成要素、環境ごとの扱いを変えたり足したりするなら、Minor でも作成者が決めずに問いの一覧に足し、ほかの人の判断と一緒に聞く。レビュー記録の「対応」欄には、直した箇所に加えて「新しい判断: なし」か「新しい判断: DL-xx」を必ず書く。
- **新しい判断を聞く前に、作成者が反対役の観点で点検する。** 判断の優先順位と比べたか、前提、受け入れることになるリスク、見直しの条件を、問いに添える。後で反対役の確認で同じ判断が覆るのを防ぐため。
- **指摘を直すときに、文書の粒度を上げない。** 細部を書き足して指摘を消さない。基本設計の粒度で決め直すか、申し送るか、問いとして人に返す。
- **レビュアーの修正案の文をそのまま採らない。** 修正の方向を参考に、正とする文書の書き方と、人が決めたことの文言に合わせて書く。
- **申し送り済みの事項が指摘されたとき**は、本文が申し送りと食い違っている場合と、セキュリティの事故やデータの消失に当たる場合だけ直す。それ以外は「不採用（申し送り済み HS-xx）」とする。申し送りを基本設計に戻す必要があると判断したら、問いにして人に決めてもらう。
- **判断が置き換わったら、前提も直す。** 新しい判断が前の判断や設計情報の前提を置き換えたら、前の判断の区分を「置き換え済み」にし、設計情報の関係する行も同時に直す。受け入れたリスクを変えたら、非機能要件定義の「約束の対象外」も同時に直す。
- 指摘に反論したくなったときほど、要件定義書と設計情報を読み直してから判断する。作成者は自分の書いたものを正しいと思い込みやすい。
- Minor は、作成者の判断で直すか、不採用にしてよい。ただし、新しい判断が要る直し方は問いにする。

### 6-1. 修正の後の点検

「今すぐ直す」を直したら、再レビューに進む前に次を行う。修正が新しい食い違いや欠陥を生むのを、レビュアーに見つけさせる前に止めるため。

1. 直すのは、段階 2 の「同じことを 2 か所に書かない」で正とする文書だけにする。ほかの文書に同じ事実が書き写されていたら、参照に置き換える。
2. 変えた事実や判断ごとに、探す語の一覧（変える前の文言、言い換え、関係する値や用語）と、正とする文書の表から決まる「影響する文書」の一覧を作る。探す語で全文書と用語集を grep し、書いている箇所をすべて直すか、参照に置き換える。古い文言だけで探さない（言い換えて書かれた箇所を拾えないため）。
3. 修正の差分を一覧にし、差分に段階 4 の自己点検（ID と名前の突き合わせ、書き写し、`【未決】`、出典の照合）をもう一度かける。
4. 新しいサブエージェント（`general-purpose`）を 1 体起動し、波及の漏れを探させる。渡すのは、作業ディレクトリ、修正の差分（`git diff` の出力か、変えた箇所の一覧）、正とする文書の表（段階 2）、出力先（`98_レビュー記録/基本設計/作業中/波及の点検_r{ラウンド番号}.md`）だけにする。指示は「差分で変わった事実や判断が、ほかの文書・用語集・設計情報・設計判断ログ・申し送りに、古いまま残っていないか、食い違っていないかだけを探し、箇所と古い記述を表で返す。設計書は書き換えない」とする。見つかったものを直してから再レビューに進む。

## 段階 7. 再レビューと終了条件

- 「今すぐ直す」を直したら、新しいレビュアーで再レビューする（段階 5 と同じ構成）。
- **終わる条件：** 最新のラウンドで、粒度の範囲内の Critical と Major のうち「今すぐ直す」に仕分けたものが 0 件になったこと（重なった指摘をまとめた後の数で数える）。それ以外の仕分け（確認、受け入れ、将来、申し送り、不採用）は、人の判断が記録されていれば残ってよい。
- **止まって相談する条件：** 次のどれかに当たるとき。3 ラウンドを待たずに止め、残件と、減らない理由（粒度が細かすぎる、前提が決まっていない、判断の一段下を掘られている、など）を見せて、ユーザーに判断を仰ぐ。
  - 「今すぐ直す」の件数が、前のラウンドの半分以下に減っていない
  - そのラウンドの仕分けで人に聞いた新しい判断の数が、前のラウンドより減っていない
- 最大 3 ラウンドで打ち切る。3 ラウンド後も「今すぐ直す」が残る場合は、残件を一覧にしてユーザーに判断を仰ぎ、次の段階には進まない。
- 再レビューのレビュアーにも、前のラウンドの指摘内容や対応内容は渡さない。前のラウンドの指摘が解消されたかどうかは、作成者が前回のレビュー記録と照らし合わせて自分で確認する。

## 段階 8. 反対役の確認

レビューが終わったら、`project-docs:basic-decision-challenger` を新しく 1 体起動し、人が決めた判断に見落としがないかを確かめる。渡すのは、作業ディレクトリ、設計判断ログ、設計情報、対象の文書のパスと、出力先（`98_レビュー記録/基本設計/作業中/反対役の確認.md`）だけにする。対象は、今回の設計で記録・変更した判断に限る。

- 結果の指摘は、関係する判断ごとにユーザーに見せる。判断を変えるかどうかは人が決める。変えたら、設計判断ログと設計書を直す。
- 反対役の確認は 1 回だけ行う。判断を変えて設計書を直した場合は、直した文書を含むまとまりのレビュアーと横断レビュアーを新しく起動し、1 回だけレビューする（判断の変更は、ほかの文書との食い違いを生みやすいため）。
- このレビューで出た「今すぐ直す」は直す。直したあとは再レビューしない代わりに、6-1 の修正の後の点検（出典の照合を含む）を必ず行い、直した指摘の一覧を報告に入れ、人が確かめられるようにする。人の判断が要る指摘や、新しい判断が要る直し方は、問いとして聞く。
- 反対役が挙げた「出典のない決定」は、本文から外して問いにし、聞いて決めてもらう。

## 段階 9. 仕上げ

### 9-1. 日本語の推敲

レビューが終わった設計書を、Skill ツールで `natural-japanese` スキルを呼び出して推敲する。対象は段階 4 で作った文書だけとし、レビュー記録は推敲しない。呼び出すときは、次の制約を必ず伝える。

- 見出し、章番号、表の構造（行・列）、テンプレートの項目名は変えない
- 要件 ID、画面 ID、API ID、テーブル名、カラム名、API パス、コード、数値、単位は一字も変えない
- `[[リンク]]` の中身は変えない
- `【要確認】` のマーカーは残す
- 推敲は文体と読みやすさに限る。設計内容の追加・削除・解釈の変更はしない
- 設計書の文体は「である調」で統一する（テンプレートや `CLAUDE.md` に指定があればそれに従う）
- Markdown の記法は記法ルールの範囲を守る
- 人が答えた水準や用語の文言（設計判断ログの「回答の原文」）は変えない

natural-japanese のスクリプトを Bash から実行するときは、文字化けで止まらないよう `PYTHONIOENCODING=utf-8` を付ける。

推敲後、次の機械的な確認を行う。

- 推敲前後で、要件 ID・各種 ID の出現回数が一致すること（grep で数えて比較する）
- 見出しの一覧と `[[リンク]]` の一覧が一致すること
- 表の数と、各表の行数・列数が一致すること
- 一致しなければ、推敲で消えた・変わった箇所を元に戻す
- 納品物（`01_`〜`09_`）に、社内向けのファイルの番号（`DL-`、`HS-`）や名前（設計情報、設計判断ログ、レビュー記録、反対役）が出てこないこと（grep で確かめる）

### 9-2. 仕様確定と確認事項一覧

`99_テンプレート/仕様確定テンプレート.md` に沿って、`02_基本設計/仕様確定.md` を作る。新しいことは決めず、すでに決まったことと `【要確認】` を、発注者が読める形に写す。

| 章 | 写す元 | 写し方 |
|---|---|---|
| 確定した仕様 | 設計判断ログのうち、「反映した文書」が `01_`〜`08_` の判断と、設計情報の「制約と決定済みのこと」のうち発注者が決めたもの | 事項、確定した内容、発注者に説明する理由、決めた人、決めた日、反映した文書の章。決めた人は設計情報の「設計を進める人」の立場で書く。開発チームが決め、発注者の了承をまだ得ていないものは「開発チーム（ご確認ください）」とする。理由は、設計判断ログの「理由」が「未確認」なら「—（未確認）」と書き、作成者が補わない |
| 確認をお願いする事項 | 基本設計の文書の `【要確認】` のうち、確認先が発注者のもの | 確認事項、背景、設計書の該当箇所、根拠の要件 |

- 判断の番号（`DL-xx`）や設計情報の No は書かない。
- 確認先が発注者でない `【要確認】`（運用部門など社内の関係者）は、仕様確定ではなく `98_レビュー記録/基本設計/確認事項一覧.md` に、次の表で書く。該当がなければ確認事項一覧は作らない。

  | No | 確認事項 | 背景（なぜ決められないか） | 設計書の該当箇所 | 根拠の要件 | 確認先 | 回答 |
  |---|---|---|---|---|---|---|

- 作ったら、9-1 と同じ制約で推敲し、次を grep で確かめる。設計判断ログの判断のうち「反映した文書」が `01_`〜`08_` のものがすべて載っていること。確認先が発注者の `【要確認】` がすべて載っていること。社内向けのファイルの番号がないこと。
- 回答をもらったら、設計書を直して版を上げ、仕様確定（または確認事項一覧）の「回答」欄を埋め、設計判断ログに記録する。仕様確定では、回答をもらった事項を「確定した仕様」に移す。

### 9-3. 改善を戻す

レビューで繰り返し出た種類の指摘（ラウンドや文書をまたいで 2 回以上出たもの）があれば、`references/review-checklist.md` の「プロジェクト固有」に足す観点か、テンプレートの記入ルールに足す内容の案として、報告に書く。追加するかどうかはユーザーが決める。

### 9-4. 作業中フォルダの片付け

9-1〜9-3 を終え、9-6 の報告に使う件数（ラウンドごとの仕分けの件数、反対役の確認の結果、反対役の確認の後のレビューで直した指摘）を控えたら、`98_レビュー記録/基本設計/作業中/` をフォルダごと消す。

- 消す前に、残すファイル（設計情報、設計判断ログ、申し送り、確認事項一覧）と納品物に `作業中/` のファイルへの参照が残っていないことを grep で確かめる。残っていれば、指摘の要旨に書き換えてから消す。
- 消すのは、段階 7 の終わる条件を満たし、段階 8 と 9-1〜9-3 を終えたときだけにする。途中で止まったときは消さない。
- `作業中/` の中にコミット済みのファイルがあれば、消したことを報告に書く（`git status` に削除として出るため）。

### 9-5. コミット

コミットは `xxxxx_document` リポジトリで行い、コードのリポジトリの変更と混ぜない。コミットや PR の作成は、ユーザーに指示されたときだけ行う。指示されたら、`develop` から作業用のブランチ（例: `feature/<担当者>/basic-design`）を切って作業し、PR の向き先は `develop` にする。ブランチ運用が `CLAUDE.md` に書かれていれば、それに従う。

### 9-6. 報告

ユーザーには次の内容を報告する。結論から書き、各項目は箇条書きで短くまとめる。

1. 作成・更新した文書の一覧と、`作業中/` を消したこと
2. 問いの数（工程ごと・優先度ごと）と、人に聞いた回数。申し送りに回した問いの数
3. レビューのラウンド数と、仕分けごとの件数の推移（重なりをまとめた後の数）。反対役の確認の後のレビューで直した指摘の一覧
4. 人が決めた判断（設計判断ログの番号と結論）と、反対役の確認の結果
5. `【要確認】` の件数と、仕様確定と確認事項一覧のパス
6. 申し送りの件数（送り先ごと）とパス
7. 改善を戻す案（9-3）

次の工程として、機能ごとの詳細設計は `/project-docs:detailed-design <機能名>` で、開発標準のコードリポジトリへの落とし込みは各コードリポジトリで `/project-dev:setup-architecture` で行うことを添える。Word や Excel での納品が必要な場合は、`/project-docs:design-export` で変換できることを最後に 1 行で添える。
