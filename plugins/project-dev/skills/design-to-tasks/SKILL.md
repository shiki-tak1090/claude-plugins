# 詳細設計の実装タスクへの分解

確定した詳細設計書を、実装タスクに分解する。タスクはドキュメントリポジトリの `97_タスク分解/<機能名>.md` に書き出す。このファイルが、次の 2 つの役割を持つ。

- **Backlog への起票の元**：各タスクの「件名」と「本文」を、人がそのまま Backlog の課題に貼り付ける
- **`/project-dev:implement` の入力**：コードリポジトリから `../<案件名>_document/97_タスク分解/` を読み、タスク ID で実装を始められる

Backlog への起票は人が行う。このスキルは Backlog に接続しない。

## 0. 前提の確認

1. `<案件名>_document` リポジトリの直下で実行されていること。
2. 対象の詳細設計書があること。引数が機能名なら `03_詳細設計/` から探す。
3. **設計が確定していること。** 次のどれかに当たれば、一覧にしてユーザーに見せ、進めてよいか確認する。
   - 詳細設計書や、関連する統合仕様（`04_API仕様/`、`05_DB設計/`）に、コミットされていない変更がある（`git status`）。どの版の設計から分解したかを記録できなくなるため
   - 設計書に `【要確認】` `【基本設計への差し戻し候補】` が残っている
   - `98_レビュー記録/<機能名>/` の最新のラウンドのレビュー記録に、「対応」欄が空の指摘か、「今すぐ直す」に仕分けて直していない Critical・Major の指摘がある
   - `98_レビュー記録/基本設計/詳細設計への申し送り.md` に、この機能が対象で「決めた詳細設計」が空の行がある
4. 同じ機能のタスクファイルがすでにある場合は、上書きせず、差分（追加・変更・不要になったタスク）を提案する。起票済みのタスク（Backlog の課題キーが記入されたもの）の ID は変えない。
5. `09_開発標準/開発標準.md` があり、タスクの対象になるコードリポジトリの節があること。なければ止まり、先に `/project-docs:system-design basic` で開発標準を作るよう伝える（実装の配置を決められないため）。

## 1. 読むもの

- 対象の詳細設計書
- 詳細設計書から参照されている統合仕様の節（`04_API仕様/API設計書.md`、`openapi.yaml`、`05_DB設計/テーブル定義.md`）
- 要件定義書（受け入れ条件の確認のため）
- `00_プロジェクト概要/リポジトリ一覧.md`（タスクの対象リポジトリを決めるため）
- `09_開発標準/開発標準.md` の、対象リポジトリの「層と責務」「迷いやすい配置の決め方」と「採用する方針」（タスクの「実装の配置」とドメインモデルを決めるため）

## 2. 分解のルール

- **1 タスク = 1 つのリポジトリの 1 つの PR。** 複数のリポジトリにまたがるタスクは作らない。
- **大きさの目安は、レビュー担当者が 1 回で読み切れる量。** 迷ったら分ける。1 つのエンドポイントや 1 つの画面を目安にする。
- **作る順に並べ、依存関係を書く。** 原則は次の順にする。
  1. DB のマイグレーション
  2. バックエンドの API（統合仕様の `openapi.yaml` に沿う）
  3. フロントエンド（API が未完成でも、`openapi.yaml` からモックを作れば並行して進められる。その場合は依存ではなく「関連」と書く）
  4. インフラは、必要になる時点に合わせて並べる
- **受け入れ条件は、設計書から写す。** 入力チェック、異常系、業務ルール、境界値を、テストに落とせる粒度のチェックボックスにする。設計書にない条件を足さない。
- **設計から一意に決まらない振る舞いは、該当するタスクの「未決事項」に書く。** 例: 複数の入力が同時に不正なときにどのエラーを返すか、想定外の型が渡されたときの扱い。受け入れ条件には入れず、報告の中だけで済ませることもしない（実装するときに見えなくなるため）。未決事項は、設計書を直して解消するまで残す。
- **各タスクに「実装の配置」を書く。** 開発標準の「層と責務」と「迷いやすい配置の決め方」に従い、そのタスクでどの層に何を作る・変えるかを書く。開発標準から一意に決まらない配置は、推測で決めずに「未決事項」に書く。実装の配置は社内向けの内容なので、納品物の詳細設計書ではなく、このタスクファイル（社内向け）に書く。
- **開発標準でドメインモデルの考え方（DDD など）を採用している場合は、機能のドメインモデルをタスクファイルの冒頭に書く。** 集約、エンティティ、値オブジェクトと、それぞれが守る業務ルール（不変条件）を、詳細設計書の業務ルールから写す。詳細設計書にない業務ルールを足さない。
- **設計の参照は、ファイルパスと節の見出しで書く。** 行番号は使わない（設計が直されるとずれるため）。
- **タスク ID は `T-<機能の略号>-<2 桁の連番>`** にする（例: `T-FAV-01`）。機能の略号は、要件 ID（`FR-FAV-01` など）の略号に合わせる。

## 3. タスクファイルの形式

`97_タスク分解/<機能名>.md` に、次の形で書く。

````markdown
# {{機能名}} 実装タスク

作成日：{{YYYY-MM-DD}}
版：v0.1

---

## 分解元

| 項目 | 内容 |
|---|---|
| 詳細設計書 | [[03_詳細設計/{{機能名}}設計]] |
| 設計の版（コミット） | `{{git rev-parse --short HEAD の値}}` |
| 開発標準 | [[09_開発標準/開発標準]]（版: {{開発標準の版}}） |
| 対応する要件 | {{FR-XXX-01〜}} |

## ドメインモデル

開発標準でドメインモデルの考え方を採用していない場合は「該当なし（開発標準で採用していないため）」と書く。

| 種類 | 名前 | 属するもの・持つ値 | 守る業務ルール（不変条件） | 根拠 |
|---|---|---|---|---|
| （集約 / エンティティ / 値オブジェクト） | （名前） | （例: 集約 `Plant` に属する） | （例: 水やり間隔は 1〜60 日） | （例: 詳細設計書「業務ルール」No.1） |

## タスク一覧

| ID | リポジトリ | 件名 | 依存 | Backlog の課題キー |
|---|---|---|---|---|
| T-XXX-01 | `xxxxx_backend` | （件名） | — | （起票後に記入） |

---

## T-XXX-01: {{件名}}

**Backlog に貼る件名**: `[backend] {{件名}}`

**Backlog に貼る本文**:

```
■ 対象リポジトリ
xxxxx_backend

■ 概要
（何を作るか。2〜3 文）

■ 設計の参照
- 03_詳細設計/{{機能名}}設計.md「{{節の見出し}}」
- 04_API仕様/openapi.yaml「{{METHOD}} /api/v1/{{path}}」
- 設計の版: {{コミット}}

■ 対応する要件
FR-XXX-01、FR-XXX-02

■ 実装の配置
- domain: （例: 値オブジェクト WateringInterval を新規作成）
- usecase: （例: RegisterPlant を新規作成。Port PlantRepository を定義）
- infrastructure: （例: PlantRepository の DB 実装を新規作成）

■ 受け入れ条件
- [ ] （条件。設計書から写す）
- [ ] （条件）

■ 未決事項
（設計から一意に決まらない振る舞い。なければ「なし」。残っている間は実装に着手しない）
- （例: total と region が両方不正なとき、どちらのエラーを返すか）

■ 依存
（先に終わっている必要があるタスク。なければ「なし」）

■ 対象外
（このタスクではやらないこと）

■ 実装の開始
xxxxx_backend で `/project-dev:implement T-XXX-01`
```
````

本文は、Backlog の課題にそのまま貼り付けられるよう、Markdown の記法に頼らない書き方にする（Backlog の記法設定によっては Markdown が表示されないため）。

## 4. 確認と保存

1. タスク一覧（ID、リポジトリ、件名、依存）を先にユーザーに見せ、分け方の了承を得る。
2. 了承を得たら、タスクファイルを書き出し、`97_タスク分解/README.md` の一覧に 1 行追加する。
3. コミットは、ユーザーに指示されたときだけ行う。

## 5. 報告

次の内容を報告する。

1. 作成したタスクファイルのパスと、タスクの数（リポジトリ別）
2. 作業の順序（依存関係）
3. 次の手順：
   - 各タスクを Backlog に起票し、発行された課題キーをタスク一覧の表に記入する（記入はこのスキルに頼んでもよい）
   - 実装は、対象のコードリポジトリで `/project-dev:implement <タスク ID>` を実行する
4. 未決事項の一覧（タスク ID ごと）。未決事項のあるタスクは、設計書を直して未決事項を消すまで実装に着手できないことを伝える。設計書を直したら、このスキルをもう一度実行してタスクを更新する
