# 設計レビュー観点

レビュアーは、レビュー種別に応じて「共通」と該当する節の観点をすべて確認する。プロジェクト固有の観点は末尾の「プロジェクト固有」に追記して使う。

## 共通

- [ ] **網羅性**: 要件定義書の要件で、この設計書が扱うべきものがすべて扱われているか。対象外にした要件に理由が書かれているか
- [ ] **根拠**: 各設計項目に要件 ID などの根拠があるか。要件にない機能・仕様が根拠なく追加されていないか
- [ ] **テンプレート準拠**: 必須の章・項目がすべて埋まっているか。記入指示や記入例が残っていないか
- [ ] **一意性**: 実装者が 2 通り以上に解釈できる記述がないか（「適切に」「必要に応じて」「など」「等」で範囲がぼかされていないか）
- [ ] **矛盾**: 同じ設計書の中で、数値・名称・振る舞いが食い違っていないか
- [ ] **用語**: 同じものを違う名前で呼んでいないか。`00_プロジェクト概要/用語集.md` に従っているか
- [ ] **版管理**: 先頭の作成日・版と、末尾の変更履歴があるか。更新した文書の版が上がっているか
- [ ] **未決事項**: `【要確認】` が、確認相手と確認内容が分かる形で書かれているか。未決なのに決まったかのように書かれた箇所がないか

## 基本設計

- [ ] **業務・機能**: 業務フローのすべての分岐に、対応する機能があるか
- [ ] **画面**: 画面一覧・画面遷移に、エラー時・キャンセル時・タイムアウト時の遷移があるか。権限ごとの表示差異が書かれているか
- [ ] **データ**: エンティティと主要項目、関連（多重度）、保持期間、削除方針（論理削除・物理削除）が決まっているか
- [ ] **外部連携**: 連携先ごとに、方式、頻度、データ形式、障害時の振る舞い（リトライ・通知・手動復旧）が書かれているか
- [ ] **非機能**: 性能目標、可用性、セキュリティ（認証・認可・個人情報の扱い）、運用・監視、バックアップの方針が要件を満たしているか
- [ ] **権限**: ロールと操作の対応が網羅されているか。権限のないユーザーが操作した場合の振る舞いが決まっているか
- [ ] **移行**: 既存データや既存システムからの移行が必要な場合、その方針があるか
- [ ] **アーキテクチャ**: アーキテクチャ設計が、方式の名前を並べるだけでなく、コードリポジトリごとに「層と責務」「依存してよい向き」「迷いやすい配置の決め方」「横断的なルール」「テストの方針」を具体的に決めているか。各ルールを、機械的な検査かレビューのどちらで確かめるかが決まっているか。守らせられないルール（全員が守れない、守ったかを確かめられない）が入っていないか

## 詳細設計

- [ ] **上位設計との整合**: 基本設計で定義した機能・画面・データ・ID がすべて詳細化されているか。基本設計と矛盾していないか
- [ ] **委ねられた事項**: 要件定義書で「詳細設計で定義」「別途定義」などとされた事項が、すべて決まっているか `【要確認】` になっているか（要件定義書を grep して自分で数える）
- [ ] **入力チェック**: 各入力項目の型、桁数、必須・任意、形式、範囲、相関チェックが決まっているか
- [ ] **境界値**: 0 件、1 件、上限件数、最大桁、日付の境界（月末・年末・うるう年・タイムゾーン）が考慮されているか
- [ ] **異常系**: 例外ごとのエラーコード、メッセージ、ログ出力、ユーザーへの表示、処理の継続・中断が決まっているか
- [ ] **トランザクション**: トランザクション境界、排他制御（楽観・悲観）、同時更新時の振る舞い、ロールバック範囲が決まっているか
- [ ] **冪等性**: 二重送信、リトライ、バッチの再実行で、データが重複・破損しないか
- [ ] **API**: エンドポイントごとにリクエスト・レスポンスの全項目、ステータスコード、エラー形式、認証方式が定義されているか
- [ ] **DB**: テーブル定義（型、桁、NULL 可否、デフォルト値、制約）、インデックス、検索条件とインデックスの対応があるか
- [ ] **バッチ**: 起動条件、処理順序、対象データの抽出条件、件数見積もり、途中失敗時の再開方法があるか
- [ ] **セキュリティ**: 入力値のエスケープ、SQL インジェクション・XSS・CSRF 対策、機密情報のマスキング・暗号化、ログに個人情報を出さない設計か
- [ ] **テスト可能性**: 各処理の期待結果が、テストケースに落とせる粒度で書かれているか

## 統合仕様との整合性

- [ ] 詳細設計書に「新規・変更」と書かれたテーブルとエンドポイントが、すべて統合仕様（`05_DB設計/テーブル定義.md`、`04_API仕様/API設計書.md`、`04_API仕様/openapi.yaml`）に反映されているか。逆に、統合仕様にだけある変更がないか
- [ ] `API設計書.md` と `openapi.yaml` で、パス、メソッド、パラメータ、型、必須、ステータスコードが一致しているか
- [ ] `テーブル定義.md` と `ER図.md` で、テーブル、主キー、外部キー、多重度が一致しているか
- [ ] 詳細設計書が統合仕様と重複して全項目の定義を書いていないか（重複していれば、どちらかが古くなる）
- [ ] 既存のテーブルやエンドポイントを変更している場合、影響する他の機能が `【影響確認】` として挙がっているか
- [ ] 同じ ID・名称が、すべての文書で同じ意味・同じ表記で使われているか。参照している ID（画面 ID、テーブル名など）が定義元に実在するか
- [ ] `[[リンク]]` の参照先が実在するか
- [ ] トレーサビリティマトリクスと設計書本文の対応が一致しているか
