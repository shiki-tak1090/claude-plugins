# 基本設計のレビュー観点

レビュアーは、「共通」と「基本設計」の観点をすべて確認する。横断レビュアーは、エージェント定義の「見るテーマ」に加えて「文書どうしの整合」を確認する。プロジェクト固有の観点は末尾の「プロジェクト固有」に追記して使う。

どの観点も、粒度の決まり（`granularity.md`）の範囲で確認する。例えば「一意性」は、基本設計の粒度で決めるべきことについてだけ確かめる。詳細設計で決めることが 2 通りに読めても、指摘にはしない（申し送りに書く）。

## 共通

- [ ] **納品物と社内向けの分離**: `01_`〜`08_` の設計書に、開発チームの内部の内容（開発手法の名前、層の細かな決まり、実装の配置）が混ざっていないか。これらは `09_開発標準/`（開発ガイドライン）やタスクファイルに書く。`01_`〜`09_` の納品物に、社内向けのファイル（設計情報、設計判断ログ、申し送り、レビュー記録）へのリンクや番号がないか

- [ ] **粒度**: 詳細設計で決めることが本文に書かれていないか（細かすぎないか）
- [ ] **前提と判断**: 設計情報の制約・決定済みのことと、設計判断ログの結論に従っているか。設計情報にない前提を、設計書が一般論で補っていないか
- [ ] **網羅性**: 要件定義書の要件で、この設計書が扱うべきものがすべて扱われているか。対象外にした要件に理由が書かれているか
- [ ] **根拠**: 各設計項目に要件 ID などの根拠があるか。要件にない機能・仕様が根拠なく追加されていないか
- [ ] **テンプレート準拠**: 必須の章・項目がすべて埋まっているか。記入指示や記入例が残っていないか
- [ ] **一意性**: 実装者が 2 通り以上に解釈できる記述がないか（「適切に」「必要に応じて」「など」「等」で範囲がぼかされていないか）
- [ ] **矛盾**: 同じ設計書の中で、数値・名称・振る舞いが食い違っていないか
- [ ] **用語**: 同じものを違う名前で呼んでいないか。`00_プロジェクト概要/用語集.md` に従っているか
- [ ] **版管理**: 先頭の作成日・版と、末尾の変更履歴があるか。更新した文書の版が上がっているか
- [ ] **未決事項**: `【要確認】` が、確認相手と確認内容が分かる形で書かれているか。未決なのに決まったかのように書かれた箇所がないか。作成者の仮定（`【仮定】`）が決定事項として本文に書かれていないか

## 基本設計

- [ ] **作る文書**: `CLAUDE.md` の「納品物の一覧」の基本設計の納品物が、すべて作られているか。該当しない文書に「該当なし」と理由が書かれているか
- [ ] **同じことを 2 か所に書かない**: 構成要素、水準、保持の期間など、正とする文書が決まっている内容が、ほかの文書に書き写されていないか（basic.md の「同じことを 2 か所に書かない」）
- [ ] **システム概要**: 目的、利用者、範囲、機能の一覧、業務の流れが、要件定義書と食い違わずに要約されているか。要件を書き写していないか
- [ ] **業務・機能**: 業務フローのすべての分岐に、対応する機能があるか
- [ ] **画面**: 画面一覧・画面遷移に、エラー時・キャンセル時・タイムアウト時の遷移があるか。権限ごとの表示差異が書かれているか
- [ ] **データ**: テーブル一覧に、テーブルごとの主に持つ情報、保持の期間、削除の方針、個人情報の有無があるか。ER図に、テーブル、主キー、外部キー、関係の多重度があり、テーブル一覧と一致しているか。主キーと外部キーのほかのカラムが書かれていないか
- [ ] **API一覧**: 画面仕様書のデータを読み書きする操作と、バッチ処理と、外部との連携に、対応する API がすべてあるか。要求と応答の項目まで書かれていないか
- [ ] **画面仕様書**: 画面一覧のすべての画面があり、領域の並び、表示する情報と元のデータ、できる操作が決まっているか。項目の型や桁、文言まで書かれていないか
- [ ] **バッチ処理**: 要件にある定期的な処理や、決まった時刻に動く処理が、すべてバッチ処理一覧にあるか。動くきっかけと、失敗したときの扱いの方針があるか
- [ ] **外部連携**: 連携先ごとに、方式、頻度、データ形式、障害時の振る舞い（リトライ・通知・手動復旧）が書かれているか
- [ ] **非機能**: 非機能要件定義の各項目の水準が、確かめられる形（数値、条件）で書かれ、要件を満たしているか。約束しない項目に理由があるか。要件定義書にない水準に、決めた人と日の根拠があるか
- [ ] **インフラ方針**: 環境、ネットワーク、可用性の構成、バックアップ、監視、運用の体制、反映の方針、費用の見込みが、方針の粒度で決まっているか。非機能要件定義の水準を守れる方針になっているか。設定値や手順まで書かれていないか
- [ ] **権限**: ロールと操作の対応が網羅されているか。権限のないユーザーが操作した場合の振る舞いが決まっているか
- [ ] **移行**: 既存データや既存システムからの移行が必要な場合、その方針があるか
- [ ] **方式設計**: 技術の選定とその理由、アプリケーションの構成、データの扱いが、顧客に伝わる言葉（何が良くなるか）で書かれているか。システム構成図の構成要素と食い違っていないか。開発チームの内部の決まり（層の細かなルール、テストの書き方、TDD・DDD などの手法の名前）が混ざっていないか
- [ ] **開発標準**: コードリポジトリごとに「層と責務」「依存してよい向き」「迷いやすい配置の決め方」「横断的なルール」「テストの方針」が具体的に決まっているか。方式の名前を並べるだけで終わっていないか。各ルールを、機械的な検査かレビューのどちらで確かめるかが決まっているか。守らせられないルールが入っていないか。方式設計の内容と食い違っていないか

## 文書どうしの整合（横断レビュー）

- [ ] 画面 ID が、画面一覧、画面遷移、画面仕様書、API一覧、システム概要で同じか。参照している画面 ID が画面一覧にあるか
- [ ] テーブル名が、テーブル一覧、ER図、画面仕様書の「元のデータ」で同じか
- [ ] 構成要素の名前が、システム構成図、方式設計、インフラ方針設計で同じか
- [ ] 非機能要件定義の水準と、インフラ方針設計・方式設計の方針が食い違っていないか
- [ ] 同じ ID・名称が、すべての文書で同じ意味・同じ表記で使われているか
- [ ] `[[リンク]]` の参照先が実在するか
- [ ] トレーサビリティマトリクスと設計書本文の対応が一致しているか
